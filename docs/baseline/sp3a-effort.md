## 2. 비율

개정 §6.3 의 선례는 "SP0~SP2 추정 합 7~8주 → 달력 약 4일 → 추정의 약 0.1배"였다. 같은 방식(경과 달력일 ÷ 추정 노동일 — 1주 = 5일)으로:

| 기준 | 계산 | 비율 |
|---|---|---|
| SP3a 경과 3.6일 ÷ 스펙 추정 중간 5.3주(26.5일) | 3.6 / 26.5 | **0.14** |
| 같은 경과 ÷ 추정 하한 4.3주(21.5일) · 상한 6.3주(31.5일) | 3.6 / 21.5 · 3.6 / 31.5 | 0.17 · 0.11 |
| (참고) SP0~SP2 | 4 / 37.5 | 0.11 |

SP3a 는 SP0~SP2 보다 약간 느리다(0.14 대 0.11). 이유는 코드를 쓰는 속도가 아니라 **검증 비용**이다:

- Phase B 는 27.6시간 중 마지막 3시간이 리뷰 3건(B7·B8·B9)·수정 라운드·E2E·성능·눈확인이었다. 구현이 아니라 검증이 지배했다.
- Phase C 는 구현 18커밋이 계획·리뷰 없이 쌓였고, 그 뒤 리뷰 3건·수정·E2E(재시작·실패 세 번)·눈확인·문서가 구현 시간의 약 0.8배를 썼다. 리뷰와 눈확인에서 실제 결함(조용한 데이터 되돌림, 화면 깨짐 4건)이 나왔으므로 낭비가 아니라 필요한 비용이었다.
- Phase D 는 처음부터 작은 단위(RPC 전환 → 읽기 액션 → 화면 → E2E)로 테스트를 먼저 쓰고 단계마다 검증했고 약 1시간에 끝났다(추정). 한 표본이라 일반화하지 않지만, 검증을 구현 뒤로 미루지 않는 쪽이 싸다는 Phase B·C 원장의 교훈과 방향이 같다.

## 3. 남은 일정 재계산 (추정)

개정 §6.3 표(레인 A 임계 경로)에서 SP3a 를 실측으로 바꾸고 나머지에 같은 비율을 적용한다. **아래는 추정이고, 비율은 한 표본(SP3a)과 한 선례(SP0~SP2)에서 나왔다.**

| 항목 | 값 |
|---|---|
| 레인 A 남은 추정(SP4 2.5 + SP5 4 + SP5b 2.5 + SP5c 3 + SP6 3 + SP9 2.5, 개정 표 기준) | 17.5주 + MIN-ATT 1~1.5주 ≈ **18.5~19주**(H1·H2 는 끝났다) |
| 에이전트 작업 환산(× 0.11~0.17, 노동일 기준) | 19주 × 5일 = 95일 → **약 10.5~16일(약 2.1~3.2주)** |
| 사람 게이트 대기(개정 §6.3 의 가정 그대로) | 2~5주 |
| **달력 추정** | **약 4~8주**(개정 표의 "약 5~10주"보다 하한이 낮다) — 사람 게이트가 일정을 정한다. 외부 팀 일정 제외 |

- 사람 게이트는 그대로 다섯이다: G0 승인과 6.7 결정, `ui/` 브랜치 눈확인(SP3a 는 이미 에이전트가 헤드리스로 확인했다 — 사용자 확인 #10), SP6 Office 열림 확인, SP7 상대 팀 릴리스, SP9 제3자 배포.
- SP3a 의 눈확인이 에이전트 몫이었던 만큼 SP3b UI-3 게이트에서 **사람이 직접 보는 눈확인**이 처음으로 일정에 들어온다 — 그 대기 시간은 위 비율에 들어 있지 않다.
- 레인 B(SP3b)는 SP3a 와 병렬로 시작해 UI-0 과제 0~3 까지 끝났다(`sp3b/ui0`). 이 표의 레인 A 값에 영향을 주지 않는다.

## 4. 이 계산이 틀릴 수 있는 곳

- 에이전트 시간을 커밋 시각의 경과로 어림했다 — 밤샘·대기·재시작·리뷰 서브에이전트의 병렬 시간이 섞인다. 원장이 있는 Phase A·B 는 기록값, C·D·마감은 추정이다.
- SP3a 는 DB(마이그레이션 한 개)와 게이트·테스트가 많은 SP 였다. 화면 중심 SP(SP5b·SP5c)나 Office 출력 SP(SP6)는 검증 비용의 모양이 다르다 — 눈확인 비중이 더 크다.
- 개정 §6.3 의 "주"는 달력이 아니라 상대 크기다. 이 문서의 달력 환산은 한 가정(1주 = 5노동일)을 둔 것이다.
