같은 앱 빌드가 1.06 과 1.54 를 냈으므로 앱 차이가 아니라 측정 조건 차이로 보았다. 리뷰(P2-1)가 짚은 방법상의 편향 셋:
① 순서 고정(기준선 → 후보) — 회차 안 부하 흐름이 늘 후보에 실린다, ② 후보만 판정 측정 직전에 1,500행까지 시드(autovacuum·캐시 상태가 다르다),
③ n 30 의 p95 는 위에서 둘째 값 근처라 이상치 하나에 흔들린다.

**정직한 한계(A2 최종 재리뷰 P2-1).** 위 네 회차는 p95 만이 아니라 p50 비율도 1.23~2.47 로 일관되게 후보 쪽이 컸고, 후보를 먼저 잰
역순 회차(진단)에서도 그랬다 — 이는 편향 ①(순서 고정)의 설명력을 약하게 하고 ②(후보만 1,500행 시드 직후)·③ 쪽을 가리킨다.
v2 에서 방향이 바뀐 것은 시드 순서·`vacuum analyze` 통일(②)과 교대 때문일 가능성이 크지만, 이 8GB 기계의 잡음(메모리 바닥·페이징)
안에서는 수 십 % 수준의 실제 회귀를 배제하지 못한다. 판정은 스펙의 식대로 통과로 두고, **SP5 이후 성능 재측정 때 같은 방법(v2)으로
`sp4-a2-done` 대비 다시 본다**(그때 기준선이 될 이 문서의 한계로 남긴다).

## 이번 방법(교대 측정 v2)

- 스택이 하나라 두 편의 스키마를 동시에 둘 수 없다 — 편마다 `db:reset`(자기 트리)·`dev:bootstrap`·시드를 다시 하고 서버를 새로 띄운다.
  빌드는 편마다 한 번(측정 앞). 기준선은 `sp3a-done` 의 스크래치 워크트리(`git worktree add --detach`, 끝나고 제거)에서
  `supabase/config.toml` 을 전용 스택 사본으로 덮고(`project_id = "d-flow-sp4"` 확인) 러너 DSN 한 줄만 `LOCAL_DB_URL` 로 바꿔(적용을 grep 으로 확인) 시드했다.
- **순서 교대(ABBA × 2)**: 라운드 1·3 은 기준선 → 후보, 2·4 는 후보 → 기준선.
- **판정 측정 앞의 시드를 같게**: 기준선은 800행, 후보는 800행 + 주간(영역 셋·문서 하나). 1,500행 `PERF-1500` 시드는 후보 800행 측정 **뒤**에 넣고 1,500행을 쟀다.
- **양쪽 모두 시드 뒤 `vacuum analyze`**(전용 컨테이너).
- **표본 n 100**(러너 기본값), 경로별 워밍업 3, `next start -H 127.0.0.1`(기준선 3102, 후보 3101). 측정 러너는 두 편 모두 후보 HEAD 의 `scripts/perf-baseline.mjs measure --personas admin`.
- **reset 뒤 검증**: 마이그레이션 최대 번호(기준선 0012 / 후보 0017)와 좌표 — 컨테이너 안 psql 과 `LOCAL_DB_URL` 접속이 같은 클러스터(`system_identifier`)이고 호스트 포트가 54522 인지. 8편 모두 ✓.
- **부하 관리**: 무거운 실행 잠금(`heavy-lock.sh`) 안에서만 측정. 빌드 뒤 1분 load ≤ 6 까지 기다렸고(90초), 라운드마다 앞에서 다시 기다렸다(0~60초).
- 비밀번호는 편마다 `openssl rand` → env → 편 끝에 unset. 측정 뒤 스택은 0017 + bootstrap 으로 되돌렸다(기록용 시드는 남지 않는다 — 과제 24 의 공통 묶음과 같은 출발점).
