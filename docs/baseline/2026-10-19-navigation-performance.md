# 페이지 전환·공통 조회 최적화 (2026-10-19)

페이지를 이동할 때 알림 패널이 매번 로딩 상태로 돌아가고, 알림 목록·로딩 상태의 변경이 내비게이션 전체로 전파됐다.
`/api/shell`은 React 렌더 밖에서도 `React.cache`가 조회를 합칠 것으로 기대해 같은 권한·프로젝트 설정을 반복 조회했다.
설정 해석기의 기본 클라이언트와 명시적 클라이언트도 서로 다른 캐시 키로 처리됐다.

## 변경

- 알림 목록과 내비게이션 배지의 컨텍스트를 분리하고 같은 배지는 기존 객체를 유지한다.
- 같은 범위의 재조회 중에는 기존 인박스를 유지한다. 경로 변경·언마운트 때 이전 요청을 취소하고 늦은 응답을 버린다.
- 알림 broadcast를 150ms 동안 합치고 구독 콜백을 고정해 범위 이동으로 인한 재구독을 줄인다.
- 메뉴가 보인다는 이유만으로 동적 경로 전체를 조회하지 않는다. 120ms 이상 가리킨 메뉴와 키보드로 선택한 메뉴만 본문까지 미리 읽는다.
- RSC 미리 읽기는 화면 갱신 보정 타이머를 만들지 않는다. 실제 이동·저장 응답의 보정 타이머는 최대 세 개로 합친다.
- 읽기 전용 `/api/shell` GET 안에서 `AsyncLocalStorage`로 인증·권한·설정의 진행 중 조회를 공유한다. RSC는 기존 React 요청 캐시를 사용한다.
- 세션 DB 클라이언트를 요청 안에서 공유하고, 설정 조회의 기본·명시적 동일 클라이언트를 같은 키로 처리한다.

캐시는 요청 밖으로 유지하지 않는다. 사용자·프로젝트·명시적으로 주입한 다른 DB 클라이언트·보관 포함 옵션은 분리한다.
다른 요청은 인증과 권한을 새로 확인한다. 설정 실패·비공개 프로젝트 은닉·모듈 관문은 기존 판정자를 사용한다.
스키마·인덱스 변경은 없다.

## 로컬 실측

동일 로컬 Supabase(사용자 2명·워크스페이스 1개·프로젝트 6개), 동일 프로젝트의 플랫폼 관리자 세션으로 기존 빌드와 변경 빌드를 비교했다.
Node의 `fetch`를 계측해 로컬 Supabase로 나가는 요청의 경로·메서드만 세었다. 워밍업 한 번 후 `/api/shell?ws=…&project=…`를 다섯 번 순차 요청했다.

| 항목 | 기존 | 변경 |
|---|---:|---:|
| PostgREST 요청 / 공통 알림 조회 | 56 | 23 |
| 인증 포함 백엔드 요청 | 59 | 24 |
| 권한 축별 조회 | 4회 | 1회 |
| 프로젝트 영역·팀·휴일 조회 | 각각 5회 | 각각 1회 |
| 인증 사용자 조회 | 3회 | 1회 |
| 응답 시간 중앙값 | 69ms | 37ms |
| 응답 시간 표본 | 76·69·66·70·64ms | 43·41·37·37·36ms |

Chrome에서 개요 → WBS → 주간보고 → 이슈 → 개요를 이동했다(메뉴 hover 500ms 후 클릭).
네 번의 이동 중 `role=status` DOM 삽입은 5회 → 2회였다. 이 수는 로딩 외의 상태 요소도 포함하므로 화면 전체의 깜빡임 횟수로 해석하지 않는다.
두 빌드 모두 공통 `main`·사이드바의 제거·재삽입은 없었고 브라우저 오류는 0건이었다.
1440×900·390×844 캡처를 확인했다. 로컬 소규모 데이터 실측이며 운영 지연·다른 페이지의 수치로 일반화하지 않는다.

## 검증

- 전체 Vitest: 1,159개 파일·15,741개 테스트 통과.
- 타입 검사·프로덕션 빌드 통과. 린트 오류 없음(기존 경고 5개).
- 회귀 검사: 동시 요청 중복 제거, 요청 간 사용자 격리, 클라이언트별 격리, 조회 거절 유지, 설정 조회 횟수,
  배지 소비자 렌더 횟수, 이전 요청 취소, 실시간 이벤트 병합, 의도 기반 미리 읽기, RSC 갱신 보정.
