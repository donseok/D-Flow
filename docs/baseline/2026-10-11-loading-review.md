## 확인된 원인과 한계

- 개발 로그에서 이슈 화면 컴파일 44.4초, 주간보고 13.5초가 확인됐다. 이슈 최초 요청은 약 49초였고 같은 시각 다른 페이지 요청도 약 47.5초 대기했다. 한 화면의 컴파일이 다른 요청 체감에도 영향을 주었다.
- 여러 화면을 순회한 뒤 `Server is approaching the used memory threshold, restarting...` 로그와 실제 자동 재시작을 확인했다. 재시작 구간에서 위키 반복 요청 및 이후 일부 요청이 연결 실패했다. 실패를 빠른 응답으로 계산하지 않았다. 서버는 자동 복구했으며 3000 health 200을 확인했다.
- 배포용 비교 서버의 주요 화면 12개 반복 중앙값은 33~68ms, 셸 통합 조회는 약 70ms였다. 권한·데이터 조회를 생략하지 않은 결과다.
- 단순 PostgREST id 조회 10회씩의 중앙값은 개발 측정 시 프로젝트 약 4ms/WBS 약 2ms, 배포 측정 시 약 1ms였다. 이는 서비스 역할의 작은 조회 연결 기준값이며 실제 RLS·복잡한 집계·대량 데이터 성능을 보장하지 않는다.
- 임베디드 Chromium 홈 첫 진입에서 TTFB 약 65ms, FCP 244ms, load 281ms였다. 이후 캐시된 홈/WBS/설정의 load는 100/154/140ms였다. 백그라운드 탭의 후속 FCP/LCP가 제공되지 않아 전체 페이지 Web Vitals 검증으로 취급하지 않았다.
- 캐시된 탐색에서도 홈/WBS/설정의 JS 디코딩 총량은 약 1.23/1.55/1.43MB, 요청 수 37/44/40개였다. 현재 로컬 로딩 병목으로 확인되지는 않았지만 저성능 기기 및 느린 네트워크에서 후속 점검할 항목이다. CDN 폰트는 현재 캐시 상태였으므로 신규 방문자의 외부 폰트 지연은 검증하지 않았다.

## 권장 후속 작업

1. UI 확인과 실제 사용 속도 평가는 최신 코드를 새로 빌드한 production 서버에서 진행한다. 개발 서버의 최초 컴파일 시간을 운영 성능으로 해석하지 않는다.
2. 개발 서버 메모리와 컴파일 시간을 별도 개선 대상으로 삼는다. 비교 실험은 번들러/옵션 변경 전후에 같은 조건으로 측정하고 최신 Gemini 변경이 포함된 빌드도 확인한다.
3. 운영 환경에서는 실제 사용자 권한, 대량 WBS·이슈 데이터, 느린 네트워크/기기에서 페이지 이동·상호작용·LCP를 측정한다. 현재 결과만으로 운영 속도가 항상 빠르다고 단정하지 않는다.

원시 측정 파일은 `/tmp/dflow-speed-review-20261011/{development,production,browser}.json`에 있다. 인증 쿠키 및 API 키는 결과 파일에 저장하지 않았다. 임시 비교 서버는 측정 후 종료했고 기존 개발 서버는 유지했다.
