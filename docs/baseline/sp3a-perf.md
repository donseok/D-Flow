## 비고 — 이 표에 잡히지 않는 관문 비용

1. **이 측정은 SSR 페이지 GET 만이다.** 라우트 핸들러·서버 액션·워커는 React `cache` 밖이라 관문 1회 = 설정
   2조회(프로젝트 1 → 워크스페이스 1, `project_settings` 의 `workspaceId` 때문에 직렬 — 판정 P27)다.
   `aiAvailable({ projectId }, { module })` 1회 = 설정 3조회(프로젝트 1 + 워크스페이스 2: `ai.enabled` 직접
   판독과 `effectiveModules` 안). `/api/shell` 은 화면 전환마다 관문 셋(공지 두 액션·결재 배지)을 지나고,
   챗 위젯 탐침(과제 24)은 이동마다 프로젝트 목록 1 + 설정 2조회를 더한다. **이 표에 잡히지 않는다.**
2. **색인 워커 스코프**(판정 P29)는 워커 1회마다 워크스페이스 수 + 켜진 워크스페이스의 프로젝트 수
   (최대 100/워크스페이스)만큼 설정을 읽는다.
3. **측정 스택** — 사용자 dev 서버(3000)를 건드리지 않으려고 전용 로컬 스택 하나를 더 띄웠다
   (`project_id = "d-flow-sp3a-e2e"`, api 54421 · db 54422, `supabase/config.toml` 을 워크트리에서만 바꿔
   띄운 것 — 커밋되지 않았다). 두 워크트리의 `scripts/lib/targets.mjs` 의 `LOCAL_DSN` 도 54422 로 바꿔
   시드가 같은 DB 를 보게 했다(SP3b 스펙 D32 가 경고한 "수정 전 러너로 재면 두 DB 가 섞인다" 함정).
   **이 변경은 측정 하네스에만 있고 앱 코드에는 없다** — 측정 대상인 `next start` 프로세스는 이 변경과 무관하다.
4. **산출물** — 여섯 번의 측정 JSON은 리포 밖(`/Users/jerry/D-Flow-wt/perf-{base,cand}-run{1,2,3}.json`)에 있다.
   커밋하지 않았다(비밀번호가 실린 시드 스크립트와 같은 부류).
