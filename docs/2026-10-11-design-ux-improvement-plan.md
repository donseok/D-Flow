# D-Flow 전체 디자인·사용성 개선 수행계획서

작성일: 2026-10-11 · 분석 기준 커밋: `88026acf`

추가 요구 반영: 세련되고 획일적인 AI 제작물처럼 느껴지지 않는 디자인, 변경 결과가 마음에 들지 않을 때 원래 디자인으로 복구할 수 있는 원복 계획.

## 1. 목적과 분석 범위

목표는 사용자가 프로젝트 상태를 빠르게 파악하고, 필요한 업무를 쉽게 찾고, 입력·저장·조회 과정에서 실수를 줄이도록 전체 UI를 정리하는 것이다. 현재 색상과 브랜드 방향을 기반으로 글자, 정보 배치, 조작 방식, 화면 크기 대응의 일관성을 높인다.

이번 작업에서는 프로그램 소스·설정·DB를 변경하지 않았다. 이 수행계획서만 추가했다. 시작 시 이미 존재하던 `supabase/config.toml` 변경은 기존 작업으로 보존했다.

분석 대상은 공통 셸·내비게이션·검색·알림·AI 패널, 인증·초대, 홈·내 업무·프로젝트 목록·포트폴리오, 프로젝트 개요, 작업 계획의 표·간트·보드, 이슈, 주간업무, 회의·회의록·공유 뷰어, 위키, 공지, 근태, 멤버·팀, 에이전트, 프로젝트·워크스페이스 설정, 계정·관리자·사용 현황, 가져오기·보고서 진입 및 공통 상태 UI다. 별도 간트·칸반 메뉴를 신설하는 계획이 아니라 현재 작업 계획 안의 보기 전환을 기준으로 한다.

확인 방법과 한계:

- 현재 라우트, 주요 화면 컴포넌트, 전역 CSS·디자인 토큰, 공용 UI, 관련 기존 검증 문서를 읽었다. `src`의 TSX 370개에 대해서는 글자 크기·고정 폭 사용 현황을 정적으로 집계했다. 370개 모두의 상호작용을 실행 검증했다는 뜻은 아니다.
- 실행 중인 `http://localhost:3000`에서 로그인 화면을 직접 열어 이미지·접근성 구조·계산된 스타일을 확인했다. 관찰 뷰포트는 1189×725 CSS px다.
- 로그인 세션이 없어 내부 화면의 현재 렌더링·실제 데이터·모바일 동작은 직접 확인하지 못했다. 내부 화면의 사실은 **소스 확인**, 실행 시 결과가 필요한 사항은 **검증 필요**로 구분했다.
- 관련 기존 검사 4파일·135개가 통과했다. 검사 대상은 `contrast-tokens`, `min-font-size`, `breakpoint-safety-net`, `touch-target`다. 전체 제품의 접근성 인증이나 전체 기능 회귀 결과로 해석하지 않는다.
- 이전 QA 문서의 다크 테마·영어 관련 내용은 과거 기록이다. `CLAUDE.md`의 2026-10-10 결정에 따라 이번 계획은 **한국어 전용·라이트 테마 전용**이다.

## 2. 전체 평가와 개선 방향

기본 디자인 체계는 잘 구축되어 있다. 밝은 회색 바탕과 흰 카드, 진한 글자, 선명한 파랑 동작 색은 장시간 사용하는 업무 도구에 적합하다. 색상·크기·반경·모션·층 순서가 토큰으로 정의되어 있고, 검색 단축키, 보기 전환, 저장 상태, 충돌 해결, 문서 글자 조절 같은 편의 기능도 갖추고 있다.

가장 큰 개선 여지는 기능이 많은 화면에서의 정보 밀도와 화면별 일관성이다. 데이터 시트, 문서 뷰어, 일반 목록, 에이전트 화면이 서로 다른 크기·색상·레이아웃 관례를 사용한다. 특히 모바일은 공통 셸이 반응형이어도 업무 본문이 넓은 표로 남는 경우가 많다. 디자인 개선의 우선순위는 브랜드를 새로 만드는 것보다 **읽기 편의성 → 작은 화면에서 핵심 업무 수행 → 동작과 상태의 일관성 → 시각적 완성도**다.

현재 사용자가 결정한 배치는 존중한다. 예를 들어 개요 화면의 조치 큐가 하단에 있는 것은 소스에 사용자 요청으로 기록되어 있다. 개선 시 이를 임의로 상단으로 이동하지 않고, 요약에서 해당 위치로 빠르게 이동하는 방식부터 검토한다.

### 2.1 세련된 디자인과 제품 고유의 인상

사용자가 요구한 디자인 목표는 **실무에 맞게 정돈되어 있고, 사람이 세심하게 구성한 제품처럼 느껴지는 화면**이다. “AI가 제작한 느낌”은 객관적인 단일 지표로 판정할 수 없으므로, 아래 구성 원칙과 실제 화면 비교에 대한 사용자의 평가로 확인한다. 제작 도구보다 화면의 구체적인 완성도를 평가한다.

| 기준 | 적용 방향 | 검토할 화면 요소 |
|---|---|---|
| 제품 고유성 | D-Flow의 프로젝트·일정·협업 맥락과 기존 브랜드를 반영 | 작업명·날짜·담당·기한·승인 상태가 화면의 중심인지 |
| 절제된 시각 표현 | 기본 중립색과 파랑을 중심으로 강조할 곳에만 색을 사용 | 의미 없는 그라데이션·빛 번짐·유리 효과·장식 배지의 반복 여부 |
| 의도 있는 배치 | 정보의 중요도와 사용 빈도에 따라 크기·위치·묶음을 다르게 구성 | 모든 정보를 같은 크기 카드로 나열하거나 빈 공간을 카드로 채우는지 |
| 정교한 타이포 | 제목·본문·숫자·메타의 역할을 분명히 하고 정렬·행간을 맞춤 | 글자 굵기의 남용, 숫자·단위의 어색한 정렬, 불규칙한 줄바꿈 |
| 균형 있는 밀도 | 데이터 화면은 비교 효율, 문서 화면은 읽기 흐름에 맞춤 | 지나친 여백·과도한 압축·카드 중첩으로 업무 흐름이 끊기는지 |
| 일관된 세부 마감 | 아이콘 계열·크기·선 굵기, 테두리·반경·그림자·간격을 정리 | 화면마다 다른 아이콘 스타일, 기준선 어긋남, 불필요한 그림자 |
| 자연스러운 문구 | 실제 업무 용어와 짧은 행동 문구를 사용 | 과장된 홍보 문장, 반복적인 AI·스마트·혁신 표현, 불필요한 영어 |
| 필요한 모션 | 상태 변화와 위치를 이해하는 데 필요한 전환만 사용 | 장식적인 등장 효과, 반복 애니메이션, 과도한 시선 유도 |

특정 유행이나 다른 서비스의 템플릿을 그대로 적용하지 않는다. 그라데이션·카드·일러스트 자체를 금지하는 것은 아니지만, 실제 정보 전달이나 브랜드 목적이 설명되지 않으면 추가하지 않는다. 모든 화면을 동일한 모양으로 만들기보다 공통 디자인 문법 안에서 업무 유형에 맞는 차이를 둔다.

수행 방법:

- 개요·작업 계획·이슈·주간업무·회의록·설정에 실제 한국어 업무 데이터를 넣은 대표 시안을 만든다. 빈 화면과 영문 더미 문구만으로 완성도를 판단하지 않는다.
- 기존 화면과 개선 시안을 같은 데이터·크기·상태로 비교한다. 필요한 경우 두 가지 방향을 먼저 비교하고 선택한 방향을 나머지 화면에 적용한다.
- 시안에서는 큰 구조뿐 아니라 긴 제목, 숫자·단위, 아이콘 정렬, 선택·오류·비활성 상태까지 확인한다.
- 기능 검사와 별도로 시각 검토를 실시한다. 정보의 우선순위, 색의 절제, 배치의 자연스러움, 세부 정렬, 제품 고유성을 기록한다.
- 사용자에게 마음에 들지 않는 영역이 있으면 해당 화면·공통 스타일 묶음을 재작업하거나 부분 원복할 수 있게 한다. 전체 디자인의 기술 검사 통과를 사용자 만족으로 대신하지 않는다.

## 3. 공통 디자인 분석과 목표

### 3.1 색감·대비·상태 표시

현재 주요 색:

| 용도 | 현재 색 | 판단·개선 방향 |
|---|---|---|
| 화면 바탕 | `#F4F6FA` | 흰 카드와 구분이 적절하다. 유지 |
| 카드·입력 표면 | `#FFFFFF` | 읽기 중심의 표면으로 적합. 유지 |
| 주 글자 | `#101828` | 충분히 진하다. 유지 |
| 보조 글자 | `#475467` | 설명·라벨에 적합. 유지 |
| 약한 글자 | `#5D6B82` | 흰 바탕 대비 약 5.40:1. opacity를 추가한 조합은 따로 확인 |
| 주 동작 | `#2456E6` | 흰 글자와 약 5.92:1. 주 버튼·링크에 사용 |
| 입력 경계 | `#7F8CA0` | 바탕 대비 약 3.15:1. 장식 경계와 역할을 구분 |
| 성공·주의·위험 | 녹색·갈색 계열 주황·빨강 | 색에 상태 이름·아이콘을 함께 제공 |
| 팀·업무영역 | 8개 범주 색 | 상태 색과 혼동하지 않도록 사용 위치·범례 정리 |

수치는 현재 CSS 값을 이용한 계산이다. 일반 글자는 4.5:1, 큰 글자는 조건에 따라 3:1을 기준으로 검증한다. 작은 KPI 숫자는 큰 글자 예외를 일괄 적용하지 않는다. [W3C 글자 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**확인된 별도 문제:** `AgentHero`의 타일은 `surface-subtle` 위에 `HeroTile.color/valueColor`를 글자색으로 사용한다. 좌석도에서 전달하는 활성 `#5DB1E5`, 오프라인 `#B7BFBA`, 대기 감시 `#7FD29A`의 계산 대비는 각각 약 2.10:1, 1.67:1, 1.61:1이다. 큰 글자 기준에도 부족하다. 좌석도 자체의 `#7E8B93` 글자와 흰 표면은 약 3.50:1로 작은 보조 글자에 부족하다. 실제 요소의 렌더링은 내부 로그인 후 재확인해야 하지만, 지정된 색 조합 자체는 개선 대상이다.

수행 항목:

- 에이전트의 상태 막대·점은 기존 색을 살릴 수 있으나 숫자·설명은 대비를 확보한 전경색으로 분리한다.
- 모듈 CSS·인라인 색·opacity·사용자 지정 accent·팀 색까지 실제 전경/배경 조합을 검사한다.
- 파랑은 주요 동작·선택, 상태 색은 업무 상태, 범주 색은 팀·영역 식별에 사용하도록 의미를 문서화한다.
- 이미 좋은 전역 팔레트를 유지하며 배지·범례가 지나치게 많은 화면만 정리한다.

근거: `src/app/globals.css`, `src/components/agent-hub/AgentFrame.tsx`, `src/components/agents/SeatmapView.tsx`, `src/components/agents/seatmap.module.css`.

### 3.2 글꼴·글자 크기·행간

Pretendard Variable을 기본으로 사용하며 한국어 업무 UI에 적합하다. 로그인에서 로딩을 확인했다. CDN을 통한 로딩과 대체 글꼴이 마련되어 있으나, 느린 네트워크·폰트 로딩 실패에서 줄바꿈과 표 폭 변화를 추가 검증해야 한다.

| 요소 | 현재 기본 | 개선 기준안 |
|---|---:|---|
| 페이지 제목 | 24px, 컴팩트 22px | 유지. 화면별 개별 제목 크기를 정리 |
| 섹션 제목 | 16px | 유지. 14px 제목과 역할을 구분 |
| 일반 본문·컨트롤 | 14px | 본문 14~16px, 중요한 필터·라벨 14px 중심 |
| 메타·배지 | 12px | 날짜·부가정보에 한정. 핵심 업무 내용에 사용 최소화 |
| KPI | 30px | 숫자와 기준일·단위·변화량의 위계 통일 |
| 문서 본문 토큰 | 16px | 장문 읽기 화면의 기준으로 검토 |
| 회의록 본문 | 기본 14px, 12~28px 조절 | 16px 초기값 시안 비교. 기존 사용자 선택 보존 |
| WBS 본문 | 기본 12px, 100·115·130% 조절 | 기존 조절 유지. 14px 기준의 편안한 밀도 보기 검토 |

정적 집계에서 `text-xs` 919회, `text-meta` 482회, `text-[13px]` 76회가 확인됐다. 선언 횟수이므로 화면에 표시되는 글자 비율을 의미하지 않는다. `text-xs`와 `text-meta`는 기본 12px로 크기는 같지만 의미 기반 사용이 섞여 있다. 전부 기계적으로 확대하면 고정 폭 표와 달력이 깨질 수 있어 화면 역할에 따라 정리해야 한다.

간트 날짜·축 눈금·링 내부 숫자에는 9~10px 예외가 남아 있다. 일부는 기존 테스트의 허용 목록에 등록되어 있다. 허용 목록 통과는 읽기 편의성 보증이 아니며, SVG 글자는 실제 렌더링 크기도 측정해야 한다.

수행 항목:

- 핵심 제목·업무명·필터·오류 사유·저장 결과에 12px 메타 크기가 쓰였는지 우선 점검한다.
- WBS 배지·헤더는 확대 상한이 적용되므로 글자 확대 시 어느 요소까지 커지는지 안내와 동작을 맞춘다.
- 주간업무·위키·채팅 등 장문 화면에 본문 행간 1.5~1.65 수준을 검토한다.
- 본문 폭, 줄바꿈, 표 내부 여백과 함께 조절한다. 글자 크기만 바꾸는 일괄 작업은 피한다.
- 모바일 폼은 16px 입력 글자를 우선 검토하고 실제 기기에서 입력·확대 동작을 확인한다.

근거: `src/app/globals.css`, `src/app/layout.tsx`, `src/lib/wbsFontScale.ts`, `src/lib/minutes/fontSize.ts`, `tests/css/min-font-size.test.ts`.

### 3.3 화면 틀·여백·정보 위계

공통 셸은 상단 48px, 사이드바 232/64px, 일반 조작 높이 36px, 컨트롤 반경 8px, 패널 반경 12px다. PageFrame은 포털 1440px, 문서 760px, 폼 800px의 폭을 제공한다. 일반 목록에는 44px 행 높이가 정의되어 있다. 기본 체계는 유지하고 적용 범위를 정리한다.

문제·확인 사항:

- PageHeader는 컴팩트 화면에서 설명과 메타를 숨긴다. 기준일·선택 범위 등 꼭 알아야 하는 정보는 도구줄이나 본문에 남아 있는지 검증한다.
- PageHeader의 추가 보조 동작은 `overflow` 슬롯에 놓이지만 자동 메뉴로 변환되지는 않는다. 모바일에서 긴 동작 줄이 넘치지 않도록 호출부를 검사한다.
- 회의록 상세 제목은 18px, 에이전트 Hero 제목은 28px 등 별도 위계가 있다. 문서 제목과 페이지 제목의 의도적인 차이를 규정한다.
- 카드·시트·표의 모서리와 그림자는 이미 구분되어 있다. 불필요한 카드 중첩과 반복 제목만 줄인다.
- 도구줄·저장바·우측 패널·전체 화면의 겹침은 실제 높이와 포커스 위치로 검증한다.

목표 배치는 `페이지 제목/범위 → 주요 동작 → 필터/보기 → 핵심 콘텐츠 → 보조 설명/상태`다. 데이터 입력 화면에서는 도구줄이 본문 높이를 과도하게 차지하지 않도록 자주 쓰는 기능과 추가 기능을 분리한다.

### 3.4 내비게이션·검색·알림·AI

워크스페이스와 프로젝트의 범위가 분리되고 메뉴·권한·기능 설정이 공통 원천을 사용한다. 검색 `⌘K/Ctrl+K`, 즐겨찾기, 최근 프로젝트, 브레드크럼, 모바일 드로어는 유지할 가치가 높다.

수행 항목:

- 긴 워크스페이스·프로젝트 이름에서도 현재 범위와 화면 이름을 알아볼 수 있게 한다.
- 자동 접힘 상태의 1024~1279px 사이드바는 글자가 숨고, 현재 Tooltip은 명시적으로 접은 상태에서만 생성된다. 자동 접힘에서도 아이콘의 뜻을 확인할 수 있는 동일한 힌트를 제공한다.
- 검색 범위·활성 필터·결과 없음·권한 제한·로딩 실패를 구분한다. 키보드 결과 이동과 상세 진입 후 위치 복원을 확인한다.
- 알림 배지·동기화 상태·AI 진입이 좁은 상단 바를 차지하는 정도를 320~390px에서 확인한다.
- 우측 레일은 400px, 본문 최소 720px을 기준으로 병치/오버레이를 선택한다. 이 기준을 유지하고 문서 전용 채팅과 전체 AI의 역할을 명확히 한다.
- 모바일 드로어·모달·레일의 Tab/Esc/초점 복귀는 유지하되, 배경의 클릭·스크린리더 접근 차단까지 확인한다. 초점 트랩만으로 전체 동작을 통과 판정하지 않는다.

근거: `src/components/app/NavList.tsx`, `GlobalBar.tsx`, `RightRail.tsx`, `MobileNavDrawer.tsx`, `src/components/search/GlobalSearchDialog.tsx`.

### 3.5 입력·저장·오류·권한

공통 Button·Field·Modal에 로딩, 비활성 사유, 라벨·설명·오류 연결, 이탈 확인, 초점 복귀가 구현되어 있다. 업무 화면에는 자동 저장, 충돌 해결, 재시도, 부분 성공 상태도 있다. 이를 보존하면서 개별 `.btn`·직접 작성한 폼의 동작 차이를 줄인다.

수행 항목:

- 자동 저장과 명시적 저장의 화면별 규칙을 짧고 일관되게 표시한다.
- 저장 중·저장됨·실패·충돌·부분 성공을 색과 텍스트로 구분하고 입력값을 보존한다.
- 조회 전용, 권한 없음, 기능 꺼짐, 초기 설정 필요를 서로 다른 안내로 표시한다.
- 삭제·교체·복원·가져오기에는 영향 범위와 복구 수단을 해당 동작 근처에서 안내한다.
- 이슈 목록의 클릭 가능한 `tr role="button"`은 Space 동작, 표 의미 구조, 내부 체크박스와의 초점·이벤트 관계를 검증하고 제목 링크/상세 버튼 방식을 검토한다.
- 화면마다 성공 알림 위치·오류 사유·재시도 버튼을 통일한다. 중복 알림과 지속적으로 반복되는 상태 알림을 줄인다.

### 3.6 터치·반응형·확대·모션

로그인 실측에서 입력과 로그인 버튼은 44px 높이, 비밀번호 표시 버튼은 16×16px다. 작은 아이콘 버튼은 클릭 영역을 확대하는 우선 과제다. 공통 IconButton과 일부 닫기 버튼은 44px 투명 영역을 사용하지만, 일반 Button·메뉴 항목·개별 버튼에 자동 적용되지는 않는다. 투명 영역은 이웃과 겹치거나 조상 overflow에 잘릴 수 있으므로 실제 클릭 검증이 필요하다.

제품 목표는 모바일 주요 조작 영역 44×44 CSS px다. WCAG 2.2 AA의 최소 목표 크기는 24×24px이며 간격 등 예외가 있다. 따라서 36px 버튼을 일괄 위반으로 판정하지 않는다. [W3C 목표 크기 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

넓은 데이터 표·간트는 본질적으로 2차원 배치를 요구할 수 있다. 이런 영역의 가로 스크롤을 무조건 없애기보다, 핵심 열 고정·스크롤 안내·간편 조회·상세 편집을 제공한다. 일반 폼·설명·버튼 줄은 좁은 화면에서 재배치한다. [W3C 리플로우 기준과 2차원 콘텐츠 예외](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

전역 reduced-motion 대응과 짧은 높이에서 시트를 보존하는 규칙은 이미 있다. 에이전트 스프라이트의 JS 기반 애니메이션까지 멈추는지는 별도 확인한다. 반응형 display 안전망은 CSS cascade에 영향을 주므로 한 번에 제거하지 않고 기존 검사와 실제 화면을 함께 확인한다.

| 사용 현황 | 요약·추이·순위·사용자·이벤트 | 기간/범위 필터와 지표 정의를 가까이 배치. 차트 숫자 대안, 긴 메뉴명, 범례·날짜 눈금의 읽기 편의성 | P2 |
| 가져오기 | 선택→검토→완료 3단계, 미리보기·결과·복구 정보 | 좁은 단계 표시와 720px 미리보기 개선. 덮어쓰기·합치기의 영향 비교. 오류 행·수정 방법·취소/재시작 동선 명확화 | P1 |
| 보고서·내보내기 | 화면에서 옵션 선택 후 출력 | 현재 화면 필터와 출력 범위의 관계 표시. 생성 중·실패·재시도 일관성. 실제 PPTX/XLSX 출력의 잘림·폰트·날짜/단위는 별도 검증 | P2 |
| 빈 상태·로딩·실패·충돌·기능 꺼짐 | 공용 상태 컴포넌트와 관련 스켈레톤 | 설명·다음 행동·원인 범주 통일. 빈 결과를 조회 실패로 오해하지 않게 구분. 좁은 화면·스크린리더에서 중복 상태 안내 확인 | P1 |

P1은 핵심 업무 수행·읽기·조작에 직접 영향을 주는 우선 과제, P2는 탐색 효율·일관성·완성도를 높이는 과제다. 실제 재현에서 업무 중단·데이터 손실 위험이 확인되면 해당 항목을 P0로 승격한다.

권장 첫 적용 묶음은 로그인 작은 버튼 → 에이전트 글자 대비 → 자동 접힘 메뉴 힌트 → 제목/도구줄/저장 상태 정리다. 이어 이슈와 주간업무의 좁은 화면 대안을 적용한다. 이 순서는 효과와 전역 영향 범위를 함께 고려한 제안이며, 내부 화면 실측 결과에 따라 조정한다.

모바일 카드·간편 편집·편안한 밀도 보기는 기능 범위를 늘릴 수 있으므로 대표 화면 시안과 실제 작업 동선으로 선택한다. 현재 상태에서 모두 구현하기로 확정하지 않는다.

자동 검사는 기존 CSS·토큰·키보드·모달·상태 회귀를 활용한다. 구현 시 변경에 맞는 기능 테스트, 타입·린트·빌드 검사를 수행하고 실제 브라우저 캡처를 함께 비교한다. axe 자동 판정 불가 항목은 수동 확인 대상으로 남긴다. 단위 테스트만으로 잘림이나 겹침을 통과 판정하지 않는다.

## 7. 작업 시 사용할 스킬·에이전트

현재 사용한 스킬은 `orca-cli`이며, Orca의 내장 브라우저로 로그인 화면을 확인했다. 이번 분석에는 보조 에이전트를 호출하지 않았다.

| 스킬·도구 | 실제 개선 작업에서의 역할 | 사용 조건 |
|---|---|---|
| `orca-cli` | Orca 작업 브랜치/워크트리와 내장 브라우저의 화면 이동·캡처·상태 확인 | 이 프로젝트 작업과 브라우저 검증에 우선 사용 |
| `visualize:visualize` | 대표 화면의 정보 배치·도구줄·모바일 대안을 비교하는 인터랙티브 시안 | 구현 전 레이아웃 선택이 필요한 경우 |
| `orchestration` | 공통 UI·업무 화면·문서 화면·독립 QA 작업의 의존성·결과 관리 | 후속 작업에서 병렬 에이전트 사용을 명시적으로 요청하는 경우 |
| `computer-use` | 외부 브라우저 실제 확대, 창 조절, OS 대화상자·실기기 관련 GUI 검증 | CLI나 페이지 자동화만으로 확인할 수 없는 GUI 작업 |
| `presentations:Presentations`, `spreadsheets:Spreadsheets` | 실제 PPTX/XLSX 보고서의 시각·구조 검증 | 출력물 디자인까지 개선 범위를 확장하는 경우 |
| `imagegen` | 새 일러스트·마스코트·비트맵이 필요한 경우 | 이번 공통 UI 개선의 필수 스킬은 아님. 기존 SVG 로고·아이콘 정리는 코드/벡터로 처리 |

추가 스킬은 실제 사용할 때 해당 `SKILL.md`를 읽어 지침을 적용한다. 위 목록은 사용 계획이며 이미 호출했다는 뜻이 아니다. 별도의 전용 UI/UX 디자인 스킬이 설치되어 있다고 가정하지 않는다. 코드 변경은 기본 코딩 도구로 진행한다.

병렬 작업을 선택한다면 아래 역할을 맡긴다. 현재 생성된 에이전트나 특정 제품 기능명이 아니라 **후속 작업의 역할 분담안**이다.

| 역할 | 소유 범위 | 결과물 |
|---|---|---|
| 주 에이전트 | 요구사항·사용자 결정·디자인 기준·통합 | 공통 기준, 수행 순서, 통합 결과 |
| 공통 UI 담당 | tokens·셸·내비·버튼·필드·모달·상태 | 공용 변경과 전 화면 영향표 |
| 업무 화면 담당 | WBS·이슈·주간업무·회의·설정 | 핵심 업무 흐름과 좁은 화면 개선 |
| 문서/검증 담당 | 회의록·위키·읽기 화면 또는 독립 QA | 문서 가독성 개선 또는 재현·접근성 검증 |

동시 작업을 한다면 공통 CSS·레이아웃은 한 담당자만 수정한다. 공통 기준이 확정된 후 화면별 작업을 나누고, 최종 QA에서는 작성자와 다른 역할이 결과를 검토한다. 범위가 작으면 단일 에이전트가 순차 수행하는 편이 적합하다.

## 8. 구현 운영 기준과 예상 규모

현재 요청은 계획서 작성까지다. 후속 구현은 별도 작업 범위로 진행한다.

공통 CSS·레이아웃·앱 셸은 `CLAUDE.md`에 지정된 UI 위험 파일이므로 후속 구현에서 UI 브랜치를 사용한다. 로컬 Preview와 영향 화면을 직접 확인한다. 현재 원격 Preview가 없다는 로컬 규칙을 적용한다. 변경은 단계별로 분리하여 화면별 비교와 되돌리기가 가능하게 한다. DB·권한·설정 상속·동시 편집 규칙을 건드리는 개선은 별도 기능 과제로 분리한다.

계획상 작업 규모 추정은 다음과 같다. 로그인 후 재현과 모바일 대안 선택 전의 추정이며 일정 약속이 아니다.

| 범위 | 예상 작업일 |
|---|---:|
| 기준선 촬영·문제 확정·시안 | 2~3일 |
| 공통 UI·색·타이포·셸 개선 | 2~4일 |
| 핵심 업무 화면 | 4~7일 |
| 문서·조회·관리 화면 | 3~5일 |
| 전체 시각·접근성·기능 검증 | 2~4일 |
| 원복 준비·리허설·절차 정리 | 1일 |
| 합계 | 약 14~24 작업일 |

모바일 전용 편집 흐름과 별도 출력물 개편을 모두 포함하면 범위가 커진다. 병렬 작업도 공통 UI 의존성과 최종 검증을 줄이지 못하므로 담당 수로 단순히 나누지 않는다.

## 9. 착수 전 확인할 항목

- 내부 화면 확인용 세션과 대표 테스트 데이터. 제품 DB에 테스트 행을 만드는 작업은 별도 범위로 정한다.
- 모바일에서 반드시 지원할 업무: 조회·승인·간단 수정과 대량 표 편집의 필요도를 구분한다.
- 기본 밀도: 기존 고밀도 표를 기본으로 유지할지, 읽기 편한 보기 선택을 제공할지 대표 시안으로 결정한다.
- 기존 사용자 요청이 기록된 화면 순서·라벨·보고서 관례의 유지 범위를 확인한다.
- 최종 디자인의 첫 확인 대상은 개요·작업 계획·이슈·주간업무·회의록·설정의 데스크톱/모바일 표본으로 한다.

이 항목들은 현재 수행계획서 완성을 막는 요구가 아니라 후속 구현 범위를 확정하기 위한 입력이다.

## 10. 원복 계획

### 10.1 원복의 목표와 기준점

디자인 변경 결과가 마음에 들지 않거나 업무 사용성이 나빠지면, **변경 전 디자인으로 전체 또는 일부를 되돌릴 수 있도록 준비한다.** 원복 시 디자인 작업 이후 사용자가 입력한 업무 데이터와 다른 작업자의 변경을 보존한다.

원복 기준은 이 문서의 분석 커밋을 무조건 사용하는 것이 아니라 **실제 디자인 구현 직전의 상태**로 정한다. 구현 사이에 기능이나 데이터가 바뀔 수 있으므로 기준 커밋·기존 미커밋 변경·자산·관련 UI 설정을 함께 기록한다. 본 문서 작성 단계에서 백업·태그·원복을 실행한 것은 아니다.

착수 시 확보할 자료:

- 기준 커밋과 구현 브랜치, 작업 일시, 기존 변경 파일 목록. 기존 미커밋 변경은 소유 범위를 확인하고 패치 또는 별도 사본으로 보존한다. 다른 작업자의 변경을 디자인 커밋에 섞지 않는다.
- 변경 대상 CSS·레이아웃·컴포넌트·폰트·아이콘·이미지·출력 템플릿의 기준 버전. 기존 자산은 원복 검증 전까지 제거하지 않는다.
- 동일 데이터·뷰포트·역할·상태에서 촬영한 변경 전 캡처와 주요 동작 기록.
- 디자인 작업이 직접 바꾸는 UI 설정만의 원래 값과 적용 범위. 개인 글자 크기·밀도·위젯 배치 등을 수정한다면 해당 항목을 구체적으로 기록한다.
- 실제 배포를 포함할 경우 기준 소스로 다시 빌드·기동하는 절차와 적용 버전. 환경 변수·비밀키는 문서나 공개 산출물에 복사하지 않는다.

### 10.2 변경 묶음과 원복 단위

디자인은 독립적으로 되돌릴 수 있는 묶음으로 나누고, 각 묶음의 변경 파일·커밋·관련 설정·의존 관계·복구 후 확인 화면을 원복 기록표에 남긴다. 미커밋 상태의 변경도 대상 파일과 차이를 기록한다.

| 원복 단위 | 대상 예시 | 원복 방법·확인 범위 |
|---|---|---|
| 화면 일부 | 이슈 도구줄, 회의록 본문 배치, 주간업무 간편 보기 | 해당 디자인 묶음을 되돌리고 관련 데이터 조회·편집·저장과 모바일 배치를 확인 |
| 공통 스타일 | 색상·타이포·버튼·입력·카드·아이콘 규칙 | 해당 공통 변경을 되돌리되 이를 전제로 한 화면 변경과의 호환성 확인. 영향받는 모든 화면군 재확인 |
| 공통 셸 | 상단 바·내비·제목·레일·모달 | 셸 묶음과 필요한 의존 변경을 함께 되돌리고 화면 이동·범위 선택·검색·초점·전체 화면 확인 |
| 전체 디자인 | 이번 디자인 작업의 모든 변경 묶음 | 의존 관계를 확인한 뒤 보통 적용의 역순으로 되돌림. 디자인과 무관한 후속 기능 수정은 보존 |
| 디자인 관련 UI 설정 | 이번 작업이 바꾼 기본 밀도·폰트 크기·배치 등의 값 | 코드 원복만으로 복구되지 않는 값은 해당 키만 복구. 사용자가 이후 바꾼 값은 자동 덮어쓰기하지 않고 충돌을 구분 |

원복 기록표에는 `묶음 이름 / 기준 버전 / 변경 커밋·파일 / 설정 변경 / 의존 묶음 / 복구 방법 / 확인 화면 / 리허설 결과`를 포함한다. 공통 CSS와 화면 변경을 한 큰 커밋으로 묶지 않아 부분 원복 범위를 명확히 한다.

### 10.3 원복 실행 절차

1. 사용자가 전체 원복 또는 특정 화면·스타일의 원복을 요청하면 해당 범위를 확정한다. 잘림·접근 불가·핵심 편집 실패 등 사용성 문제가 발견되어도 영향 범위에 맞는 원복을 검토한다.
2. 현재 브랜치와 기존 변경을 확인하고, 원복 전 상태도 복구할 수 있게 보존한다. 미저장 입력·처리 중 저장이 있는 상태에서 서비스를 중단하지 않는다.
3. 원복 기록표에 따라 해당 디자인 커밋을 `git revert`하거나, 미커밋 디자인 변경의 대상 파일만 복구한다. 기능 수정과 섞인 파일은 디자인에 해당하는 차이만 되돌린다. 저장소 전체 `reset --hard`·일괄 파일 복구·강제 push로 다른 작업을 삭제하지 않는다.
4. 공통 토큰·컴포넌트에 의존하는 화면을 함께 확인하고 필요하면 해당 의존 묶음도 원복한다. 변경 후 새로 저장된 사용자 선호는 기준값과 현재값을 비교하여 처리한다.
5. 관련 타입·린트·빌드·기능 검사를 수행한 후 같은 데이터·조건의 기준 캡처와 비교한다. 디자인 작업 이후 데이터가 바뀌었다면 데이터 차이와 스타일 차이를 구분한다.
6. 원복한 소스로 서비스 또는 Preview를 다시 기동하고 새로고침·직접 URL 진입을 확인한다. 배포가 있다면 실제 제공 버전과 자산 캐시 갱신도 확인한다.
7. 원복 범위·복구 버전·검증 결과·보존한 기능/데이터·남은 차이를 기록한다. 원복 완료 여부는 단순히 코드가 되돌아간 사실만으로 판단하지 않는다.

디자인 원복을 이유로 프로젝트·계정·업무 데이터 전체 DB를 초기화하거나 과거 DB 백업으로 덮어쓰지 않는다. 디자인 작업은 원칙적으로 DB 스키마 변경을 포함하지 않으며, 불가피한 기능·스키마 변경은 별도 계획과 복구 절차로 분리한다.

### 10.4 원복 리허설과 완료 조건

최종 적용 전에 구현 브랜치의 검증 환경에서 **대표 화면 부분 원복 1회와 전체 디자인 원복 1회**를 수행한다. 공통 스타일이 바뀌었다면 해당 스타일 원복의 영향도 포함한다. 원복 후 개선 버전을 다시 적용할 수 있는지도 확인한다.

완료 조건:

- 기준 화면의 색상·글꼴·크기·배치·자산이 복구되고, 차이가 있다면 원인이 기록되어 있다.
- 로그인·프로젝트 이동·조회·편집·저장·검색·모달·보고서 진입의 관련 핵심 동작이 정상이다.
- 업무 데이터와 디자인 범위 밖의 기존·후속 변경이 보존되어 있다.
- UI 설정을 바꾼 경우 해당 항목의 복구 결과와 충돌 여부가 기록되어 있다.
- 원복 절차와 실제 소요 시간이 기록되어 있어 다음 요청 때 재현 가능하다. 실제 환경에서 측정하기 전에는 특정 복구 시간을 보장하지 않는다.
- 기술 복구 확인과 함께 사용자가 요청한 화면의 디자인이 원래 상태로 돌아왔는지 확인한다.
