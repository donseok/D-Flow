# D-Flow 범용성 검토 및 Claude Code 구현 지시서

작성·통합일: 2026-09-26.

**이 파일이 이번 검토와 구현 인계의 단일 정본이다.** 최초 적대적 검증, 설정 제어 범위 재검토, 원본 특화 검토, Claude Code 구현 지시, 포털·메뉴·화면 디자인 설계를 모두 포함한다. 이후 발견 사항과 구현 지시도 이 파일에 갱신한다. 별도의 검토 보고서나 인계서 사본을 만들지 않는다.

현재 판정: 코드와 설계 모두 ‘고객별 업무 정책 대부분을 설정만으로 제어’한다는 목표에 미달한다. 아래 내용은 검토 결과와 수정 지시이며, 제품 코드 수정이 완료됐다는 의미가 아니다. 각 검증의 실행 범위와 미검증 항목은 해당 부에 기록했다.

읽는 순서:

1. **제1부 — 적대적 검증:** 최초 9개 발견 사항과 반례.
2. **제2부 — 설정 제어 범위 재검토:** 기능군별 지원 범위, 추가 발견 COV-01~09, 추가 구현 묶음 I~M.
3. **제3부 — Claude Code 구현 지시:** 수정 파일·설계 계약·구현 묶음 A~H·데이터 이행·테스트·완료 조건. 제2부의 I~M도 함께 수행 범위에 포함한다.
4. **제4부 — 원본 고객·원본 프로젝트 특화 잔존 재검토:** 직접 브랜드 검색, 실행 중인 업무 가정, 배포 스킬·PPT 자산·테스트 전용 잔재의 구분. 이 부의 재확인 결과가 과거 문서의 낡은 파일명/상수명보다 우선한다.
5. **제5부 — 포털·메뉴·화면 디자인 검증 및 신규 설계:** 전문 역할 에이전트 2명의 검토를 반영한 정보 구조, 대표 화면 와이어프레임, 시각 토큰, 전체 화면 적용표, 구현·검증 기준.
6. **제6부 — 상용 제품 수준의 상세 디자인:** 추가 전문 디자이너 역할 에이전트 3명의 UX·시각·인터랙션 설계를 통합한 사용 여정, 컴포넌트 상태, 저장·복구 계약, 설정 스키마 경계, 구현 순서와 출시 수용 기준. 제5부를 구체화하며 겹치는 세부 규격은 제6부를 우선한다.

Claude Code에는 이 파일 전체를 읽고 제3부의 공통 구현 지시, 제2·4부의 추가 작업, 제5부의 UI-0~6 및 제6부의 COM-0~6 디자인 구현 지시를 함께 수행하도록 전달하면 된다. 기존 코드/설계 문서 경로는 근거와 수정 대상이므로 그대로 유지한다. 작업 트리가 계속 변경되고 있으므로 각 발견 사항은 착수 시 현재 코드와 재대조한다.

## 제1부 — 적대적 검증

검증일: 2026-09-26. 대상: 현재 작업 트리의 코드, 기준선 및 후속 마이그레이션, 범용 플랫폼 정본 설계, SP1 설계, README와 작업 규칙. 구현 변경 없이 검토했다. 기존 미커밋 변경은 보존했다.

### 판정

**현재 구현은 목표 미충족이며, 현 설계를 끝까지 구현해도 ‘어떤 프로젝트든 설정만으로 대응’이라는 이번 요구는 충족하지 못한다.**

SP0·SP1 중심의 현재 코드에 SP3~SP9 예정 작업이 남은 것은 구분해야 한다. 아래에서 ‘구현 공백’은 이미 계획된 작업이고, ‘설계 충돌’은 로드맵 완료로도 해결되지 않는 문제다. 문서의 과거 ‘변경 불가’ 결정과 이번 요구가 충돌하는 부분은 이번 요구를 기준으로 판정했다.

모든 상수를 설정으로 만들 필요는 없다. 프로토콜, 보안 경계, 자원 제한은 명시적인 제품 계약으로 유지할 수 있다. 그러나 고객의 업무 분류·상태·근무 달력·승인 정책·출력 구조는 코드 수정을 요구하면 안 된다.

### 발견 사항

#### 1. [P1 / 설계 충돌] 프로젝트 업무 흐름을 바꿀 수 없다

- 근거: 정본 설계 81, 1483행 이후, 2978행은 이슈 상태와 WBS 단계를 제품 고정으로 선언한다. `src/lib/domain/issues.ts:8`, `src/lib/domain/agentWork.ts:9`, `:12`, `:43`, 기준선 SQL의 `issues_status_check`·`wbs_items_stage_check`에도 고정돼 있다.
- 반례: ‘접수 → 검토 → 고객 승인 → 실행 → 종료’ 또는 승인 2단계가 필요한 프로젝트는 설정만으로 표현할 수 없다. 특히 `predecessorReached`는 `im`도 선행 충족으로 본다. 최종 승인 전 후속 작업을 금지하는 프로젝트와 맞지 않는다.
- 영향: 표시 이름만 바꿔도 실제 전이·선행 조건·완료 의미는 바뀌지 않는다.
- 수정 방향: 프로젝트별 상태 정의와 전이, 승인 조건, 선행 충족 조건을 설정으로 만들고 UI·서버·DB·에이전트가 동일 정의를 사용해야 한다. 완료/취소 등의 시스템 의미는 상태 ID와 별도 속성으로 둔다.

#### 2. [P1 / 실행 재현 / 구현 공백] 사용자 정의 주간 구분이 이월 과정에서 PMO로 변한다

- 근거: `src/lib/domain/weeklySheet.ts:21`, `:44`, `:98`, `:124`, `:159`; 실제 저장 경로는 `src/app/actions/weekly.ts`의 `carryOverRows`·`defaultWeeklyRows` 호출이다.
- 재현: `section='Research', nextContent='Run experiment'`인 행을 `carryOverRows`에 전달하면 `section='PMO', thisContent='Run experiment'`가 나온다. 결과 구조도 고정 11개 구분이다.
- 영향: 단순 기본값 문제가 아니라 사용자 분류의 의미가 변하는 데이터 변환이다. 여러 사용자 구분은 같은 PMO 셀에 합쳐질 수 있다.
- 수정 방향: `area_id`와 프로젝트 영역 설정을 주입한다. 미매핑 구분은 명시적으로 보존하거나 변환을 거부하고, 과거 체계 변환은 별도 마이그레이션에 한정한다. SP4에 계획돼 있으므로 완료 전 범용 주간보고로 간주하면 안 된다.

#### 3. [P1 / 실행 재현 / 구현 공백] 근무일 설정을 계산 경로가 읽지 않는다

- 근거: `src/lib/domain/dates.ts:10`, `:21`, `:50`; `src/lib/domain/progress.ts:10`; `src/lib/data/projectConfig.ts:39`. DB에는 `working_days`가 있지만 로더의 SELECT와 반환 타입에 없다.
- 재현: `isBusinessDay('2026-09-26', new Set())`는 false, 금요일인 2026-09-25는 true다. 근무요일을 전달할 인자도 없다. `2026-09-26T02:00:00Z`는 로스앤젤레스에서 9월 25일이지만 `seoulYmd`는 9월 26일을 반환한다.
- 영향: 일~목 근무 프로젝트, 주말 공사 프로젝트, 해외 프로젝트에서 계획 진척과 오늘 기준 판정이 틀린다.
- 수정 방향: 프로젝트 달력을 날짜·간트·의존 일정·집계·봇·SQL 시간 집계까지 전달한다. 한국 공휴일 표시를 고정 유지한다는 설계 1627행도 국가/지역 달력 선택으로 개정해야 한다. 프로젝트 시간대와 워크스페이스 화면 시간대의 우선순위도 명시한다.

#### 4. [P1 / 설계 충돌] 양식 변경과 업무 데이터 구조 변경을 혼동하고 있다

- 근거: 정본 설계 69행 ‘열=제품 고정’, 1101행 설정 항목 코드 고정, 1492행 주간 시트 4열 고정. `src/lib/domain/weeklySheet.ts:134`의 `WEEKLY_CELL_KEYS`도 4개뿐이다.
- 반례: 건설 프로젝트의 공종·수량·검측 결과, 연구 프로젝트의 실험 조건·판정, 고객별 추가 승인 정보를 독립 필드로 수집·검증·검색하려면 코드와 스키마 변경이 필요하다.
- 영향: 고객 PPT를 올릴 수 있어도 병합할 원본 데이터 필드가 없으면 그 업무를 지원하지 못한다.
- 수정 방향: 핵심 엔티티의 타입 있는 사용자 정의 필드와 필수 여부·선택지·검증·표시·검색·양식 매핑을 설계에 포함한다. 출력 템플릿만으로 이 문제를 해결했다고 판단하지 않는다.

#### 5. [P1 / 실행 재현 및 설계 충돌] 이슈 영역과 출력물의 범용성이 서로 다르다

- 근거: `src/lib/domain/issueAnalysis.ts:4`, `:89`, `:168`; `src/lib/report/issues/model.ts:236`; 기준선 SQL 1106, 6369행의 `PI-I-` 생성 및 CHECK. 정본 설계 2235행은 활성 영역 8개 초과 시 `FIXED_SLIDE_LIMIT`로 렌더 거부한다.
- 재현: `isIssueMegaCode('RND')`는 false다. 현재는 00~07의 제조업 중심 영역만 유효하다.
- 영향: SP5로 영역을 설정화해도 SP6 설계상 9개 영역의 프로세스 슬라이드는 출력하지 못한다. 접두사 설정만으로 고객별 연도·전역 일련번호 등의 ID 규칙을 지원할 수도 없다.
- 수정 방향: 영역 목록·채번 정책을 설정으로 통합하고, 보고서는 영역 수에 따라 페이지 분할 또는 레이아웃을 계산한다. 8개 제한을 유지하려면 해당 출력 유형의 명시적인 지원 한계로 선언해야 한다.

#### 6. [P1 / 설계 결함] 모듈 설정 검증에 서로 만족할 수 없는 조건이 있다

- 근거: 정본 설계 1204행은 `modules.enabled ⊆ PROJECT_TOGGLABLE`을 요구하고, 바로 다음 1205행은 core 모듈이 `modules.enabled`에서 빠지면 거부한다고 한다. 1289행의 `PROJECT_TOGGLABLE` 정의는 `!core`다.
- 반례: WBS가 core라면 enabled에 WBS를 넣으면 첫 조건 위반이고, 빼면 두 번째 조건 위반이다.
- 영향: 문면대로 구현하면 유효한 프로젝트 모듈 설정을 저장할 수 없다.
- 수정 방향: 저장되는 enabled에는 선택 모듈만 담고 core는 계산 결과에만 포함하도록 규칙을 하나로 정한다. 1307행의 의존성 정리보다 core 추가가 뒤인 순서도 점검해 core 의존 모듈이 먼저 제거되지 않게 한다. 현재는 미구현 설계 문제이며 실제 런타임 장애로 판정한 것은 아니다.

#### 7. [P2 / 구현 공백] 설정된 엑셀 프로파일이 모든 내보내기 경로에 적용되지 않는다

- 근거: `src/app/api/export/route.ts:26`의 `expand` 분기. true일 때만 `config.excelProfile`을 검증해 사용하고, false일 때는 `buildWbsWorkbook`에 팀·레벨 라벨만 전달한다. 39행 이후는 프로파일 손상 시 레거시 양식으로 폴백한다.
- 반례: 같은 프로젝트와 같은 저장 설정으로 `/api/export?projectId=...`와 `&expand=1`을 호출하면 양식 적용 경로가 다르다.
- 영향: 관리자가 지정한 출력 계약이 버튼/URL에 따라 무시되거나 잘못된 양식으로 대체된다.
- 수정 방향: 모든 출력 진입점이 같은 해석된 설정을 사용하고, expand는 행 펼침 옵션만 결정하게 한다. 유효하지 않은 고객 양식은 명시적으로 실패시킨다.

#### 8. [P2 / 설계 공백] 설정 변경 시 데이터 무결성과 과거 의미 보존 계약이 부족하다

- 근거: 정본 설계 1176~1210행은 사용 중 어휘 삭제를 액션의 사전 count 조회로 검증하고 이후 별도 RPC로 저장한다. 1166행은 parse 실패를 default로 치환한다. 설정 저장소 정의에는 명시적인 스키마 버전·예상 revision이 없다.
- 반례(설계 추론, 동시 실행 미검증): count=0 확인 직후 다른 요청이 그 유형의 레코드를 쓰고 이어 설정에서 code를 삭제하면 참조가 남는다. `counts_as`를 변경하면 과거 근태의 재집계 의미도 바뀔 수 있으나 적용 시점 계약이 없다.
- 수정 방향: 설정 변경과 참조 검증을 동일 DB 트랜잭션 및 공통 잠금 규약으로 보호한다. 설정 revision·스키마 마이그레이션·충돌 처리를 정의하고, 의미가 달라지는 설정은 적용일/버전 또는 데이터 스냅샷 정책을 둔다. 잘못된 업무 설정을 정상 default처럼 소비하지 않게 한다.

#### 9. [P2 / 구현 공백 및 설계 충돌] 설정 가능한 것처럼 보여도 공급자·계산 정책이 고정돼 있다

- 메일: `src/lib/mail/transport.ts:32`는 Gmail 465/TLS 고정이다. 계정만 바꿔 회사 SMTP를 쓸 수 없다. host·port·TLS·인증·발신 주소를 배포 설정으로 분리해야 한다(SP9 예정).
- AI 팀 인식: `src/lib/ai/chat/router.ts:207`은 PMO/ERP/MES/가공/MDM만 메시지에서 추출한다. 팀 마스터를 늘려도 자연어 팀 필터가 따라 늘지 않는다(SP8 예정). 프로젝트 설정을 라우터에도 주입해야 한다.
- 진척 정책: `src/lib/domain/stageCredits.ts:18`의 5단위, 19행의 최소 간격 10은 설정 검증 자체에 고정돼 있으며 설계 1441행도 유지한다. 실행 시 0/20/25/90/100 표는 거부됐다. 고객별 단계 진척 정책을 허용할지, 지원 제한으로 둘지 요구를 다시 정리해야 한다.

### 실행 근거와 한계

### 3. 이전 인계서에서 빠졌거나 부족한 추가 발견

#### COV-01 [P1] 진척률 집계 방식도 업무 정책인데 설정 대상에서 빠졌다

근거: `src/lib/domain/rollup.ts:16`의 overallProgress와 computeNode, `src/lib/domain/progress.ts`, `src/lib/domain/format.ts`.

상위/전체 진척은 가중 평균이다. 전체 루트 계산은 가중치가 모두 null이면 균등, 일부만 null이면 null의 기여도를 0으로 본다. 반면 자식 집계의 siblingWeight는 null을 1로 본다. 이 차이는 코드에 고정돼 있다.

실행 반례: 완료100%·weight=1인 루트와 완료0%·weight=null인 루트를 overallProgress에 전달하면 전체 actual=100이다. 균등 계산을 원하는 프로젝트의 기대값 50과 다르다. 이것을 일률적인 계산 버그라 단정하지 않는다. **프로젝트가 집계 규칙을 선택할 수 없다는 점**이 문제다.

추가할 설정: 지원 산식(균등/명시 가중치/기간 가중치 등), null 가중치 처리(거부/균등/제외), 소수 정밀도, 계획 곡선 방식, 수동 진척 허용 범위. 임의 코드 수식을 실행하지 말고 지원 가능한 선언형 전략으로 제한한다.

합격 조건: 같은 트리에서 정책을 바꿔 기대 집계가 달라지고 대시보드·WBS·스냅샷·보고서가 일치한다. 저장된 과거 지표를 재계산할지 유지할지 정책 버전을 기록한다.

#### COV-04 [P2] 알림은 개인 필터만으로 정책 제어가 되지 않는다

알림 타입별 prefs 읽기와 일반적인 prefs 저장 API는 있으므로 ‘저장 불가’라고 단정하지 않는다. 그러나 전용 설정 UI는 이번 검색에서 찾지 못했다. 수신자 선택·필수 알림 여부·채널·발행 조건을 관리자 설정으로 제어하는 공통 정책은 확인하지 못했다.

추가할 설정: 이벤트별 활성/채널/수신 대상 규칙/요약 주기/방해금지 시간. 권한 없는 사용자에게 전달하거나 승인 대기 업무 자체를 숨기는 설정은 허용하지 않는다. 인앱 필수 업무함과 선택적인 전달 알림을 구분한다. 필수 보안 알림은 별도 고정 불변식으로 선언할 수 있다.

합격 조건: 개인 opt-out과 프로젝트 필수 정책의 우선순위, 관리자/담당자 라우팅, 이벤트 중복 억제, 설정 후 새 이벤트의 전달을 검증한다. UI 표시만 필터링하고 메일은 계속 보내는 불일치를 금지한다.

#### COV-05 [P1] 보존기간은 파라미터가 있어도 호출부에서 90일로 고정된다

근거: `src/app/api/cron/inbox-retention/route.ts:24`는 RPC에 retention_days:90을 전달한다. `src/lib/domain/usage.ts:8`의 USAGE_RETAIN_DAYS=90을 `src/lib/data/usage.ts:238`의 정리 경로가 소비한다. vercel.json에는 `0 19 * * *` cron이 고정돼 있다.

영향: 장기 보존이 필요한 고객에서 단순 조회/정리 작업이 정책에 맞지 않는 삭제를 수행할 수 있다. 이번 검토에서 실제 삭제를 실행하지 않았다.

추가할 설정: 데이터 종류별 보존 기간·자동 삭제 활성·법적/업무 보존 잠금이 필요한지·실행 스케줄. 상위 운영자가 허용한 범위 내에서만 변경하게 한다. 워크스페이스별 기간이면 삭제 RPC도 해당 스코프로 좁혀야 한다.

합격 조건: 30일/365일 워크스페이스를 같은 시각에 정리해 각자 해당되는 행만 삭제한다. 비활성/보존 잠금/조회 실패일 때 삭제하지 않는다. 스케줄 설정과 실제 배포 산출물이 일치한다.

#### COV-06 [P2] 에이전트 운영 정책이 코드/프로토콜과 섞여 있다

근거: `src/lib/domain/seatState.ts:16` stale5분/offline30분/watcherTTL70분, `src/lib/domain/agentWork.ts:109`의 critical100/high50/medium10/low0, `src/lib/agent/wbsImport.ts:94`의 허용 우선순위.

실행 확인: `orderPriorityFromLabel('urgent')`는 오류가 아니라 0을 반환한다. 외부 입력 검증에서는 거부되는 경로도 있으므로 모든 API가 0으로 저장한다고 주장하지 않는다. 순수 함수와 importer의 허용 범위가 설정 기반이어야 한다는 근거다.

추가할 설정: 표시용 stale/offline 시간, 실제 lease/재선점 정책, 업무 우선순위 코드/점수, 동시 작업 수가 필요한 경우의 허용치. 시각적 offline과 실제 작업 회수는 반드시 구분한다. heartbeat·watcher·runner·서버가 상충하는 TTL을 쓰지 않게 한다.

#### COV-07 [P2] env로 노출했어도 변경 가능한 설정이 아닌 값이 있다

근거: `src/lib/ai/provider.ts:82`, `:92`는 EMBED_DIM을 받지만 DB는 vector(768)·차원 CHECK를 갖는다. `src/lib/ai/embeddings.ts`의 검증은 응답 길이와 cfg.dim을 비교하므로, cfg.dim 변경만으로 DB 계약은 바뀌지 않는다.

정본 §5.4.5는 이 문제를 알고 768 고정+env 삭제를 계획했다. 그 방안은 정직한 지원 제한이며 설정화율에 포함하면 안 된다. 모델/차원을 자유롭게 선택하게 하려면 별도 인덱스 버전과 재색인/전환 절차가 필요하다. 단순 슬라이더나 env 추가로 해결하지 않는다.

같은 이유로 `src/lib/branding.ts`의 NEXT_PUBLIC_*는 배포별 설정이지, 재배포 없는 워크스페이스별 설정이 아니다. 문서와 UI에 적용 시점(즉시/다음 실행/재시작/재빌드/재색인)을 표시해야 한다.

#### COV-08 [P2] 권한 배정과 권한 모델 설정은 다르다

근거: `src/lib/domain/authz.ts`의 roleIn/isProjectAdmin/isProjectMember는 역할 격자와 관리자 승계를 고정한다. canSeeProject는 비공개를 화면 숨김으로 해석한다고 명시한다.

‘이슈만 편집하는 외부 협력사’, ‘회의록 검토만 가능한 역할’, ‘프로젝트 관리자도 승인 불가’처럼 권한 세분화가 필요한 프로젝트에는 기존 역할 배정만으로 부족할 수 있다. 이는 확인된 지원 한계이며 이번 검토에서 보안 침해를 실증한 것은 아니다.

설정 범위를 확대한다면 기능별 capability 및 역할 매핑을 설계하고 중앙 가드와 DB/RLS를 동시에 반영해야 한다. 현재 인계서의 ‘기존 가드 만족’만으로 임의 고객 역할까지 지원한다고 주장하지 않는다. 테넌트 경계·자기 권한 상승 금지·서비스 계정 비밀은 설정으로 해제 불가다.

#### COV-09 [P2] 조직 언어·표현과 입력 한계의 경계가 명시되지 않았다

근거: `src/lib/prefs/sync.ts`는 locale ko/en; report/week.ts는 한국어 주차 문구; report/weekly.ts는 한국어 요일/상태 표현을 갖는다. `src/lib/domain/minutes.ts`는 첨부20MB/10개·폴더 깊이5, levelSettings는 WBS10단을 고정한다.

날짜/숫자 표기·보고서 언어·업무 용어는 고객 설정 대상이다. 새로운 언어 번역 자원이 없는 문제까지 locale 문자열로 해결되지는 않는다. 지원 언어와 사용자 정의 업무 라벨을 구분한다.

파일 크기/폴더 깊이/요청 크기 등은 무제한 허용하지 않는다. 운영 상한을 고정하고 그 이하의 프로젝트별 정책을 설정으로 둘 수 있다. UI/API/Storage 제한이 일치해야 한다. 현재 상한과 고객 정책을 하나의 숫자로 뭉뚱그리지 않는다.

### 4. 설정으로 바꿀 것과 고정할 것

| 분류 | 예시 | 원칙 |
|---|---|---|
| 고객 업무 설정 | 분류·필드·상태·승인·달력·지표·알림·양식 | 관리자 UI/API, DB 검증, 프로젝트별 격리 |
| 운영 설정 | SMTP·제공자 endpoint·작업 주기·보존 상한·동시성 | 운영자 권한, 시크릿 보호, 적용 시점 명시 |

| 제품 불변식 | 인증·테넌트 격리·ID 무결성·원자성·프로토콜 구문 | 일반 설정으로 해제하지 않음 |

‘거의 대부분’의 실용적인 정의는 **고객 업무 정책은 전부 카탈로그화하고, 카탈로그 항목은 전부 관리자 설정→실제 소비처→테스트가 연결되게 한다**는 것이다. 새로운 도메인의 모든 개념이나 외부 프로토콜까지 코드 없이 확장할 수 있다는 무제한 약속은 하지 않는다.

## 제3부 — Claude Code 구현 지시

### 0. 작업 지시와 권한 범위

이 문서를 읽고 D-Flow의 범용성 결함을 실제 코드와 설계 문서에 수정하라. 분석·계획만 제출하고 끝내지 말고, 아래 의존 순서대로 구현과 검증을 진행하라. 이 문서는 사용자가 Claude Code에 전달하기 위한 구현 지시서다. 현재 작성자는 제품 코드를 수정하지 않았다.

**추가 재검토 반영:** 사용자는 ‘거의 대부분을 설정값으로 제어’할 수 있는지도 확인하도록 요청했다. 이 파일의 제2부 「설정 제어 범위 재검토」를 반드시 함께 읽어라. 기존 A~H만으로 완료를 선언하지 말고, 제2부 §5의 I~M(집계/위험 정책, 보고 주기, 알림/보존/스케줄, 운영/호환성, 권한 범위)도 작업 목록과 설정 카탈로그에 반영하라. 구현 제안과 확인된 반례, 아직 실행 검증하지 않은 위험을 구분하라.

최상위 요구는 다음과 같다.

> 어떤 고객사·프로젝트에도 유연하게 대응할 수 있어야 한다. 프로젝트의 업무 규칙을 바꾸기 위해 소스 코드나 고객별 DB 마이그레이션을 수정하게 만들지 말고, 관리자가 설정으로 변경할 수 있게 한다.

이 요구와 충돌하는 기존 설계의 ‘제품 고정’ 결정을 재검토하고 정본 설계에 반영하라. 단, 이 문서의 제안 스키마·함수 이름은 구현 방향이며 이미 존재하는 API가 아니다. 착수 시 현재 코드와 대조하여 최소한의 일관된 설계로 확정하라.

프로토콜 버전, 보안 불변식, 자원 상한까지 무조건 사용자 설정으로 만들라는 뜻은 아니다. 고객별 업무 분류·워크플로·근무 달력·진척 정책·추가 필드·양식·공급자 연결은 설정 대상이다. 제품상 고정할 것은 근거와 지원 한계를 `docs/settings-catalog.md`에 명시하라.

이 지시에는 로컬 구현·테스트·문서 수정이 포함된다. 원격 배포, push, 외부 메시지 발송, 원본 고객 DB 접근은 포함되지 않는다.

### 1. 착수 시 읽고 보존할 것

필수 입력:

- `CLAUDE.md`, `README.md`, 적용되는 `AGENTS.md`가 있다면 해당 파일.
- 이 파일 제1부 「적대적 검증」와 제2부 「설정 제어 범위 재검토」.
- `docs/superpowers/specs/2026-09-23-generic-platform-design.md`.
- `docs/superpowers/specs/2026-09-24-sp1-org-core-design.md` 및 관련 계획.
- `supabase/migrations/0000_baseline.sql` 이후 모든 적용 마이그레이션과 rollback.

작업 트리에는 다른 작업의 미커밋 변경이 있다. `git status --short`와 해당 diff를 먼저 확인하라. 검토 시점에도 변경 목록이 움직였으므로 과거 목록을 믿지 말라. reset·clean·일괄 checkout·전체 덮어쓰기를 하지 말고, 기존 변경과 겹치는 파일은 현재 내용을 기준으로 수정하라. `git add -A`는 금지다.

UI 위험 파일을 수정하면 `CLAUDE.md`의 브랜치 규칙을 따른다. 원본 Supabase 금지 목록을 우회하지 않는다. 기존 기준선 SQL을 직접 편집해 이력을 바꾸지 말고 새 마이그레이션으로 적용한다. 새 번호는 착수 시 마지막 번호와 기존 예약 계획을 확인해 배정하고, 동명의 rollback을 별도로 만든다. 마이그레이션과 앱 코드를 커밋한다면 서로 분리한다.

`db:reset`은 계정과 데이터를 지운다. 기존 개발 DB를 무조건 초기화하지 말고, 비어 있거나 폐기 가능한 검증용 로컬 DB임을 확인해 실행한다. 제약 완화를 통해 테스트를 통과시키지 않는다.

### 2. 현재 확인된 사실과 검증 한계

검토 시점에는 SP1 조직 코어까지의 구현을 확인했다. `project_areas`·`area_teams`는 `0003_org_core.sql`에 이미 있으므로 새로 중복 생성하지 말라. 반면 정본의 `src/lib/settings`·`src/lib/modules`·`tests/settings`·`tests/gates`는 검토 당시 미구현이었다. 이후 변경 여부를 다시 확인하라.

확인한 반례:

| 입력/상황 | 현재 결과 | 요구 결과 |
|---|---|---|
| 주간 이월: Research 구분에 Run experiment | PMO 구분으로 이월 | 같은 영역 ID·내용 보존 |
| 토요일 근무 프로젝트, 2026-09-26 | 비근무일 고정 | 해당 프로젝트 달력으로 근무일 판정 |
| 2026-09-26T02:00:00Z, America/Los_Angeles | 서울 기준 9월 26일 | 현지 기준 9월 25일 |
| 이슈 영역 code=RND | 거부 | 해당 프로젝트 등록 영역이면 허용 |
| 진척표 0/20/25/90/100 | 간격 10 미만으로 거부 | 설정한 정책이 허용하면 수용 |
| 같은 설정으로 export의 expand 변경 | 저장 프로파일 사용 경로가 달라짐 | 양식은 같고 펼침만 변경 |

순수 함수 반례는 실제 소스를 실행해 확인했다. DB 동시성 결함은 설계에서 추론한 위험이며 아직 동시 실행으로 재현하지 않았다. 영역 8개 제한과 모듈 검증 모순은 설계 결함이다. 이를 현재 런타임에서 재현한 장애로 보고하지 말라.

기존 테스트는 `tests/domain/weeklySheet.test.ts`, `tests/domain/dates.test.ts`의 46개가 통과했다. 크레딧·이슈 테스트의 정확한 파일명은 각각 `tests/domain/stage-credits.test.ts`, `tests/domain/issue-analysis.test.ts`다. 최초 검토에서는 이 두 파일을 실행하지 않았다. 이번 작업에서는 포함하라.

### 3. 공통 구현 계약 — 개별 상수 치환보다 먼저

#### 3.1 설정의 정본과 스코프

하나의 설정 레지스트리와 하나의 프로젝트 설정 해석기를 사용하라. 기존 `src/lib/data/projectConfig.ts`를 포함해 두 개의 정본이 생기지 않게 이전한다.

- 배포 설정: SMTP·AI endpoint 등 운영자가 제어할 연결 정보. 시크릿은 서버 전용.
- 워크스페이스 설정: 공용 기본값·허용 모듈·브랜딩·초대 정책.
- 프로젝트 설정: 업무 규칙·상태·영역·달력·양식·추가 필드.
- 계정 취향: 테마·표시 옵션. 업무 계산의 정본과 분리.

키마다 타입, 기본값 또는 생성 필수 여부, 검증, 소유 모듈, 변경 권한, 적용 범위, 기존 데이터에 미치는 영향을 선언하라. 정의 자체가 코드에 있다는 이유로 고객별 값을 코드에 넣지 말라.

목록형 엔티티는 안정적인 ID/code와 표시 라벨을 분리한다. 라벨 변경이 FK·검색 필터·보고서 연결을 끊으면 안 된다. 팀/영역은 기존 테이블을 재사용하고, 다른 목록의 JSONB/테이블 저장 방식은 참조 무결성 요구에 맞춰 확정한다.

순수 함수에는 필요한 설정 조각을 인자로 전달한다. 프로젝트 설정을 모듈 전역 변수나 마지막 로드한 팀 목록에 저장하지 않는다. 요청 밖 캐시가 필요하면 workspaceId·projectId·설정 revision을 키에 포함하고 무효화 정책을 둔다.

#### 3.2 저장·읽기·오류 계약

- 미설정, 명시적 빈 배열, 비활성, 유효하지 않은 값, 조회 실패를 구분한다.
- 미설정은 선언된 중립 기본값 또는 ‘설정 필요’ 상태로 처리한다. 잘못된 값은 키와 오류를 드러내며 해당 업무 실행을 중단한다. PMO·서울·레거시 양식으로 조용히 대체하지 않는다.
- 모르는 설정 키는 저장 성공으로 위장하지 말고 명시적으로 거부한다. 기존 설계의 strip 정책과 차이를 문서화한다.
- 읽기/쓰기 API의 오류 형식을 맞춘다. 설정 충돌은 `CONFIG_CONFLICT`, 잘못된 설정은 `CONFIG_INVALID`, 누락은 `CONFIG_REQUIRED`처럼 호출자가 구분 가능한 코드로 정한다. 이름은 기존 에러 규약과 맞춰 확정한다.
- UI만 검증하지 않는다. 직접 PostgREST 쓰기·RPC·외부 API·워커에서도 같은 계약이 강제돼야 한다.

#### 3.3 원자성·버전·이력

프로젝트 생성과 필수 설정 저장을 동일 트랜잭션에 넣는다. 신규 설정은 schema version과 revision 또는 동등한 버전 계약을 갖게 한다. 변경 API는 expected revision을 받아 동시 편집 유실을 거부한다.

사용 중 code 삭제 금지를 액션의 사전 count만으로 구현하지 말라. DB 안에서 참조 검사와 변경을 원자적으로 하고, 해당 code를 새로 참조하는 쓰기 경로도 같은 잠금/무결성 규약을 사용한다. FK가 가능한 모델이라면 FK를 우선 활용한다. 설정 저장 측만 잠그면 충분하다고 가정하지 않는다.

설정 변경 이력은 수정 전후 값·수정자·revision·시각을 기록한다. 근태 집계 분류, 진척 산식처럼 과거 수치의 의미를 바꾸는 변경은 적용일/버전 참조 또는 스냅샷 정책을 확정한다. 기본 동작으로 과거 확정 보고서가 조용히 재해석되지 않게 한다.

기존 데이터 이행은 프로젝트별 현행 값의 명시적 복사로 한다. 과거 고객 기본값을 새 프로젝트의 런타임 fallback으로 남기지 않는다. 무매핑 데이터는 목록과 건수를 보고하고 보존한다.

### 4. 구현 작업별 지시

#### A. 설정 엔진과 모듈 검증 모순 해소

관련 위치: 정본 §3.1, §3.2, `src/lib/data/projectConfig.ts`, `src/app/actions/project.ts`, 프로젝트 settings 페이지.

5. 메뉴 숨김만으로 완료하지 말고 페이지·액션·API·봇 도구·워커를 같은 판정으로 막는다. 외부 API 기존 오류 계약은 유지하거나 명시적 호환 처리를 한다.

프로젝트별 상태는 stable code, label, sort, active, 완료/취소 등의 의미 속성, 진척값을 갖게 하고, 허용 전이와 승인 요구·선행 충족 조건을 별도 정의한다. 임의 JS/SQL 수식을 설정으로 실행하는 범용 스크립트 엔진은 도입하지 말고 선언형 규칙만 허용한다.

- 2단계 승인에서는 첫 승인으로 최종 완료/착수 허용이 되지 않아야 한다. 승인자의 권한은 설정만으로 확장되지 않으며 기존 권한 가드를 반드시 만족해야 한다.
- 상태와 관련 진척·주문 상태·승인 기록·로그를 DB 트랜잭션으로 변경한다. TS는 같은 정의로 옵션/사전 검증을 생성하고 DB가 최종 판정한다.
- 5단위/최소 간격 10은 필수 업무 규칙으로 두지 않는다. 필요하면 프로젝트 정책으로 두고, 유한 숫자·0~100 등 기본 검증은 유지한다. 반려·재작업의 진척 감소 정책도 명시한다.
- 사용 중 상태 삭제를 막고 비활성화 및 명시적 상태 이관을 제공한다. 과거 이벤트와 알림의 의미를 보존한다.

필수 테스트: 기존 동작을 데이터 설정으로 재현, 새로운 5상태 흐름, 고객 승인 2단계, 금지 전이 거부, 같은 작업 동시 전이 충돌, 승인 전 실적 100 우회 차단, 완료 전 알림 미발송, 반려/승인 취소 후 판정 일치, 0/20/25/90/100 설정 수용.

#### E. 사용자 정의 필드

‘열=제품 고정’만으로는 이번 목표를 달성할 수 없다. 핵심 필드와 확장 필드를 함께 지원하도록 정본 §1.3·§3·§4를 개정한다. 1차 지원 엔티티는 WBS 항목·이슈·주간행으로 명시하고, 미지원 엔티티까지 지원한다고 보고하지 않는다.

필드 정의에는 프로젝트·대상 엔티티·stable key/ID·표시명·타입·필수 여부·선택지·순서·활성 여부를 둔다. 최소 타입은 text, multiline, number, date, boolean, select, multiselect다. 저장 형식은 JSONB 또는 typed value 테이블 중 현재 조회 패턴에 맞춰 확정하되 다음 계약은 지킨다.

- 정의된 키만 저장하고 서버/DB에서 타입·선택지·프로젝트 스코프를 검증한다.
- 기존 데이터가 있는 타입 변경은 기본 거부한다. 필수화는 기존 누락 데이터 처리와 함께 수행한다.
- UI 입력·상세·목록 필터·검색·봇 근거·Excel/PPT 매핑에 같은 field ID를 사용한다.
- 개명은 값의 key를 바꾸지 않는다. 비활성화는 과거 값을 지우지 않는다.
- 문서 검색 색인 갱신과 형식화에 설정 revision 또는 적절한 무효화 경로를 연결한다.

필수 테스트: 연구 프로젝트 experiment_result 선택지와 건설 프로젝트 inspected_quantity 숫자 필드, 잘못된 타입 거부, 다른 프로젝트 정의 참조 거부, 개명 후 값·필터·출력 유지, 내보내기/다시 가져오기에서 지원 필드 보존.

#### F. 이슈 영역·ID 정책·8개 초과 출력

주요 파일: `src/lib/domain/issueAnalysis.ts`, `src/lib/data/issueAnalysis.ts`, `src/app/actions/issueAnalysis.ts`, `src/app/actions/issues.ts`, `src/lib/report/issues/{model,deckPlan,processPages,processSlideRenderer,export}.ts`, `src/lib/ai/minute-issue-draft.ts` 및 관련 AI 생성 코드. 실제 파일 존재와 호출 관계를 확인한다.

00~07 제조업 분류·`PI-I-`를 런타임 정답으로 두지 않는다. 기존 project_areas의 issue_area를 정본으로 쓰고 생성/폼/봇/검증/채번/출력이 이를 읽게 한다. 회의록 출처처럼 무결성 경로를 구별하는 시스템 의미는 표시 라벨과 분리해 보존한다.

채번 정책은 프로젝트/영역별 카운터 범위, 접두사, 최소 자리수, 연도 포함/초기화 여부처럼 제한된 선언형 설정으로 표현한다. 설정 변경은 신규 ID에만 적용하고 기존 ID는 불변이다. 중복은 DB 유니크 제약과 원자 채번으로 막으며, 과거 CHECK가 새 형식을 거부하지 않도록 함께 교체한다.

8개 슬롯인 기존 PPT 자산은 페이지당 용량으로 취급한다. 9개 이상이면 이어지는 페이지를 만들거나 선택 양식이 명시한 용량대로 분할한다. 한 페이지의 영역 수가 제품 전체 영역 수 제한이 되지 않게 한다. 긴 라벨·테마·슬라이드 크기·연결선 및 Major 하위 항목도 검증한다.

필수 테스트: RND 영역 등록과 이슈 생성, 0/1/8/9/17개 영역의 전체 출력, 마지막 영역까지 누락 없음, 동시 채번 고유성, 접두/연도 정책 변경 후 기존 ID 유지, 주요 프로세스 연결 보존. 실제 렌더 또는 Office에서 확인한 결과를 남긴다.

#### G. Excel 프로파일 경로 통합

주요 파일: `src/app/api/export/route.ts`, `src/lib/excel/profile.ts`, `export.ts`, `exportWithProfile.ts`, 임포트/inspect 라우트와 다운로드 버튼.

`expand` 여부와 무관하게 같은 검증된 프로젝트 프로파일을 사용한다. expand는 하위 행 표현만 바꾸게 한다. 손상된 프로파일에서 `LEGACY_EXCEL_PROFILE_V1`로 성공 응답하는 경로를 제거한다. 프로파일이 없으면 설정 필요로 안내하거나, 명시적으로 선택/저장된 동봉 양식만 사용한다.

기존 기본 내보내기가 지원하던 기능이 새 경로에서 빠지는지 대조한다. outline+expand 등 미지원 조합은 오류로 명시한다. 엑셀에서 WBS N단계·추가 필드·팀 열이 왕복 보존되는지 검사한다. 기존 양식은 선택 가능한 자산/이행 데이터 또는 fixture로 남길 수 있으나 자동 fallback으로 쓰지 않는다.

필수 테스트: expand true/false의 sheet/header/team 매핑 일치, 깨진 프로파일 오류, 프로젝트별 다른 양식 교차 오염 없음, N단계 왕복, 필드/날짜/담당자 누락 없음.

#### H. SMTP·팀 인식 및 잔여 소비처

`src/lib/mail/transport.ts`에 SMTP_HOST·SMTP_PORT·SMTP_SECURE·SMTP_FROM_ADDRESS 등 명시적 연결 설정을 도입하고 `.env.local.example`·README를 갱신한다. 기존 env 이름은 가능한 한 유지한다. 포트/TLS 관계를 검증하고 인증이 없는 내부 relay를 지원할지 명시적으로 정한다. 인증서 검증을 비활성화하는 편법은 금지다. 실제 메일은 보내지 말고 transport mock 또는 로컬 수신기로 확인한다.

`src/lib/ai/chat/router.ts`의 고정 팀 정규식을 프로젝트 팀/별칭 데이터 기반으로 교체한다. 정규식을 구성한다면 메타문자를 escape하고, 비슷한 팀명·다국어·다중 프로젝트 동명 팀을 구별한다. 모호한 입력은 다른 팀을 추측해 선택하지 말라. `weekly.ts`의 팀→영역도 area_teams로 통일한다.

근태 유형·회의 분류·심각도·원인·출처·팀 색상·회의록 폴더/별칭도 동일 설정 체계로 이전한다. `DEFAULT_TEAMS`·TeamsProvider fallback·팀 전역 캐시·레거시 WBS 라벨·마일스톤 키워드·하드코딩된 i18n 업무명을 소비처까지 추적한다. 문자열을 상수 파일 하나로 옮기는 것으로 완료하지 않는다.

## 제4부 — 원본 고객·원본 프로젝트 특화 잔존 재검토

검토일: 2026-09-26. 이번 요청은 원본 고객에 맞춰 제작된 전제가 남았는지 다시 확인하는 것이다. **특화된 업무 가정은 여전히 남아 있다. 직접 브랜드 문자열이 없다는 것과 범용화 완료는 다르다.**

### 1. 직접 브랜드와 출처 판정

- 현재 소스·문서·스크립트·kit·`.claude`·`.github` 텍스트에서 원본 고객명과 그 유사 표기를 대소문자 무시로 검색했으나, 이번 제4부 작성 전 검색에서는 직접 명칭을 찾지 못했다.
- 동봉 PPTX 2개의 XML 텍스트에서도 해당 직접 명칭을 찾지 못했다.
- 정본 설계는 원본 고객명과 브랜드를 익명화했다고 명시한다. 따라서 남은 ERP/MES 등의 단어만으로 ‘원본 고객에서만 쓰는 고유 규칙’이라고 단정하지 않는다. 아래는 **현재 리포에 남은 원본 프로젝트 지향의 구체적인 동작·제약**이다.
- `.env.local` 비밀값, git 과거 보관 브랜치, 원본 고객 DB는 열람하거나 접속하지 않았다. 배포된 서비스의 실제 데이터·로그까지 이름이 제거됐다는 보증은 아니다.

### 2. 실제 실행/배포 경로에 남은 특화

#### DC-01 [P1] 기존 5팀과 11개 업무 구분이 신규 프로젝트의 동작에도 관여한다

검증 한계: 현재 코드·설계 구조를 대조했다. 원본 고객 화면 스크린샷과 현재 서비스의 픽셀 단위 비교는 하지 않았다. ‘더 세련됨’의 결과물 검증은 아래 디자인을 실제 구현한 뒤 화면 검수로 판정해야 한다.

### 2. 새 디자인 방향 — 작업 중심의 차분한 업무 공간

목표는 ‘다른 색의 기존 대시보드’가 아니라 **포털에서 할 일을 판단하고, 프로젝트에서 집중해서 처리하고, 설정에서 변경 영향을 이해하는 경험**이다.

확정할 변화:

1. 워크스페이스 포털과 프로젝트 작업 공간을 명확히 분리한다.
2. 짙은 사이드바·큰 그라데이션 히어로 중심 표현을 밝은 중립 셸·명확한 글자 위계·얇은 구분선으로 바꾼다.
3. 모든 데이터를 카드로 감싸지 않는다. 업무는 행 목록, 계획은 그리드/타임라인, 문서는 읽기 영역, 설정은 편집 폼으로 표현한다.
4. 포털과 개요는 정보 여백을 확보하고, WBS/주간보고는 화면 대부분을 편집 영역에 쓴다.
5. 화면마다 가장 중요한 행동 하나를 주 버튼으로 정한다. 위험 삭제는 주 버튼으로 노출하지 않는다.
6. 장식용 숫자보다 사용자가 다음 행동으로 이동할 수 있는 근거·기한·담당·상태를 우선한다.

보존할 기능: WBS 키보드/다중셀/붙여넣기/undo, 실시간 동시편집, 필터와 스크롤 복원, 직접 링크, 낮은 노트북 대응, 실패/빈 상태 구분, 권한 가드, 기존 Modal의 focus trap/restore. 새 디자인을 이유로 회귀시키지 않는다.

### 3. 정보 구조와 메뉴

화면에 보이는 메뉴는 아래 구조로 정하되 최종 노출은 `effectiveModules ∩ 권한 ∩ 메뉴 표시 설정`으로 계산한다. 관리자 메뉴 숨김은 서버 권한 검사나 모듈 차단을 대체하지 않는다.

```text
워크스페이스 전환: [워크스페이스 이름 ▾]
  홈                  오늘의 업무와 프로젝트 현황
  내 업무              내 작업·승인 대기·알림
  프로젝트             전체 목록·즐겨찾기·최근 방문
  공용 공간
    회의 일정           워크스페이스 범위
    회의록              워크스페이스 범위
    에이전트            전체 실행/검토 현황, 권한에 따라
  운영                  관리자에게만
    포트폴리오 / 사용 현황 / 워크스페이스 설정

프로젝트를 연 상태: [← 워크스페이스 홈] [프로젝트 이름 ▾]
  개요
  계획과 실행
    작업 계획           한 화면의 보기 전환: 표 | 간트 | 보드
    이슈
    주간보고
  협업과 지식
    회의 / 회의록 / 위키 / 공지
  팀과 자동화
    팀 구성 / 근태 / 에이전트
  프로젝트 설정         별도 하단 구분, 관리자만
```

설계 계약:

- 동일 WBS 데이터를 보는 표/간트/보드는 프로젝트 메뉴 3개가 아니라 작업 계획의 보기 전환으로 묶는다. 다른 편집 엔진이 필요하면 내부 구현은 유지하되 사용자 동선은 통일한다.
- 현재 `/wbs`, `/gantt`, `/kanban` 직접 링크는 보존하거나 명확한 view 매핑/리디렉션을 둔다. 저장된 링크/쿼리 파라미터가 깨지면 안 된다.
- 공용 공간을 열면 프로젝트 선택 표시는 ‘워크스페이스 전체’로 바뀐다. 최근 방문 프로젝트를 현재 범위처럼 강조하지 않는다.
- ‘내 업무’와 workspace home은 신규 집계 화면 제안이다. 현재 API가 모두 존재한다고 가정하지 않는다. 승인/담당 작업/알림의 스코프가 검증된 읽기 모델을 먼저 준비한다.
- 메뉴 그룹은 한 단계만 펼친다. 그룹 내 표시 순서와 명칭은 허용된 module ID에 대해 설정 가능하다. 사용자에게 임의 라우트·HTML·CSS 주입을 허용하지 않는다.
- 모듈이 꺼지면 메뉴·검색 진입점·페이지·액션이 함께 차단된다. 관리자는 설정에서 ‘사용 안 함’을 볼 수 있고 일반 사용자에게 회색 메뉴를 무더기로 노출하지 않는다.
- 글로벌 헤더의 breadcrumb가 workspace→project→screen을 한 번만 보여준다. 페이지 제목은 업무 화면명이며 프로젝트명을 반복하지 않는다.
- 프로젝트 전환 시 대상 프로젝트에서도 허용된 같은 모듈을 유지하고, 불가능하면 대상의 유효한 기본 화면으로 이동한다. 항목 ID 등 이전 프로젝트의 선택 파라미터는 제거하고, 공통 적용 가능한 보기/밀도만 보존한다. 설정으로 기본 화면이 비활성화되면 관리자가 유효한 대상으로 변경할 수 있어야 한다.
- 메뉴를 숨기는 개인/관리자 표시 설정과 모듈 비활성은 다르다. `hidden`은 탐색 취향이며 권한 부여/회수를 뜻하지 않는다. 메뉴를 숨겨도 권한 있는 직접 링크는 유지될 수 있고, 모듈 비활성 시에는 서버에서도 차단한다.
- 통합 검색은 현재 범위와 검색 대상을 명시한다. 권한 확인 전 데이터·검색 결과를 클라이언트로 내려 보내 숨기는 방식은 금지한다.

### 5. 시각 토큰과 표현 규칙

라이트 기본안은 밝은 neutral/cobalt다. 기존 cream/teal의 대면적 사용과 구분된다. 고객 accent 설정은 안전한 토큰만 바꾸며 상태의 의미 색을 덮어쓰지 않는다.

| 토큰 | 라이트 값 | 용도 |
|---|---|---|
| canvas | `#F5F7FA` | 앱 바탕 |
| surface | `#FFFFFF` | 내용/탐색 표면 |
| surface-subtle | `#EEF2F7` | 조용한 그룹/선택 보조 배경 |
| border | `#DCE2EA` | 장식적 경계. 입력 식별/포커스는 더 강한 별도 토큰 사용 |
| text | `#17212F` | 주요 본문 |
| text-secondary | `#526074` | 설명 |
| text-muted | `#606E82` | 보조 메타데이터. 제6부 대비 재검토로 보정 |
| action | `#315CDB` | 주 행동/선택. 흰 글자 |
| action-soft | `#EDF2FF` | 선택 행/탭 배경 |
| success | `#197455` | 완료. 텍스트/아이콘 동반 |
| warning | `#8A5B13` | 주의. 텍스트/아이콘 동반 |
| danger | `#B93845` | 위험/삭제/실패. 텍스트/아이콘 동반 |

다크 대응안: canvas `#11151C`, surface `#191F29`, subtle `#222B38`, border `#344052`, text `#EDF2FA`, secondary `#B6C2D2`, muted `#96A5BA`, action `#8AA8FF`, action-foreground `#111B35`. 상태색은 밝은 대응 토큰을 따로 정의한다. 라이트 값을 단순 반전하거나 라이트의 어두운 글자 색을 그대로 쓰지 않는다.

폰트는 현재 Pretendard Variable을 재사용하되 위계를 새로 정한다. 기본 본문14px/행간22px, 제목24px/32px, section16px/24px, 메뉴13px/20px, 보조12px/18px. 큰 KPI는28px/34px이며 숫자는 tabular-nums를 사용한다. 본문400, 메뉴/레이블500, 제목600. 화면 주요 조작에 10px 글자를 쓰지 않는다.

대비 계산 확인: 흰 배경 대비 text16.22, secondary6.39, 보정한 muted5.19, action5.70, danger5.65, success5.72, warning5.86이다. 이는 해당 단색 쌍의 계산값일 뿐 전체 UI 접근성 검증 결과는 아니다. 실제 hover·soft background·다크·고객 accent 조합은 구현 시 별도 검사한다. 제6부에 배경별 재계산 근거를 기록했다.

모션은 메뉴/inspector 전환160~200ms 정도의 opacity/transform만 사용한다. 수치/그리드 위치가 과하게 움직이지 않게 하고 reduced-motion에서는 생략한다. 포털 입장 시 카드가 순서대로 날아드는 장식 애니메이션은 사용하지 않는다.

### 6. 대표 화면 설계

아래 숫자·이름은 구도를 설명하기 위한 예시이며 실제 사용자 데이터가 아니다. 고해상도 시안이나 구현 완료 스크린샷이 아니라 구현 가능한 구조 와이어프레임이다.

#### 6.1 워크스페이스 포털 — 오늘 처리할 일을 먼저

```text
┌────────────────┬───────────────────────────────────────────────────────┐
│ D-Flow         │ 연구 워크스페이스        범위 내 검색       알림  계정 │
│ 워크스페이스 ▾ ├───────────────────────────────────────────────────────┤
│                │ 오늘의 업무                         [업무 만들기 ▾]   │
│ ● 홈           │ 9월 26일 토요일 · 프로젝트별 현지 일정               │
│   내 업무      │                                                       │
│   프로젝트     │ 내 담당 12     검토 대기 3     오늘 마감 2             │
│                │ ────────────────────────────────  ────────────────── │
│ 공용 공간      │ 지금 처리할 일                    오늘 일정           │
│   회의 일정    │ [전체] [내 담당] [승인 대기]       10:00 설계 검토     │
│   회의록       │ 승인 · 실험 설계 검토    A프로젝트 11:30 운영 회의     │
│   에이전트     │ 기한 · 검측 결과 등록    B프로젝트                    │
│                │ 담당 · 데이터 확인       A프로젝트 최근 문서           │
│ 즐겨찾기       │                                  실험 기록 · 20분 전 │
│   A 프로젝트   │ 진행 중인 프로젝트               검토 회의 · 1시간 전│
│   B 프로젝트   │ 이름         현황/근거   다음 기한                    │
│                │ A 프로젝트   주의 2건    09.28                        │
│ 운영           │ B 프로젝트   정상       10.02                        │
│   설정         │                                                       │
└────────────────┴───────────────────────────────────────────────────────┘
```

설계 결정:

- 최상단은 거대한 회사 소개/환영 히어로 대신 오늘의 업무 제목과 한 줄 메타다.
- 지표는 3개 내외의 낮은 한 줄 요약이며 각각 해당 필터 목록으로 이동한다. 실제 API가 없으면 숫자를 임의로 만들지 않는다.
- 우선순위 목록에서 프로젝트 이름·기한·행동을 한 행에서 확인한다. 승인 행을 열면 근거/변경 사항 inspector로 이어지고 목록에서 무맥락 일괄 승인하지 않는다.
- 프로젝트는 기본 행 목록, 필요 시 카드 보기 전환. 2개와 100개 프로젝트 모두 쓰기 위해 검색/상태 필터/즐겨찾기를 제공한다.
- 워크스페이스가 다른 항목을 집계하지 않는다. API 실패 위젯은 ‘0건’이 아니라 재시도 가능한 오류가 된다.
- 포털 우선 배치는 역할과 개인 선택에 따라 조정하되, capability 없는 승인 큐를 만들지 않는다. 개인이 숨겨도 필수 업무 자체는 내 업무에 남는다.

#### 6.2 프로젝트 작업 계획 — 표·간트·보드가 같은 작업을 보여준다

```text
┌────────────────┬───────────────────────────────────────────────────────┐
│ ← 홈           │ 워크스페이스 / A 프로젝트 / 작업 계획      검색       │
│ A 프로젝트 ▾   ├───────────────────────────────────────────────────────┤
│   개요         │ 작업 계획                 동기화됨   [작업 추가] [···]│
│ 계획과 실행    │ [표] [간트] [보드]   보기: 전체 ▾  필터  열  밀도     │
│ ● 작업 계획    │ ┌─────┬─────────────────┬──────┬──────┬──────────────┐ │
│   이슈         │ │     │ 작업명          │ 담당 │ 상태 │ 일정 / 진척  │ │
│   주간보고     │ ├─────┼─────────────────┼──────┼──────┼──────────────┤ │
│                │ │  ▾  │ 실험 준비       │ 팀 A │ 진행 │ …            │ │
│ 협업과 지식    │ │  □  │  샘플 기준 확정 │ 지윤 │ 검토 │ …            │ │
│   회의         │ │  □  │  데이터 검증    │ 민수 │ 진행 │ …            │ │
│   회의록       │ │  □  │  결과 정리      │ —    │ 대기 │ …            │ │
│   위키         │ └─────┴─────────────────┴──────┴──────┴──────────────┘ │
│                │ [2개 선택] 담당 변경 · 상태 변경 · 선택 해제          │
│ 팀과 자동화    │                                                       │
│   팀 구성      │           ← 작업 영역이 남은 높이 전체 사용 →        │
│   에이전트     │                                                       │
│ ────────────── │                                                       │
│ 프로젝트 설정  │ 126개 작업 · 필터 32개 · 마지막 동기화 10:32          │
└────────────────┴───────────────────────────────────────────────────────┘
```

- 주 행동과 보기 전환은 1280×720에서도 남는다. 설명/보조 메타부터 압축한다.
- 표/간트/보드 전환은 동일 필터·선택 항목을 가능한 범위에서 유지한다. 보드의 열은 프로젝트 상태 정의에서 파생한다.
- inspector는 상태·일정·담당·확장 필드·연결 문서·변경 이력 순으로 배치한다. 중요한 오류는 필드 옆, 저장 결과는 inspector 하단에 둔다.
- 컬럼 폭/순서/숨김·밀도는 개인별로 저장하고 관리자가 정한 필수 식별 열은 유지한다. 사용자 정의 필드는 동일 컬럼/상세 패턴을 쓴다.
- 완료 여부·업무 위험과 편집 동기화 상태는 서로 다른 표시 체계를 쓴다. 셀 저장 오류를 업무 지연 색상으로만 표시하지 않는다.
- 간트는 작업명/트리 열 고정+시간축 수평 이동. 작은 화면에서 전체 그리드를 축소하지 않는다.

#### 6.3 프로젝트 설정 — 변경 영향과 현재 적용값을 함께

```text
┌────────────────┬───────────────────────────────────────────────────────┐
│ 프로젝트 메뉴  │ 워크스페이스 / A 프로젝트 / 설정                     │
│                ├───────────────────────────────────────────────────────┤
│ ● 프로젝트 설정│ 프로젝트 설정                         설정 내 검색     │
│                │                                                       │
│                │ 일반        │ 근무 달력                                │
│                │ 모듈/메뉴   │ 이 프로젝트의 일정과 진척 계산에 적용    │
│                │ 팀/업무영역 │                                          │
│                │ 상태/승인   │ 시간대       [America/Los_Angeles ▾]      │
│                │ ● 달력      │ 근무 요일    월 화 수 목 금 [토] [일]    │
│                │ 지표/위험   │ 날짜 예외    [+ 예외 추가]                │
│                │ 추가 필드   │                                          │
│                │ 양식        │ 적용값 출처: 프로젝트 직접 설정          │
│                │ 알림        │ ─────────────────────────────────────── │
│                │ 연동        │ 변경 영향 미리보기                       │
│                │ 기록        │ 일정/진척 재계산 대상과 적용 시점 표시   │
│                │             │ 오류/충돌이 있으면 해당 필드로 이동       │
│                │             │                                          │
│                │             │ 변경 2개          [취소] [변경 내용 검토] │
└────────────────┴─────────────┴──────────────────────────────────────────┘
```

- 설정 내부 목차와 프로젝트 메뉴는 다른 위계로 보인다. 좁은 화면에서는 내부 목차를 셀렉트/드로어로 바꿔 본문을 확보한다.
- 각 값은 현재 적용값·출처(프로젝트/워크스페이스/제품 기본)·적용 시점·변경 권한을 표시한다. 상속을 해제하는 동작은 명시적이어야 한다.
- 생성 시 워크스페이스 기본값을 복사한 독립 설정은 ‘상속 중’으로 표시하지 않는다. 현재 동적 상속과 과거 초기값 출처를 구분하고, 실제 설정 엔진의 합성 계약과 같은 문구를 사용한다.
- 일반 값은 같은 화면에서 저장한다. 데이터 해석/권한/보존/채번처럼 영향이 큰 변경만 ‘변경 내용 검토’로 전후 차이와 영향 대상을 보여준다. 모든 작은 변경에 확인 모달을 강제하지 않는다.
- invalid/미설정/비활성/조회 실패를 다른 상태로 표시한다. disabled 이유와 설정으로 이동할 수 있는 경로를 제공한다.
- revision 충돌 시 내 편집값을 보존하고 서버 변경과 차이를 비교한다. 알리지 않고 덮어쓰지 않는다.
- 내보낸 설정에는 시크릿을 넣지 않는다. 원본 프로젝트 복사에서 데이터/멤버까지 복제되지 않음을 UI에 구체적으로 표시한다.

### 8. 반응형·입력·접근성·상태 설계

| 조건 | 결정 |
|---|---|
| ≥1280px | 전체 sidebar와 본문. inspector를 열 때 작업 최소 폭을 확보할 수 있을 때만 옆에 배치 |
| 1024~1279px | sidebar를 접을 수 있음. 보조 column을 아래로 이동. 장시간 표 편집의 가용 높이 우선 |
| 768~1023px | 탐색 drawer. 본문 한 열 중심, inspector overlay |
| <768px | 상단 범위 선택+메뉴, 본문 한 열. 작업 상세는 전체 화면. WBS는 이름/상태 고정+수평 이동 또는 업무 목록 보기 |
| 1280×720 | title/주 행동/필터를 유지. 보조 설명·장식·통계부터 줄이며 핵심 기능을 숨기지 않음 |
| 200% 확대 | 중요 조작이 클리핑되지 않고 목록/설정은 한 열로 흐름. 표만 통제된 수평 스크롤 허용 |

키보드: 메뉴→페이지 행동→필터→본문→inspector 순으로 이동한다. 현재 메뉴에는 aria-current, 보기 전환에는 선택 상태를 명시한다. focus indicator는 항상 보이고 modal/drawer 종료 시 트리거로 복귀한다. Esc로 편집 내용을 잃게 하면 안 되며 미저장 확인을 거친다.

상태 공통 규격:

- Loading: 실제 레이아웃 높이를 유지하는 skeleton. 아직 모르는 수치를 0으로 표시하지 않음.
- Empty: 무엇이 없는지 설명하고 권한에 맞는 첫 행동 하나 제공.
- Configuration required: 모듈 자체의 Empty와 구분. 부족한 설정과 관리자 이동 링크 표시.
- Disabled: 관리자 설정 화면에서만 비활성 사유와 켜기 경로. 일반 사용자는 해당 기능 미노출.
- Partial error: 실패한 위젯/행에 재시도. 정상 데이터까지 비우지 않음.
- Conflict: 내 값 보존, 최신값 비교, 재적용 선택.
- Offline/save pending: 편집 상태를 눈에 띄게 표시하고 저장 전 이동 정책을 적용.
- Permission changed: 행동 중단 후 현재 데이터/접근 권한 재확인. 단순 버튼 숨김으로 끝내지 않음.

### 9. 디자인의 설정 가능 범위

| 소유자 | 설정할 수 있는 항목 | 제한 |
|---|---|---|
| 워크스페이스 관리자 | 로고/제품 표시명, 검증된 accent, 홈 위젯 노출/순서, 허용 메뉴 명칭/순서 | 권한 밖 데이터/기능을 노출할 수 없음. 무제한 CSS 금지 |
| 프로젝트 관리자 | 활성 모듈, 업무 라벨, 개요 위젯, 기본 보기/공유 필터/필수 열 | 업무 정책·권한 변경과 단순 배치를 구분 |
| 개인 | 밝기 테마, 조밀도, sidebar 접힘, 개인 열/필터/즐겨찾기, 시작 화면 | 공유 데이터/필수 식별 정보의 의미를 변경하지 않음 |
| 제품 고정 | 핵심 focus/입력/오류 계약, 보안 경계, 기본 최소 글자·조작 크기 | 고객 설정으로 접근성·보안을 해제하지 않음 |

브랜드 색/보기 설정에는 preview, 저장, 기본값 복귀를 제공한다. 고객 설정이 없으면 이 부의 중립 디자인으로 작동하며 옛 고객 팔레트나 메뉴를 fallback하지 않는다.

### 10. 프론트엔드 구현 구조와 순서

기존 컴포넌트 재사용 여부를 실제 소비처와 계약으로 결정한다. 전부 새 라이브러리로 갈아엎지 않는다. 아래 이름은 신규 컴포넌트 제안이다.

1. **UI-0 기준선:** 현재 주요 화면·1280×720·모바일의 스크린샷과 핵심 동작을 기록한다. 실제 페이지/사용하지 않는 컴포넌트를 구분한다.
2. **UI-1 시각 토큰:** semantic token light/dark/고객 accent를 정의한다. 기존 CSS 토큰에서 새 토큰으로 옮기는 매핑표를 만든다. 토큰 재정의만으로 전체 재설계를 완료 처리하지 않는다.
3. **UI-2 셸/탐색:** WorkspaceShell, ProjectNavigation, ContextBreadcrumb, PageHeader, PageToolbar를 도입한다. AppLayout/Sidebar/HeaderChrome/ProjectNavigationContext를 이행한다. nav registry에서 desktop/mobile/search를 함께 파생한다.
4. **UI-3 대표 화면:** 포털, 작업 계획, 설정을 먼저 구현해 이 부의 3개 구도와 비교한다. 새 포털의 집계 API는 스코프·부분 실패·페이지네이션까지 설계한다.
5. **UI-4 공통 패턴:** WorkList, DataGridFrame, Inspector, DocumentLayout, SettingsLayout, StatusMessage 등을 만든다. 기존 WBS 엔진·Modal·폼 검증은 어댑터로 연결한다.
6. **UI-5 전체 화면 적용:** §7 적용표 순서대로 현재 page를 이행한다. 사용하지 않는 ProjectTabs를 실제 shell로 가정하지 말고 삭제/대체 여부를 확인한다.
7. **UI-6 회귀/실측:** 반응형·키보드·전체 링크·브라우저 실제 layout·출력물·권한/모듈 조합을 검증한다.

특별 위험:

- globals.css의 unlayered 반응형 display 안전망을 무시하지 않는다. `group-hover:flex`, `data-[state=open]:hidden` 등은 기존 규칙과 충돌할 수 있다. 별도 scoped CSS나 상태별 명시 렌더링으로 처리하고, 안전망 제거는 근거 있는 독립 작업으로 한다.
- PageHero에 actions를 새로 넘기는 것으로 끝내지 않는다. 기존 호출부에서 표시되지 않던 props와 실제 toolbar를 대조해 중복/유실 없이 PageHeader로 옮긴다.
- 작업표의 column virtualization·sticky·portal overlay·drag hit target과 새 shell 높이를 함께 확인한다.
- 페이지 이동 시 sidebar/검색/알림 때문에 기존 API 호출이 늘어나지 않게 한다. portal 위젯마다 전체 WBS를 다시 가져오는 N+1 집계를 만들지 않는다.
- 앱/레이아웃/UI 위험 파일은 `ui/` 브랜치와 로컬 눈확인 규칙을 따른다. 기존 사용자 작업을 덮어쓰지 않는다. 현재 원격 Preview가 없다는 CLAUDE.md 조건을 지킨다.

### 11. 디자인 완료 판정

기능 테스트 통과와 별도로 다음 증거가 있어야 한다.

1. 포털/작업 계획/설정 및 전체 화면군의 라이트·다크 스크린샷. 1440×900, 1280×720, 768px, 390px를 포함한다.
2. 워크스페이스/프로젝트 문맥이 전환 후 오인되지 않고, 메뉴/검색/직접 링크가 같은 권한·모듈 판정을 따른다.
3. 모든 화면에서 주 행동·제목·필터가 실사용 크기에서 접근 가능하다. 숨겨진 action props나 화면 아래 가려진 저장 버튼이 없다.
4. 색상 교체뿐 아니라 §6의 정보 구조와 §7의 화면 유형 차이가 실제 구현에서 드러난다.
5. 긴 한글/영문 이름, 많은 메뉴/프로젝트/열, 0건/실패/미설정, 고객 accent 변경을 확인한다.
6. 키보드만으로 탐색·편집·상세 열기·닫기·저장을 수행하고 focus가 복원된다. 터치에서 hover 전용 액션이 없다.
7. WBS 편집/이월/승인/업로드/설정 충돌 등 핵심 업무 회귀가 없다. 1만 행 합성 WBS와 많은 프로젝트 목록으로 불필요한 전체 렌더를 확인한다. 성능 목표값은 UI-0 실측 후 명시하며 측정 없이 ‘빨라짐’으로 보고하지 않는다.
8. 명도 대비는 실제 상태 조합에서 본문4.5:1 이상, 조작 식별/포커스3:1 이상을 내부 목표로 확인한다. 대비를 만족한 단색 토큰이 있다는 이유로 전체 화면 검증을 생략하지 않는다.

최종 구조 점검에서 현재 `src/app/**/page.tsx` 31개를 열거해 위 적용표와 대조했다. 루트 리디렉션·로그인·초대·외부 공유도 포함한다. 이 수는 해당 시점의 라우트 수이며, 이후 새 화면이 추가되면 적용표도 갱신한다. 각 라우트의 loading/error/not-found 상태와 전역 AI/알림 패널은 해당 화면군의 반응형·포커스 검증에 함께 포함한다.

**이번 턴의 완료 범위는 디자인 검증과 이 설계안 작성이다. 제품 UI 구현·브라우저 시각 검수·고해상도 시안 제작까지 완료한 것은 아니다.** Claude Code 구현 보고에는 UI-0~6 단계별 결과와 아직 검수하지 못한 화면을 명시한다. 설계 문서는 이 단일 파일을 계속 사용한다.

## 제6부 — 상용 제품 수준의 상세 디자인

### 1. 설계 책임과 최종 방향

추가 전문 역할 에이전트 3명을 호출했다. **commercial_ux_designer**는 정보 구조·첫 사용·반복 업무, **commercial_visual_designer**는 시각 체계·브랜드·컴포넌트 상태, **commercial_interaction_designer**는 데이터 편집·접근성·협업·오류 복구를 담당했다. 루트 에이전트가 코드 근거를 재확인하고 상충하는 제안을 조정해 아래 단일 설계로 확정했다. 이들은 디자인 전문 역할로 작업한 에이전트이며 실사용자 평가를 대체하지 않는다.

제품 인상은 **차분하고 정밀한 업무 도구**로 정한다. 밝은 중립 배경, 분명한 타이포그래피, 제한된 cobalt 강조색, 일관된 정렬이 기본이다. 포털은 해야 할 일을 발견하기 쉽게, 작업 화면은 많은 정보를 빠르게 다루기 쉽게, 설정은 효과와 출처를 이해하기 쉽게 설계한다. 모든 화면에 같은 hero·KPI·카드 묶음을 반복하지 않는다.

‘상용 수준’의 기준은 다음 여섯 가지다: 첫 업무를 도움 없이 시작할 수 있음, 현재 프로젝트와 권한을 혼동하지 않음, 반복 업무가 빠름, 실패해도 입력과 맥락을 복구함, 긴 데이터·작은 화면·키보드에서도 완수 가능함, 고객 설정이 달라도 같은 완성도를 유지함. 아래 P0는 이 디자인 범위의 출시 차단 항목이고 P1은 후속 구현 우선순위다. 앞선 적대적 검증의 심각도 등급과 별개다.

프로젝트 전환 fallback 예: “이 프로젝트에서는 작업 계획을 사용하지 않아 개요를 열었습니다.” 전역 페이지에서는 이전 프로젝트가 여전히 선택된 것처럼 표시하지 않는다. 직접 링크로 들어올 때도 URL·헤더·메뉴·권한 판정의 프로젝트가 일치해야 한다.

포털의 기한은 단순 색만 사용하지 않고 날짜·지연 기간을 같이 쓴다. 알림 배지·검토 대기·긴급 위험을 모두 같은 빨간 점으로 표현하지 않는다. 모든 화면의 대표 행동은 한 개를 우선 강조하되, 저장/취소·승인/반려처럼 업무상 필요한 짝은 역할이 구분되도록 유지한다.

### 5. 상용 시각 체계: 정확한 토큰·밀도·브랜드 규칙

**토큰 계층:** 원색 팔레트→의미 토큰→컴포넌트 토큰으로 연결한다. 예: `cobalt.600 → action.primary.bg → button.primary.bg`. 화면 컴포넌트가 고객 HEX나 원색을 직접 참조하지 않는다. 기존 canvas/surface/ink/brand는 이행 어댑터로 두고, `line` 하나를 장식 경계·입력 경계·선택·포커스에 공용하지 않는다.

| 추가·보정 의미 토큰 | 라이트 기본값 | 다크 기본값 | 사용 규칙 |
|---|---|---|---|
| text.muted | `#606E82` | `#96A5BA` | 보조 정보, 중요한 설명은 secondary/primary |
| border.input | `#7B8798` | `#718198` | 입력 경계를 식별해야 하는 곳. 장식 구분선과 별도 |
| border.focus | `#315CDB` | `#A8BDFF` | 2px 표시+필요한 offset. 배경별 식별 검증 |
| action.primary.hover | `#274CC5` | `#A8BDFF` | 기본 foreground와 조합 검사 |
| action.primary.pressed | `#2142AB` | `#7799F7` | 눌림 피드백, 상태색으로 전용하지 않음 |
| surface.hover | `#F0F3F8` | `#222B38` | hover 때 콘텐츠 이동 없음 |
| surface.selected | `#EDF2FF` | `#26375E` | 체크·선택 표시를 함께 제공 |

| surface.disabled | `#EDF0F4` | `#232A35` | 부모 opacity로 텍스트까지 일괄 희석하지 않음 |

**대비 보정 근거:** 기존 muted `#677489`는 white에서4.73이나 canvas `#F5F7FA`에서4.41, subtle `#EEF2F7`에서4.21이었다. 따라서 `#606E82`로 보정했고 같은 순서로5.19/4.83/4.61이다. 입력 경계 `#7B8798`은 white3.65/canvas3.40, 다크 경계 `#718198`/surface `#191F29`는4.17이다. 로컬 계산으로 상대 명도 비율을 확인했으며 실제 렌더·접근성 인증 결과가 아니다. hover·selected·오류·고객 accent에서는 다시 검증한다.

**문자 규격:** 제목24/32px·600, 모바일 제목22/30px·600, 섹션16/24px·600, 본문14/22px·400, 기본 메뉴·버튼·입력14/20px·400~500, 보조 메타12/18px·400, KPI28/34px·600, 문서16/26px·400. 제5부의 메뉴13px는 조밀 데스크톱 모드에서만 허용한다. 10px 주요 레이블·한글 uppercase/과도한 자간을 제거한다. 숫자는 tabular-nums, 수치 열은 우측 정렬, 날짜·단위는 일관된 위치에 둔다. 한글 폰트 대체 시에도 줄바꿈·높이를 검수한다.

**밀도 규격:** 간격4/8/12/16/24/32/48px, 버튼·입력 기본36px, 일반 데이터 행40px, 조밀 행32px, 포털 업무 행56px. 터치는 조작 영역44px 이상과 충분한 실제 행 간격을 함께 확보하며 투명 hit area가 서로 겹치지 않게 한다. 조밀 모드는 표의 행·패딩만 줄이고 오류·설명·모달 전체를 축소하지 않는다. 기존 sidebar232/64·header56·inspector400 기본은 유지한다.

**고객 브랜딩:** accent는 주 행동·링크·선택에 적용하고 위험/완료 의미 색과 분리한다. 자유 입력을 제공한다면 bg/fg/hover/pressed/focus 세트를 파생·검증한다. 실패 시 문제가 되는 샘플을 보여주고 마지막 유효 설정을 유지한다. 로고는136×28px, 접힘28×28px 박스에 contain. 밝기별 로고가 없으면 중립 배경을 둔다. 임의 CSS·JS를 설정값으로 실행하지 않는다.

**상태와 차트:** 업무 상태는 icon+label+연한 badge, 위험은 사유+warning/danger, 선택은 check+선택 배경, 저장은 중립 spinner/문구로 구분한다. 차트는 단위·기간·기준일·집계 정책을 가까이 표시하고 결측을0으로 잇지 않는다. 범주색은 엔티티 ID에 안정 매핑한다. 팀 구분색에 위험 의미를 부여하지 않는다. 선·마커·패턴·데이터 표로 색 외 구분을 제공한다. 간트 ‘오늘’ 선은 위험과 다른 토큰·레이블을 쓴다.

**모션:** hover/focus100~120ms, 메뉴120~160ms, inspector160~200ms. 셀 이동은 즉시 반영하고 장식 transform으로 흔들지 않는다. reduced-motion에서는 비필수 이동을 없애되 저장·실패 피드백은 남긴다. 셀 저장마다 성공 toast를 쌓지 않고 해당 편집 영역에서 상태를 갱신한다.

### 7. 저장·충돌·중단 복구의 공통 상태 머신 — P0

업무 상태는 프로젝트 정책, 편집 상태는 공통 편집 엔진, 연결 상태는 네트워크 계층에서 각각 관리한다. 실시간 채널이 연결됐다는 이유로 ‘저장됨’으로 표시하지 않는다.

| 현재→다음 | 이벤트 | 보존 데이터·가능 행동 |
|---|---|---|
| Synced→Editing | 입력 시작 | 원값·base revision·draft·대상 ID 보관 |
| Editing→Invalid | 입력 검증 실패 | draft 유지, 필드 오류 표시, 같은 필드에서 수정 |
| Editing/Invalid→Saving | 유효 입력 제출 | command ID, 중복 제출 차단, 해당 묶음만 pending |
| Saving→Synced | 서버 성공·새 revision 확인 | 기준값 갱신, 성공한 변경의 undo 기록, 마지막 저장 시각 |
| Saving→OutcomeUnknown | 응답 전 연결 단절 | draft와 command ID 유지, ‘저장 결과 확인 중’, 결과 조회 |
| OutcomeUnknown→Synced/Failed/Conflict | 결과 조회 완료 | 확인한 서버 결과에 따라 분기, 무조건 재전송하지 않음 |
| Saving→Failed | 확정적 저장 실패 | 입력 유지, 원인·재시도·취소 제공 |
| Editing/Saving→Conflict | 원격 변경·revision 불일치 | 내 값/원값/최신 값 비교, 최신 revision으로 재검증 후 재적용 |
| Editing→Synced | 명시적 편집 취소 | 해당 세션만 원복, 다른 성공 변경 보존 |
| 임의→PermissionChanged | 권한 회수·모듈 차단 | mutation 중지, 범위 재조회, 허용되지 않는 데이터 제거 |

`Offline/Connecting/Connected`는 별도 연결 상태다. 연결이 회복되어도 초안이 남으면 저장 완료가 아니다. 헤더의 ‘동기화됨’은 현재 범위의 미저장·실패·대기 명령이 없고 서버 상태를 확인한 경우에만 표시한다.

명시 저장 폼은 **저장/변경 버리기/계속 편집**으로 이탈을 처리한다. ‘초안으로 남기기’는 실제 저장소가 구현된 경우에만 추가한다. 셀 편집의 Esc는 그 셀 세션만 취소한다. 내부 날짜 선택기의 첫 Esc는 선택기만 닫고, 이후 Esc에 상위 편집/모달 계약을 적용한다. 저장 중 닫더라도 요청 결과와 복구 경로를 잃지 않게 mutation 상태를 모달 밖에 유지한다.

로컬 초안은 사용자·워크스페이스·프로젝트·항목·base revision으로 격리하고 보존기간·로그아웃·권한 회수 정리 정책을 정의한다. 비밀값은 저장하지 않는다. 지원되는 필드만 오프라인 초안을 허용하고 서버 업무 명령은 연결 없이 실행 완료로 표시하지 않는다. 개인정보·기밀의 로컬 보관 허용 여부는 워크스페이스 정책으로 제어하되 보안 제한을 개인 설정이 완화할 수 없다.

공통 서버 응답은 최소 `commandId`, 결과 종류, 성공 시 `revision`, 실패 시 필드 오류/재시도 가능 여부, 충돌 시 권한 내 최신값을 표현해야 한다. 결과가 불명확한 요청의 조회·중복 방지는 저장/승인/가져오기 서버 계약까지 구현한다. 프런트 토스트만 바꾸어 완료 처리하지 않는다.

### 8. 복잡한 업무 화면의 조작 명세

**표·시트:** 탐색 모드의 방향키는 셀 이동, Shift+방향키는 범위 선택, Enter/F2는 편집, Tab은 다음 외부 영역으로 이동한다. 편집 모드의 방향키는 텍스트 커서 이동, 단일행 Enter는 커밋, 다중행 Enter는 줄바꿈·수정키+Enter는 커밋이다. Tab/Shift+Tab은 유효한 입력을 저장하고 다음/이전 편집 가능 셀로 이동한다. 검증 실패 시 현재 필드에 머문다. 한글 조합 중 Enter/Esc/방향키를 업무 단축키로 처리하지 않는다. 기존 weekly 동작과 다른 부분은 공통 키보드 도움말과 함께 명시적으로 이행한다.

행 체크 선택과 셀 범위 선택은 다른 상태다. 셀 선택만으로 행 삭제를 활성화하지 않는다. focus는 배열 index 대신 `itemId+fieldId`로 유지하고 가상화·정렬·원격 업데이트 뒤 다른 작업으로 이동하지 않는다. 네이티브 텍스트 undo와 그리드 배치 undo는 편집 모드로 구분한다.

**대량 변경·붙여넣기:** ‘선택한25개’와 ‘현재 검색 결과1,240개 전체’는 명시적 선택이다. 전체 선택은 서버 대상 snapshot 또는 동등한 일관성 계약으로 실행 중 추가된 항목의 혼입을 막는다. 필드의 ‘혼합’은 빈값과 구별하며 변경하지 않음/값 지정/값 지우기를 제공한다. 필수 필드는 지우지 못한다. 숨긴 열·필터 제외 행에 몰래 붙여넣지 않는다. 미리보기에 대상·읽기 전용·형식 오류를 표시한다. 종속 변경은 원자적 처리, 독립 변경은 항목별 처리 등 보장 수준을 API에서 정한다. 결과 패널은 성공/충돌/권한 없음/검증 실패를 남기고 실패 건만 재시도한다.

**Undo:** 서버가 성공을 확인한 변경만 이력에 포함한다. 역변경도 최신 revision과 정책을 검사한다. 이후 다른 사용자의 변경을 과거 값으로 덮어쓰지 않는다. 일부만 되돌릴 수 있으면 항목별 결과와 남은 이력을 일치시킨다. 외부 발송·승인·파괴적 가져오기는 실제 역명령이 없으면 Undo를 제공하지 않는다.

**간트:** 드래그 중 원래 일정은 점선, 변경 예정 일정은 실선으로 표시한다. 시작/종료·기간 변화·달력·시간대를 보여주고 손을 놓으면 선후행 영향과 오류를 검토한다. 전파 정책 없이 후속 작업을 자동 이동하지 않는다. 확대/축소는 선택 작업 또는 중앙 날짜를 기준으로 유지한다. 오늘로 이동/선택 작업으로 이동을 구분한다. 날짜 입력·관계 검색 폼으로 드래그 없는 동일 업무를 지원한다.

**보드:** 그룹 기준과 업무 전이를 분리한다. 담당자별 그룹에서 이동은 담당자 변경일 수 있고 읽기 전용 그룹은 이동을 허용하지 않는다. 진척 구간을 상태 전이로 추정하지 않는다. 허용 목적지·불가 사유·필수 입력은 유효 정책에서 가져온다. 카드의 이동 메뉴가 드래그와 같은 검증을 사용한다. 수동 정렬이 가능한 보기에서만 순서 변경을 제공한다. 실패하면 현재 위치와 의도한 위치를 보존한다.

**문서·첨부:** 열람 버전·최신 여부·수정자·업무상 승인 상태를 구분한다. 이전 버전에는 ‘v3 열람 중·현재v5’를 표시한다. 초안 저장은 게시/승인을 의미하지 않는다. 발행 개념이 있는 모듈만 게시 행동을 제공한다. 비교는 제목·본문·메타·첨부를 포함한다. 첨부는 전송 중→처리 중→사용 가능/실패를 구분한다.

**승인:** 큐의 기본 행동은 검토다. 검토 화면에 제출 버전·제출자·변경 요약·근거·필수 조건·처리 영향을 표시한다. 요청에 검토한 revision과 command ID를 포함한다. 재제출·타인 처리·권한 변경 시 오래된 자료로 승인하지 않고 재검토한다. 반려 사유 필수 여부·일괄 승인 허용은 정책에서 읽는다. ‘처리 완료·목록 갱신 실패’를 승인 실패와 구별한다.

**실시간 변경:** presence는 잠금이나 저장 보증이 아니다. 편집 중인 필드의 원격 값은 draft를 덮지 않고 충돌 후보로 보관한다. 정렬값이 바뀌어도 입력 중 행을 즉시 화면 밖으로 제거하지 않는다. 새 항목은 묶어서 안내하고 읽고 있는 위치를 유지한다. 재연결 후 최신 snapshot을 확인한다. live region은 변경을 묶어 읽고 모든 셀 이벤트를 연속 낭독하지 않는다.

### 9. 모바일·접근성·제품 문구

390px에서는 오늘 업무 확인, 상세 읽기, 상태 변경, 검토, 짧은 작성과 저장을 완수할 수 있어야 한다. 복잡한 표는 자기 viewport 안에서 가로 스크롤하고 선택 항목의 단일 필드/폼 편집을 제공한다. 간트는 개요·날짜 폼으로, inspector는 전체 화면 상세로 전환한다. 정밀 대량 편집이 데스크톱 전용이면 범위와 대체 경로를 표시한다. 단순히 버튼을 숨기고 모바일 지원으로 판정하지 않는다.

가상 키보드가 열린 경우에도 저장/취소와 오류 위치에 접근 가능해야 한다. hover 전용 동작은 메뉴나 항상 접근 가능한 버튼으로 대체한다. 모달 최상위만 focus를 소유하고 닫을 때 원래 trigger, 사라졌다면 인접 유효 행 또는 목록 제목으로 복원한다. 비모달 inspector는 본문 조작을 허용한다. 200% 확대에서 필수 정보와 행동이 사라지지 않는다.

| 상황 | 기본 제품 문구 | 제공할 행동 |
|---|---|---|
| 저장 실패 | “저장하지 못했습니다. 입력 내용은 유지됩니다.” | 다시 시도·계속 편집. 복사가 허용된 콘텐츠에만 복사 |
| 충돌 | “다른 사용자가 이 항목을 변경했습니다. 내 변경과 최신 내용을 확인하세요.” | 비교·최신 내용 사용·선택 필드 재적용 |
| 결과 불명확 | “저장 결과를 확인하고 있습니다.” | 상태 확인, 확인 전 중복 제출 차단 |
| 필터0건 | “현재 조건에 맞는 항목이 없습니다.” | 적용 조건 표시·필터 지우기 |
| 미설정 | “이 기능을 사용하려면 먼저 필요한 설정을 확인하세요.” | 권한자에게만 설정 이동, 나머지는 필요한 담당 안내 |
| 부분 처리 | “12개 중10개를 변경했습니다. 2개는 확인이 필요합니다.” | 실패 항목과 이유·해당 항목만 재시도 |
| 연결 끊김 | “연결이 끊겼습니다. 마지막 확인: 14:32.” | 재연결·실제 허용된 초안 행동 |

위 문구의 입력 보존·복구 행동은 실제 구현과 일치할 때만 사용한다. 시간은 유효 locale/시간대와 날짜 경계를 적용한다. 사용자에게 기술 stack이나 내부 구현 설명을 노출하지 않고 지원용 참조 ID를 제공한다.

### 10. 디자인도 설정으로 제어하는 범위와 계약

‘설정 가능’은 화면에 토글이 있다는 뜻이 아니다. 저장·유효성 검증·상속 해석·실제 소비처·오류 표시·기본값 복귀가 연결되어야 한다. 아래 키는 신규 설계 예시이며 현재 구현된 스키마로 오인하지 않는다. 기존 설정 저장소에 동일 개념이 있으면 재사용한다.

| 설정 범주·예시 | 소유 범위 | 실제 소비처·검증 |
|---|---|---|
| `appearance.logo`, `appearance.accentPalette` | 워크스페이스 | shell·로그인 문맥·버튼·링크·브랜드 preview. 색 조합 검증 |
| `navigation.labels/order`, `home.widgets` | 워크스페이스 기본→허용된 프로젝트 override | desktop/mobile/menu search/breadcrumb 공통 registry. 활성 모듈·권한 필터 |
| `views.default`, `views.shared` | 프로젝트 | 표·간트·보드·목록의 열/정렬/그룹/필터. field ID 참조와 소유권 검증 |
| `preferences.theme/density/startPage`, `views.personal` | 개인+문맥 | 시스템 테마보다 명시 선택 우선. 접근 가능한 시작 화면인지 검사 |
| `terminology`, `fields`, `workflow`, `calendar`, `approval` | 앞선 업무 설정 모델 | 라벨·검증·전이·필수 입력·날짜·승인을 공통 resolved config에서 읽음 |
| `draftPolicy.allowed/retention` | 워크스페이스 보안 정책 | 로컬 초안 저장·정리. 비밀값 제외·사용자 격리·권한 회수 |

기본값→워크스페이스→허용된 프로젝트 override→개인 표현 설정 순서로 해석하되, 개인 설정은 업무 의미·권한·필수 필드를 변경하지 않는다. 예를 들어 개인이 공유 보기의 열을 숨겨도 필수 입력 검증은 유지한다. 메뉴 숨김은 모듈 비활성화나 권한 회수와 다르다. source·effective value·override 여부를 설정 UI에 표시한다.

모든 설정 문서에는 `schemaVersion`, `revision`, 적용 범위, 안정적인 ID 참조, 마이그레이션 전략을 둔다. 상태/필드 삭제로 깨진 저장 보기는 영향을 안내하고 유효한 부분을 복구하며 예전 고객 체계로 fallback하지 않는다. 명도 대비·focus 계약·최소 터치 크기·권한 경계는 고객이 해제하는 옵션으로 만들지 않는다. 무제한 HTML/CSS/실행 코드 설정 대신 검증된 레이아웃/위젯/필드 registry를 제공한다.

설정화 검증은 서로 다른 업무 체계를 가진 합성 프로젝트 최소2개로 수행한다. 상태 수·이름·필수 확장필드·근무요일·시간대·승인 정책·메뉴 순서를 다르게 설정하고 소스 변경 없이 포털부터 출력까지 반영되는지 확인한다. 제조업 구분, PMO, 서울 시간, 특정 개발 단계가 숨은 fallback으로 나타나면 실패다. 실제 원본 고객 데이터는 사용하지 않는다.

COM-2의 서버 계약과 COM-3의 shell/검색 스코프를 먼저 정한 후 의존 화면을 구현한다. COM-5를 생략한 초기 배포라면 ‘상용 설계 전체 완료’로 표현하지 않고 제공 기능 범위를 명시한다. 대표3화면만 예쁘게 바꾸고 승인·공유·로그인·실패 화면을 남겨두면 전체 디자인 완료가 아니다.

### 12. 종단 사용성 평가와 출시 수용 기준

**J1 첫 관리자:** 초대→역할 확인→프로젝트 생성→작업/회의록만 활성화→용어·달력 확인→정형20행 파일 매핑→오류1개 수정→가져오기→담당 지정→다음 로그인에서 준비 이어하기. 사전 로그인·정상 서버 조건에서10분 내 첫 유효 업무 생성, 형성평가5명 중4명 도움 없이 성공을 목표로 한다. 현실의 모든 파일에 대한 처리시간 보장은 아니다.

**J2 반복 사용자:** 포털에서 검토 대기 열기→근거 확인·처리→기존 목록 스크롤/필터 복원→다른 프로젝트의 같은 작업 보기→12개 담당 변경→10개 성공/2개 실패 확인→실패만 처리. 검토 진입2회 이내 조작, 참여자 전원의 현재 프로젝트·부분 처리 결과 이해를 목표로 한다. 근거 확인을 생략해 클릭 수를 줄이지 않는다.

**J3 고급 관리자:** 설정 검색→근무요일 필드→상속 출처 확인→영향 미리보기→다른 관리자 변경과 충돌→필드별 재적용→응답 유실 결과 확인→허용된 초안 복구→변경 기록 확인. 데이터 손실0건·무통보 덮어쓰기0건, 적용됨/미적용/확인 중을 모든 평가자가 구분하는 것을 목표로 한다. 미구현 영향 계산을 가짜 숫자로 채워 시연하지 않는다.

형성평가는 관리자·일반 참여자·여러 프로젝트 담당자 각5명을 권장하며 시장 대표성을 증명하는 표본이 아니다. 도움 없는 성공률·첫 결과 시간·잘못된 프로젝트 변경 시도·설정 출처 이해·저장 상태 이해·복구 성공을 기록한다. ‘세련돼 보이는가’와 함께 ‘지금 무엇이 저장됐고 어느 프로젝트인가’를 설명하게 한다. 사용성 계측 도구 도입을 이유로 고객 본문·검색어를 외부에 자동 전송하지 않는다.

**이번 추가 작업의 완료 범위:** 전문 디자이너 역할 에이전트3명의 검토·제안, 코드 근거 재대조, 색상 대비 계산, 상용 제품 상세 디자인과 구현·검증 계약을 이 한 파일에 통합했다. 제품 소스 수정, 실제 렌더 시안, 브라우저/스크린리더/터치 검수, 사용자 평가는 아직 수행하지 않았다. 따라서 현재 판정은 ‘상용 수준을 목표로 하는 구현 가능한 설계 작성 완료’이며 ‘제품이 이미 상용 수준으로 검증됨’은 아니다.

### 13. 후속 구현 — D-Flow 아이콘 포털 선적용

사용자의 후속 요청으로 **아이콘에 한정해 실제 제품 코드에 반영했다.** 앞선 전체 디자인 설계의 구현 완료와는 구분한다.

- 디자인: 기울어진 민트 리본과 열린 흰색 D 곡선을 결합한 흐름 모노그램. 코발트 블루의 얕은 그라데이션, 둥근 사각 실루엣. 외부 폰트·이미지 서비스 없이 확대 가능한64×64 SVG.
- 원본: `public/brand/dflow-flow.svg`. 색상은 브랜드 자산 내부에만 위치하며 고객 업무 규칙과 무관하다.
- 적용: `src/components/ui/BrandMark.tsx`가 `/projects`에서 새 아이콘을 선택한다. `src/app/(app)/projects/page.tsx` 상단에도 같은 아이콘을 배치해 작은 화면에서 기존 헤더 로고가 숨겨져도 확인할 수 있게 했다. 워드마크·제품명·포털 업무 동작은 변경하지 않았다.
- 설정: `src/lib/branding.ts`의 `BRAND.portalIcon`, 환경변수 `NEXT_PUBLIC_BRAND_PORTAL_ICON=flow|monogram`. 기본은 flow, monogram 선택 시 기존 제품명 첫 글자 마크. `.env.local.example`에 명시했으며 빌드 시 적용되는 설정이다. 워크스페이스 런타임 설정 화면 구현을 의미하지 않는다.
- 범위: 로그인·초대·외부 공유·프로젝트 상세·파비콘에는 확장하지 않았다. 전체 브랜드 변경은 이번 포털 선적용을 확인한 후 별도 수행한다.
- 검증: SVG 래스터 렌더로 실루엣·색·여백 확인, 변경 소스 ESLint 및 TypeScript 검사 통과, 기존 브랜드/반응형 안전망 테스트2파일13건 통과. 브라우저의 로컬 포털 접근은 보안 정책에서 거부되어 실제 페이지 눈확인은 미완료다. 접근을 우회하지 않았다.
- 작업 제약: `.git` 쓰기 제한으로 새 UI 브랜치 생성이 실패했다. 별도 브랜치를 요구하는 `src/components/app/*`·전역 CSS·layout은 수정하지 않고 기존 브랜치의 위 파일에 미커밋 변경으로 남겼다. 병렬 작업의 마이그레이션·RLS 테스트 파일은 건드리지 않았다.
