# Mac mini 2대 + Windows PC 2대로 D-Flow 에이전트 오피스 테스트하기

작성일: 2026-10-23. 대상: 혼자 PC 네 대를 운영하며 WBS에 적힌 개발 작업을 AI에게 맡겨 보고 싶은 사용자.

**처음에는 Mac mini 한 대에서 작업 하나만 끝내세요.** 웹에서 위임하고, PC에서 개발하고, 웹에서 승인하는 흐름이 확인되면 나머지 세 대를 붙입니다.

이 안내서는 현재 D-Flow 저장소에 들어 있는 **Claude Code용 dflow-kit**을 기준으로 합니다. 개발할 코드는 별도 실습 저장소에 두고, WBS와 승인 상태는 [D-Flow 운영 서비스](https://d-flow-eight.vercel.app)에서 관리합니다. D-Flow 서비스 자체의 코드를 바꾸는 실습은 아닙니다.

함께 제공하는 파일: [실습용 WBS — agent-office-demo-wbs.md](./agent-office-demo-wbs.md). 이 파일을 그대로 업로드하면 준비된 작업 5건을 사용할 수 있습니다.

**후속 작업 메모:** 웹에 `에이전트 오피스 실습` 프로젝트를 생성했습니다. 프로젝트 ID와 최신 등록 상태는 [다른 PC용 연결 메모](./agent-office-pc-handoff.md)에 기록했습니다. 이미 만든 프로젝트를 사용한다면 아래 3-1의 프로젝트 생성은 반복하지 않습니다.

### 자주 쓰는 메뉴만 먼저 보기

| 할 일 | 누르는 순서 |
|---|---|
| 실습 프로젝트 만들기 | 워크스페이스 → 전체 프로젝트 → 새 프로젝트 시작 |
| 에이전트 기능 켜기 | 프로젝트 → 설정 → 기능·메뉴 항목 → 에이전트 → 변경 내용 검토 → 변경 저장 |
| 개발 계정 만들기 | 워크스페이스 → 운영 → 멤버·초대 → 계정 추가 |
| 프로젝트 권한 확인 | 프로젝트 → 팀 구성 → 명단 · 권한 |
| PC 연결 토큰 발급 | 해당 개발 계정 로그인 → 오른쪽 위 계정 메뉴 → 내 계정 → 개인 액세스 토큰(PAT) |
| WBS 올리기 | 프로젝트 → 설정 → 일반 → WBS 데이터 가져오기 · 내보내기 → 가져오기 마법사 열기 |
| 담당자 정하기 | 작업 계획 → 작업 이름 → 담당·단계 → 담당자 |
| AI에게 맡기기 | 팀 → 에이전트 → 위임·승인 → 작업의 위임 체크 |
| 진행 보기 | 팀 → 에이전트 → 에이전트 오피스 → 전체 |
| 결과 승인 | 에이전트 → 위임·승인 → 승인 대기 → 보고 확인 → 승인 |

## 1. 먼저 알아둘 것 세 가지

1. **에이전트 오피스는 현황판입니다.** 웹에서 위임 체크를 해도 꺼진 PC나 AI 프로그램을 원격으로 켜 주지는 않습니다. 각 PC에서 개발 세션을 실행해야 합니다.
2. **PC 네 대가 같은 개발 저장소를 각각 복제해 사용합니다.** 결과는 GitHub를 통해 모읍니다. 공유 폴더의 코드 한 벌을 네 대가 동시에 수정하는 방식으로 시작하지 마세요.
3. **완료 보고, 웹 승인, 코드 합치기는 서로 다릅니다.** AI가 보고한 뒤 사람이 결과를 확인해 승인하고, 그다음 작업 브랜치의 코드를 기본 브랜치로 합칩니다. 코드 합치기는 뒤에서 `/dflow-merge`로 설명합니다.

```text
내가 D-Flow 웹에서 WBS 작성·담당자 배정·위임
                 ↓
각 PC의 Claude Code가 자기 담당 작업 개발
                 ↓
D-Flow 에이전트 오피스에서 진행 상태 확인
                 ↓
내가 웹에서 완료 보고 승인 또는 반려
                 ↓
승인된 코드를 GitHub 기본 브랜치에 합치기
```

**이 실습에는 D-Flow 서버나 Supabase를 네 대에 설치할 필요가 없습니다.** 네 대 모두 같은 운영 웹 주소에 연결하면 됩니다. 실습 코드도 데이터베이스 없이 실행되는 작은 Node.js 함수로 준비했습니다.

## 2. PC와 계정을 이렇게 나누세요

### PC 역할

| 장비 | 이름표 예시 | 처음 할 일 | 확장 후 할 일 |
|---|---|---|---|
| Mac mini 1 | `macmini-1` | 웹에서 설정하고 개발 1건 시험 | 관리자 웹 화면 + 개발자 1 |
| Mac mini 2 | `macmini-2` | 첫 시험이 끝날 때까지 준비만 | 개발자 2 |
| Windows PC 1 | `winpc-1` | WSL2 설치와 연결 준비 | 개발자 3 |
| Windows PC 2 | `winpc-2` | WSL2 설치와 연결 준비 | 개발자 4 |

**처음 동시 작업 수는 PC당 1건, 총 4건으로 제한합니다.** 한 PC에서도 여러 AI를 실행할 수 있지만, 첫 시험부터 늘리면 어느 PC의 문제인지 찾기 어려워집니다.

### D-Flow 계정은 관리자 1개 + 개발 계정 4개

| 계정의 표시 이름 예시 | 사용하는 곳 | 워크스페이스 역할 | 실습 프로젝트 권한 |
|---|---|---|---|
| 내 기존 계정 | 웹 설정·WBS 작성·승인 | 관리자 | 관리자 권한 사용 |
| 개발-Mac1 | Mac mini 1의 개발 세션 | 멤버 | 멤버 |
| 개발-Mac2 | Mac mini 2의 개발 세션 | 멤버 | 멤버 |
| 개발-Win1 | Windows PC 1의 개발 세션 | 멤버 | 멤버 |
| 개발-Win2 | Windows PC 2의 개발 세션 | 멤버 | 멤버 |

사람은 한 명이어도 D-Flow에서는 역할을 나눕니다. **개발 계정으로 시작하거나 담당한 작업을 같은 계정으로 승인할 수 없기 때문입니다.** 처음에는 기존 관리자 계정과 `개발-Mac1` 두 개만 준비해도 됩니다.

여기서 계정 세 종류를 구분하세요.

| 종류 | 쓰임새 |
|---|---|
| D-Flow 계정·토큰 | 누가 어떤 WBS 작업을 개발하는지 식별 |
| Claude Code 로그인 | 각 PC에서 AI 개발 도구 사용 |
| GitHub 로그인 | 실습 코드 내려받기·브랜치 올리기·합치기 |

D-Flow 개발 계정을 네 개 만든다고 Claude 이용 계정이나 GitHub 계정을 네 개 만들어야 하는 것은 아닙니다. 각 서비스의 이용 권한·사용량 조건에 맞게 로그인하세요. 동시 실행을 늘리면 AI 사용량도 늘어납니다.

## 3. 웹에서 먼저 설정하기 — 관리자 계정으로

아래 메뉴 이름은 현재 기본 이름입니다. 관리자가 메뉴 이름을 바꾼 워크스페이스에서는 같은 위치의 메뉴를 찾으세요.

### 3-1. 실습 프로젝트 만들기

**이동: 워크스페이스 → 전체 프로젝트 → 새 프로젝트 시작**

1. 기존 관리자 계정으로 D-Flow에 로그인합니다.
2. 워크스페이스의 **전체 프로젝트**를 엽니다.
3. 오른쪽 위 **새 프로젝트 시작**을 누릅니다.
4. **시작 방법**이 나오면 **빈 값으로 시작**을 고릅니다.
5. **프로젝트명**에 `에이전트 오피스 실습`을 입력합니다.
6. **WBS 단계**에 `단계, 묶음, 작업`을 입력합니다. 함께 제공한 WBS 파일의 단계 이름과 같습니다.
7. **프로젝트 생성**을 누릅니다.

프로젝트를 만든 뒤 주소의 `/p/` 다음 UUID를 복사해 둡니다.

```text
https://d-flow-eight.vercel.app/p/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx/settings
                                      └──────── 프로젝트 ID ────────┘
```

복사할 값은 UUID 부분만입니다. `/settings`나 `/agents/office`까지 복사하지 않습니다. 네 PC 모두 이 프로젝트 ID를 사용합니다.

### 3-2. 에이전트 기능 켜기

**이동: 실습 프로젝트 → 설정 → 기능과 메뉴를 고르는 항목**

1. 프로젝트 왼쪽 메뉴에서 **설정**을 누릅니다.
2. 설정 목차에서 이름이 `·메뉴`로 끝나는 항목을 찾습니다. 찾기 어렵다면 **설정 검색**에 `에이전트`를 입력합니다.
3. 기능 목록의 **에이전트**를 체크합니다. 꺼진 기능 접힘 목록에 있으면 먼저 펼칩니다.
4. **변경 내용 검토**를 누릅니다.
5. 추가 목록을 확인하고 **변경 저장**을 누릅니다.
6. 프로젝트 메뉴의 **팀 → 에이전트**가 나타나는지 확인합니다.

에이전트가 `워크스페이스 미허용`으로 나온다면 **플랫폼 관리자**가 먼저 아래 설정을 해야 합니다.

**워크스페이스 → 운영 → 설정 → AI가 붙은 목차 항목 → 허용 기능의 에이전트 체크 → 변경 내용 검토 → 변경 저장**

허용 기능 목록은 일반 워크스페이스 관리자에게는 보이지 않습니다. D-Flow의 챗봇용 API 키를 넣는 것과 개발 PC의 Claude Code 연결은 별개의 설정입니다.

### 3-3. 개발 계정 만들기

**이동: 워크스페이스 → 운영 → 멤버·초대 → 계정 추가**

1. 프로젝트 메뉴 위쪽의 워크스페이스로 돌아가는 링크를 누릅니다.
2. **운영 → 멤버·초대**를 엽니다.
3. 프로젝트 선택 목록에서 **에이전트 오피스 실습**을 고릅니다.
4. **계정 추가**를 누릅니다.
5. 다음처럼 입력합니다.

| 입력 칸 | 설정 |
|---|---|
| 이메일 (로그인 아이디) | 본인이 관리할 수 있는 개발용 이메일 또는 별칭 |
| 이름 | 처음에는 `개발-Mac1` |
| 워크스페이스 역할 | **멤버** |
| 이 프로젝트 권한 | **멤버** — 기본값인 조회로 두지 않기 |
| 초기 비밀번호 | **생성**을 누르거나 8자 이상 입력 |

6. **계정 만들기**를 누릅니다.
7. 네 대로 확장할 때 `개발-Mac2`, `개발-Win1`, `개발-Win2`도 같은 방법으로 만듭니다.

계정 추가는 메일을 발송하지 않습니다. 이 실습에서는 직접 만든 계정과 초기 비밀번호로 로그인하면 됩니다.

### 3-4. 프로젝트 명단에서 확인하기

**이동: 실습 프로젝트 → 팀 구성 → 명단 · 권한**

각 개발 계정에 대해 다음을 확인합니다.

- **상태**가 활성입니다.
- **권한**과 **실효 역할**이 멤버입니다.
- **계정 미연결** 표시가 없습니다.

기존 계정을 사용했는데 명단에 없다면 표 아래 **사람 추가**에서 그 계정과 같은 이메일로 추가하고, **권한 → 멤버 → 행 오른쪽 저장**을 누릅니다. 이름만 등록한 외부 인력은 에이전트 토큰의 주인으로 사용할 수 없습니다.

### 3-5. 승인 규칙을 한 단계로 맞추기

**이동: 실습 프로젝트 → 설정 → 상태·승인 → WBS 승인 흐름**

첫 실습에서는 다음처럼 단순하게 설정합니다.

| 설정 | 권장값 |
|---|---|
| 승인 단계 | 1개. 기존 기본 단계가 하나면 그대로 사용 |
| 승인자 | 프로젝트 관리자만 |
| 선행 작업 기준 | 최종 승인 뒤 후속 착수 |

**승인 단계** 구역의 **저장**을 누릅니다. 실습 WBS의 첫 5건은 서로 선행 관계가 없어 병렬로 실행할 수 있습니다. 여러 단계 승인이나 선행 의존성 시험은 기본 흐름이 성공한 뒤 추가하세요.

## 4. 실습 WBS를 메뉴에서 올리기

**이동: 실습 프로젝트 → 설정 → 일반 → WBS 데이터 가져오기 · 내보내기 → 가져오기 마법사 열기**

1. 이 안내서와 함께 있는 [agent-office-demo-wbs.md](./agent-office-demo-wbs.md)를 PC에 저장합니다.
2. **WBS 데이터 가져오기 · 내보내기** 카드의 **가져오기 마법사 열기**를 누릅니다.
3. **WBS 마크다운 (wbs.md)** 탭을 누릅니다.
4. **파일 선택**에서 `agent-office-demo-wbs.md`를 고릅니다.
5. 미리보기에서 단계 이름이 `단계 / 묶음 / 작업`인지, 검증 오류가 없는지 확인합니다.
6. **적용**을 누릅니다.
7. 프로젝트 **작업 계획**으로 이동하여 다음 작업들이 보이는지 확인합니다.

| 작업 ID | 작업 | 배정할 개발 계정 | 실행 시점 |
|---|---|---|---|
| TSK-01-01 | 이름 정리 함수 개발 | 개발-Mac1 | 첫 단독 시험 |
| TSK-02-01 | 합계 함수 개발 | 개발-Mac1 | 네 대 확장 시험 |
| TSK-02-02 | 퍼센트 표시 함수 개발 | 개발-Mac2 | 네 대 확장 시험 |
| TSK-02-03 | 안전한 나눗셈 함수 개발 | 개발-Win1 | 네 대 확장 시험 |
| TSK-02-04 | 긴 문장 줄이기 함수 개발 | 개발-Win2 | 네 대 확장 시험 |

이 파일은 `levels` 선언이 있는 현재 마크다운 형식입니다. 오류·경고 없이 파싱되는 것을 확인했고, 작업마다 명세와 수용 기준이 들어 있습니다. 아직 담당자와 자동 착수용 `agent` 태그는 넣지 않았습니다. 아래에서 웹 메뉴로 지정합니다.

메뉴의 **작업 추가 → 상세 패널의 구조 편집 → 하위 추가**로 WBS를 직접 만들 수도 있습니다. 다만 이 실습에서는 개발 스킬이 쓰는 `TSK` 식별자와 명세를 함께 갖추도록 제공한 파일을 올리는 방법을 권합니다. 작업 이름에 `TSK-01-01`만 적는 것은 가져오기 파일의 작업 ID를 설정하는 것과 다릅니다.

### 4-1. 담당자 지정하기

**이동: 작업 계획 → 작업 이름 클릭 → 상세 패널 → 담당·단계**

1. 먼저 **이름 정리 함수 개발**을 누릅니다.
2. **담당자**에서 `개발-Mac1`을 선택합니다.
3. **지금 저장**이 보이면 눌러 저장합니다.
4. 나머지 네 건은 확장 시험을 시작할 때 위 표대로 배정합니다.

**담당팀과 담당자는 다릅니다.** 자동 감시는 개인 담당자 기준으로 자기 작업을 찾으므로, 담당팀만 선택해서는 안 됩니다.

### 4-2. 명세 확인하기

같은 상세 패널에서 **명세**를 펼칩니다. **명세 본문**과 수용 기준이 보이는지 확인하세요. 고치려면 관리자가 **명세 본문 → 편집 → 저장**을 사용합니다.

예를 들어 첫 작업의 목표는 다음과 같습니다.

```text
src/normalize-name.mjs에 normalizeName(value)을 만든다.
"  홍길동  "을 넣으면 "홍길동"을 반환한다.
빈 문자열·공백뿐인 문자열·문자열이 아닌 입력은 "이름 없음"을 반환한다.
tests/normalize-name.test.mjs에 자동 테스트를 만든다.
다른 작업 파일과 package.json은 바꾸지 않는다.
npm test 전체가 통과해야 한다.
```

위임 화면의 연필로 쓰는 **에이전트 지시문**은 추가 지시입니다. **명세 본문을 비워 둔 채 지시문만 쓰면 개발 스킬의 착수 검사에서 멈출 수 있습니다.**

### 4-3. 첫 작업 하나만 위임하기

**이동: 팀 → 에이전트 → 위임·승인**

1. **전체** 보기를 선택합니다.
2. `이름 정리 함수 개발` 줄의 **위임** 체크 상자를 켭니다.
3. **지금 저장**을 누르거나 자동 저장을 기다립니다.
4. **대기(미착수)** 상태인지 확인합니다.

체크 하나로 `agent` 태그와 개발 워크플로가 켜지고 필요한 주문이 보장됩니다. 별도 태그 편집이나 주문 등록은 하지 않아도 됩니다. 아직 개발 PC를 켜지 않았다면 **에이전트 꺼짐**으로 보이는 것이 정상입니다.

## 6. 개발 PC 준비하기

설치는 각 PC에서 한 번씩 합니다. 이미 설치된 도구는 다시 설치할 필요가 없습니다. **이 문서의 터미널 명령과 `/dflow-dev` 같은 Claude 입력을 구분하세요.** `git`, `sh`, `npm`은 터미널에, `/dflow-dev`는 Claude Code 대화 입력칸에 넣습니다.

### 6-1. Mac mini 두 대

1. **응용 프로그램 → 유틸리티 → 터미널**을 엽니다.
2. [Node.js 다운로드](https://nodejs.org/en/download)에서 **24.x LTS / macOS** 설치 프로그램을 선택해 설치합니다. 개발 대상과 킷을 실행할 Node 환경입니다.
3. Homebrew가 없다면 [공식 설치 안내](https://brew.sh/)대로 설치하고, 마지막의 `Next steps` 안내도 적용합니다.
4. 터미널에서 아래를 실행합니다.

```bash
brew install git jq gh tmux
curl -fsSL https://claude.ai/install.sh | bash
```

5. 터미널을 새로 열고 확인합니다.

```bash
git --version
node --version
jq --version
gh --version
tmux -V
claude --version
```

`node --version`은 `v24.`로 시작하면 됩니다. Claude 설치·로그인은 [Claude Code 공식 설치 문서](https://code.claude.com/docs/en/setup)를 기준으로 했습니다.

### 6-2. Windows PC 두 대 — WSL2 권장

이 킷은 셸 스크립트를 사용하므로 Windows에서는 **WSL2의 Ubuntu 터미널 안에서 설치와 개발을 모두 진행하는 구성**을 권합니다. Windows용 Node와 Ubuntu용 Node는 별개입니다.

1. Windows의 **시작**에서 `PowerShell`을 검색합니다.
2. **관리자 권한으로 실행**을 선택합니다.
3. 아래 명령을 실행하고 안내에 따라 재부팅합니다.

```powershell
wsl --install
```

4. **시작 → Ubuntu**를 열고 Ubuntu 사용자 이름과 비밀번호를 만듭니다.
5. WSL2 확인은 Windows PowerShell에서 합니다.

```powershell
wsl -l -v
```

Ubuntu 줄의 `VERSION`이 `2`인지 확인합니다. 설치 조건과 문제가 생겼을 때의 절차는 [Microsoft WSL 설치 안내](https://learn.microsoft.com/en-us/windows/wsl/install)에 있습니다.

6. **이후 명령은 Ubuntu 터미널에서** 실행합니다.

```bash
sudo apt update
sudo apt install -y git curl jq gh tmux build-essential
```

7. [Node.js 다운로드](https://nodejs.org/en/download)에서 **24.x / Linux / nvm**을 선택해 표시되는 설치 절차를 Ubuntu 터미널에서 실행합니다. nvm이 설치되면 다음으로 Node 버전을 맞춥니다. nvm 설치 자체는 [nvm 공식 안내](https://github.com/nvm-sh/nvm#installing-and-updating)도 참고할 수 있습니다.

```bash
nvm install 24
nvm use 24
nvm alias default 24
```

8. 같은 Ubuntu 터미널에서 Claude Code를 설치합니다.

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

9. Ubuntu 터미널을 새로 열고 Mac과 같은 여섯 가지 버전 확인 명령을 실행합니다.

실습 저장소는 Ubuntu의 `~/work/office-demo`에 두세요. Windows의 `C:\` 경로와 Ubuntu의 경로를 섞어 사용하지 않습니다. WSL은 Claude Code의 공식 지원 설치 환경입니다. [Claude Code 설치 안내](https://code.claude.com/docs/en/setup#install-in-wsl)

### 6-3. GitHub와 Claude에 로그인하기 — 네 PC 공통

각 PC의 개발 터미널에서:

```bash
gh auth login
```

메뉴가 나오면 **GitHub.com → HTTPS → 웹 브라우저로 로그인**을 고릅니다. Git 인증 설정 질문이 나오면 동의합니다. 아래 명령의 이름·이메일은 본인 것으로 바꿉니다.

```bash
git config --global user.name "내 이름"
git config --global user.email "내 GitHub 커밋 이메일"
```

`claude`를 실행해 로그인까지 마칩니다. 로그인 후에는 `/exit`로 나와도 됩니다. 네 PC 모두 실습 GitHub 저장소에 읽기·쓰기 권한이 있어야 합니다.

### 6-4. 테스트하는 동안 절전 방지하기

| 장비 | 설정 메뉴 |
|---|---|
| Mac mini | Apple 메뉴 → 시스템 설정 → 에너지 → **디스플레이가 꺼져 있을 때 자동으로 잠자지 않게 하기** 켬 |

화면만 꺼지는 것과 컴퓨터가 잠드는 것은 다릅니다. 개발 세션이 있는 PC가 잠들면 진행과 신호가 멈춥니다. 테스트가 끝나면 원래 절전 설정으로 돌려도 됩니다. OS 버전에 따라 이름이 다르면 [Apple 잠자기 설정 안내](https://support.apple.com/ko-kr/guide/mac-help/mchle41a6ccd/mac)와 [Windows 전원 설정 안내](https://support.microsoft.com/en-us/windows/experience/power-battery/power-settings-in-windows-11)를 참고하세요.

### 7-4. PC마다 `.env`에 자기 토큰 넣기

각 PC의 **office-demo 폴더**에 `.env` 파일을 만듭니다. 숨김 파일이므로 편집기에서 파일 이름을 직접 지정하면 편합니다. 내용은 다음과 같습니다.

```dotenv
DFLOW_API_BASE=https://d-flow-eight.vercel.app
DFLOW_PATS=여기에_해당_PC_개발계정의_토큰_전체
DFLOW_PROJECT_ID=여기에_실습_프로젝트_UUID
DFLOW_AS=
DFLOW_AUTOMERGE=0
```

| 값 | 네 PC에서 같은가? |
|---|---|
| DFLOW_API_BASE | 같음 |
| DFLOW_PROJECT_ID | 같음 |
| DFLOW_PATS | **PC마다 해당 개발 계정의 토큰으로 다름** |

토큰 하나만 넣는 실습이므로 `DFLOW_AS`는 비워 둡니다. `.env`는 설치기가 `.gitignore`에 넣습니다. 개발 대상 저장소가 이미 `.env`를 쓰면 기존 내용을 지우지 말고 위 키만 추가합니다.

**이 안내서의 킷은 `.env` + `dflow.sh` 방식입니다.** 다른 리포의 dmes-standard가 쓰는 `.dflow`·`.dflow.local` + `dflow.mjs` 방식과 섞지 않습니다. 기존 dmes 스킬을 덮어쓰는 대신 새 실습 저장소를 사용하는 이유입니다.

## 8. 오피스 신호가 유지되도록 heartbeat 설정하기

에이전트가 도구를 사용할 때 보내는 생존 신호입니다. Mac mini 1은 앞의 `--hooks` 설치로 파일이 이미 복사되었습니다. 나머지 세 PC에서는 아래 방법으로 같은 파일을 준비합니다.

```bash
cd "$HOME/work"
git clone https://github.com/donseok/D-Flow.git D-Flow-kit-source
mkdir -p "$HOME/.dflow/hooks"
cp "$HOME/work/D-Flow-kit-source/kit/hooks/heartbeat.sh" "$HOME/.dflow/hooks/heartbeat.sh"
chmod +x "$HOME/.dflow/hooks/heartbeat.sh"
```

이미 원본 사본이 있으면 clone 줄은 생략합니다. Windows에서는 이 작업도 Ubuntu 안에서 합니다.

**네 PC 모두** Claude Code 사용자 설정 `~/.claude/settings.json`의 `hooks.PostToolUse`에 아래 항목을 등록합니다. 기존 설정을 통째로 바꾸지 말고 기존 배열에 한 항목만 합칩니다. 이미 등록되어 있으면 중복 추가하지 않습니다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "timeout": 5,
            "command": "if [ -x \"${HOME-}/.dflow/hooks/heartbeat.sh\" ]; then /bin/sh \"${HOME-}/.dflow/hooks/heartbeat.sh\"; else cat >/dev/null 2>&1 || :; fi"
          }
        ]
      }
    ]
  }
}
```

직접 JSON을 합치기 어렵다면 이 절을 Claude에게 보여 주고 **“기존 사용자 설정을 보존하고 이 PostToolUse 항목만 중복 없이 합쳐 줘. 토큰은 읽거나 출력하지 마.”**라고 요청하세요. Windows에서는 Windows 홈이 아닌 **Ubuntu 사용자의 홈**에 있는 설정입니다. 등록 후 Claude Code 세션을 새로 엽니다. 훅의 설정 방식은 [Claude Code 공식 훅 문서](https://code.claude.com/docs/en/hooks)를 참고했습니다.

실제 작업 중 도구를 사용하면 최대 분당 한 번 신호를 보냅니다. 오랫동안 도구 사용이 없거나 응답을 기다리면 신호가 뜸해질 수 있습니다. 이 훅은 **일감 감시용 팀장**을 등록하는 설정과는 다릅니다.

## 9. 첫 시험 — Mac mini 1에서 작업 하나 끝내기

### 9-1. 개발 시작

Mac mini 1의 `office-demo` 폴더에서 Claude Code를 새로 열어 다음을 입력합니다.

```text
/dflow-work
```

내 담당 작업 목록에서 `이름 정리 함수 개발`의 **주문 ID 앞 8자리**를 확인합니다. 목록을 못 찾으면 “내 담당 작업 목록을 조회해서 이 작업의 주문 ID를 알려 줘”라고 요청합니다. 앞에서 터미널의 `list --scope assigned`로 확인해도 됩니다.

그다음 Claude 입력칸에 실행합니다. `여덟자리주문ID`는 실제 값으로 바꿉니다.

```text
/dflow-dev 여덟자리주문ID
```

이 킷의 셸 명령은 주문 UUID·앞 8자리·현재 목록 순번을 해석합니다. `TSK-01-01`은 WBS의 작업 ID이므로, 첫 실행은 혼동을 피하려고 실제 **주문 ID**로 지시합니다.

Claude가 설계 → 구현 → 검증 → 완료 보고를 진행합니다. 판단이나 실행 권한을 물으면 해당 개발 세션에서 답합니다. 자동으로 다른 작업까지 계속 맡기지 말고 첫 작업의 완료 보고를 기다립니다.

### 9-2. 웹에서 상태 확인

관리자 브라우저에서 **실습 프로젝트 → 팀 → 에이전트 → 에이전트 오피스**를 엽니다.

| 화면 조작 | 무엇을 보나 |
|---|---|
| **전체** 선택 | 관리자 계정의 작업만 보는 필터를 피하고 개발 계정의 작업까지 확인 |
| **에이전트** 보기 | 실제 작업하는 에이전트와 PC별 현황 |
| **평면도** 보기 | 작업별 책상과 상태 |
| **상태 레인** 보기 | 업무 중·결재 대기·손봐야 함 분류 |
| 책상 클릭 | 작업 이름·진행률·마지막 신호·보고 내용 |

수동 `/dflow-dev`만 실행한 경우 **감시 중인 팀장 캐릭터가 없어도 작업 좌석이 보이면 정상**입니다. 대기 중인 PC 네 대가 항상 카드 네 개로 나오는 것을 성공 조건으로 잡지 마세요. 팀장·감시자 등록과 실제 개발 좌석은 다른 신호입니다.

### 9-3. 완료 보고 승인

**이동: 에이전트 → 위임·승인 → 승인 대기**

1. 기존 **관리자 계정**으로 보고를 엽니다.
2. 결과 링크·변경 파일·테스트 결과를 확인합니다.
3. 문제가 있으면 **반려 → 반려 사유 (필수) → 반려 확정**을 누릅니다.
4. 문제가 없으면 **승인**을 누릅니다.

자기 담당이거나 자기 계정의 에이전트가 시작한 작업이면 승인할 수 없습니다. 그래서 개발-Mac1 토큰과 승인용 관리자 로그인을 분리했습니다. **승인 단추를 누른 사실만으로 코드가 GitHub main에 합쳐진 것은 아닙니다.**

### 9-4. 승인된 코드 합치기

첫 작업을 수행한 Mac mini 1의 Claude 세션에서 다음을 실행합니다.

```text
/dflow-merge
```

이 스킬은 승인된 작업 브랜치를 찾아 합칩니다. 결과가 실습 저장소의 기본 브랜치에 반영됐는지, `npm test`가 통과하는지 확인합니다. 첫 작업이 **보고 → 승인 → 코드 반영**까지 끝나면 다음 단계로 갑니다.

## 10. PC 네 대로 늘리기

### 10-1. 웹에서 네 작업을 배정하고 위임

1. 관리자 계정으로 나머지 개발 계정 세 개의 권한과 토큰을 준비합니다.
2. **작업 계획 → 각 작업 상세 → 담당·단계 → 담당자**에서 아래처럼 배정합니다.
3. **에이전트 → 위임·승인**에서 아래 네 작업의 **위임**을 켜고 저장합니다.

| PC | 담당 계정 | 맡길 작업 | 바뀌는 코드 파일 |
|---|---|---|---|
| Mac mini 1 | 개발-Mac1 | TSK-02-01 합계 함수 | `src/sum-values.mjs` |
| Mac mini 2 | 개발-Mac2 | TSK-02-02 퍼센트 표시 함수 | `src/format-percent.mjs` |
| Windows PC 1 | 개발-Win1 | TSK-02-03 안전한 나눗셈 함수 | `src/safe-divide.mjs` |
| Windows PC 2 | 개발-Win2 | TSK-02-04 긴 문장 줄이기 함수 | `src/shorten-text.mjs` |

함수 파일과 테스트 파일이 서로 달라 처음 병렬 개발을 시험하기 쉽습니다. 공통 `package.json`이나 같은 화면 파일을 네 대가 동시에 바꾸는 시험은 나중에 하세요.

### 10-2. 각 PC에서 자기 작업 한 건씩 실행

각 PC의 개발 세션에 아래처럼 요청합니다.

```text
이 리포의 D-Flow 연결 신원과 프로젝트를 확인하고,
내게 배정된 위임 작업 한 건의 주문 ID를 보여 줘.
그 한 건만 /dflow-dev로 개발해서 완료 보고까지 진행해 줘.
다른 계정의 작업을 가져가거나 승인하지 마.
```

처음에는 네 PC 모두 수동 실행으로 시작하면 됩니다. 전부 같은 프로젝트를 쓰되 **토큰 주인과 담당자가 PC마다 다르게 맞는 것**이 핵심입니다.

### 10-3. 결과는 한 PC에서 차례대로 합치기

첫 병렬 시험은 네 PC가 모두 완료 보고를 올리고 더는 작업을 시작하지 않는 상태에서, 웹에서 네 건의 결과를 확인해 승인합니다. 코드 합치기를 네 PC에서 동시에 시작하지 말고 **Mac mini 1 한 대에서** `/dflow-merge`를 실행해 정리합니다. 원격 `agent/…` 브랜치에 보고와 결과가 올라가 있어야 다른 PC에서 만든 결과도 찾을 수 있습니다.

`/dflow-dev`도 시작할 때 승인된 작업을 합치는 절차가 있습니다. 따라서 이 첫 시험에서는 결과를 승인한 뒤 다른 PC에서 다음 `/dflow-dev`를 다시 실행하지 않고, Mac mini 1의 합치기를 먼저 끝냅니다.

다른 PC들은 진행 중인 작업을 마친 뒤, 미커밋 변경이 없는 기본 브랜치에서 최신 코드를 받습니다. 진행 중 작업의 브랜치나 미커밋 변경을 강제로 지워 맞추지 않습니다.

## 11. 그다음 단계 — 새 일감 자동 감시

수동 4대 시험이 끝난 뒤에만 진행하세요. 자동 감시는 우선 Mac mini 1에서만 켜고, 다른 PC의 자동 루프는 종료한 상태로 시험합니다. 아래 둘 중 하나를 선택합니다.

### 방법 A: 한 Mac에서 한 작업씩 순서대로 감시

Mac mini 1의 Claude Code에서:

```text
/dflow-poll --interval 60 --until 18:00
```

`18:00`은 아직 지나지 않은 오늘 종료 시각으로 바꿉니다. 이 방식은 자기 담당이면서 `agent` 태그가 켜진 작업을 한 건씩 찾습니다. 새 실습 작업의 담당자를 개발-Mac1로 지정하고, 사람이 근처에 있는 동안 시험합니다.

`dflow-poll`도 승인된 작업을 합치는 절차를 포함합니다. **머지 담당 PC만 지정하는 웹 설정이나 이 킷의 전용 옵션은 없습니다.** 네 대를 모두 자동 감시로 돌리려면 동시 머지와 실패 재시도를 조정하는 운영 방식을 별도로 검증해야 합니다. 첫 테스트에서는 네 대 수동 개발과 한 대 자동 감시를 구분하세요.

### 방법 B: 한 Mac에서 팀장과 팀원 보기

Mac mini 1의 Claude Code에서 예를 들어:

```text
/dflow-team 1명 18:00
```

- `1명`은 **그 PC에서 띄우는 팀원 수**입니다. 네 PC를 원격으로 한 명씩 켜는 뜻이 아닙니다.
- 처음에는 Mac mini 1에서만 시험합니다. 같은 PC에 팀원이 생기고, 새 일감 감시 신호가 등록되는지 확인합니다.
- 현재 Orca 세션 안에서 실행하면 Orca 탭을, 일반 터미널에서는 tmux를 이용하도록 동봉 스킬이 작성되어 있습니다. 새 작업 폴더의 신뢰 확인이 나오면 사용자가 확인해야 합니다.
- 팀장 스킬의 팀원 실행은 권한 확인 생략 모드를 사용합니다. 첫 확인은 별도 실습 저장소에서 사람이 지켜보며 합니다.
- 팀장 하나의 인원을 `4명`으로 주면 **그 PC에 팀원 네 명**을 띄웁니다. PC 네 대 분산 구성과는 다릅니다.
- 같은 D-Flow 계정의 PAT를 여러 개 발급해도 같은 신원입니다. 동일 계정의 팀장을 여러 PC에서 같은 프로젝트에 중복 실행하지 않습니다.
- 동봉 셸 킷에는 서버 lease 명령이 없으므로, 계약 2.5 서버의 lease 보호가 이 킷의 모든 팀장 실행에 자동 적용된다고 가정하지 않습니다.
- `DFLOW_AUTOMERGE=0`을 유지합니다. 승인 전 자동 합치기를 켜는 시험은 포함하지 않습니다.

**서버 계약 호환성:** 이번에 확인한 배포는 계약 2.5입니다. dmes-standard의 더 최신 Node 클라이언트는 2.11 전용 기능을 사용하기도 합니다. 이 안내서의 셸 킷과 최신 dmes 클라이언트를 섞거나, 최신 설계 단계·콘솔·heartbeat 기능까지 모두 지원한다고 생각하지 마세요. 해당 조합의 `/dflow-team` 전체 실행은 별도 검증이 필요합니다.

| 404 | 서버 주소·프로젝트 범위·멤버십·에이전트 모듈을 확인. 코드만으로 하나를 단정하지 않기 |
| 명세가 없어 시작하지 않음 | 작업 상세의 **명세 본문**을 채움. 추가 지시문만 채운 것은 아닌지 확인 |
| 계속 대기(미착수) | 웹 위임만 했는지 확인. 해당 PC에서 `/dflow-dev` 또는 감시 세션을 실제로 실행해야 함 |

| 5분 뒤 무응답, 30분 뒤 끊김 | PC 절전·네트워크·Claude 대기·사용량 제한·heartbeat 설정 확인 |
| 승인 버튼이 없거나 비활성 | 승인용 관리자 계정인지, 자기 담당·자기 시작 작업인지 확인 |
| 승인했는데 코드가 안 바뀜 | 완료 보고와 코드 반영은 별개. 원격 작업 브랜치와 `/dflow-merge` 결과 확인 |
| 선행 작업 때문에 착수 못 함 | 선행 승인 상태와 해당 코드가 기본 브랜치에 합쳐졌는지 모두 확인 |
| Windows에서 command not found | PowerShell이 아닌 Ubuntu 안에서 실행했는지, 도구도 Ubuntu에 설치했는지 확인 |
| 팀장 시작 시 DIRTY | 초기 준비 파일이나 설치기가 바꾼 설정이 남았는지 확인. 변경을 확인해 정리하고 재시작. 강제 reset으로 지우지 않기 |
| 다른 PC 팀장과 lease 충돌 | 같은 계정으로 중복 시작했는지 확인. 살아 있는 팀장을 확인하기 전에 takeover하지 않기 |

### 멈추려면

- **웹:** `에이전트 → 위임·승인 → 작업 줄의 중단 → 중단 확정`. 또는 해당 작업의 위임 체크를 해제합니다.
- **실행 PC:** 개발 세션에도 중단을 알리고 실제로 멈췄는지 확인합니다. 웹의 중단 신호 반영에는 훅·통신 시점에 따른 지연이 있습니다.
- **팀장:** 팀장 세션에 `팀장 종료`라고 입력합니다. 팀장이 끝나도 이미 실행 중인 팀원은 남을 수 있으니 개별 작업 상태를 확인합니다.
- **토큰 정리:** 개발 계정의 `내 계정 → 개인 액세스 토큰(PAT) → 해당 토큰 폐기`로 연결을 닫을 수 있습니다.
