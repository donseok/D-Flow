## 페이지 구성(장별 계획)

- **3장 준비**: 첫머리에 '준비 지도'(세 장소 × 단계)를 둔다.

  - B 웹·개발 계정: B1 PAT 발급 폼 모형. **스코프 두 칸**

## 안내서와 다른 점(매뉴얼에 반드시 반영)

1. **PAT 스코프는 두 칸 모두 체크한다.** 서버는 목록·상세 조회에 `work:read` 를 따로 본다. `work:claim` 만 있으면 403 `insufficient_scope` 가 난다. 화면의 "조회 포함" 설명은 실제와 다르다.
2. 설정 이름은 프로젝트 「모듈·메뉴」(꺼진 것은 「꺼진 모듈 (n)」), 워크스페이스 「모듈·AI」 › 「모듈 사용 범위」(플랫폼 관리자에게만 보임)다.
3. 프로젝트 관리자는 자기가 담당하거나 착수한 작업도 승인할 수 있다. 자기 승인 금지는 관리자가 아닌 상위 담당자에게만 걸린다. 계정을 나누는 이유는 담당자=토큰 주인 규칙과 신원 구분이다.
4. 「보고 확인」 단추는 없다. 승인 대기 카드에 요약·링크가 바로 보이고, 「승인」은 확인 창 없이 처리된다. 보고 본문은 오피스 상세 카드에 없다.
5. 오피스 범위는 처음부터 「전체」다. 기본 「에이전트」 보기는 착수한 좌석만 보여 준다. 빈자리·승인 대기·머지 완료는 평면도와 상태 레인에서 본다.
6. `/dflow-dev` 는 설계 → 구현 → 검증 → **정리(리팩터)** 를 거친 뒤 완료 보고한다. `dflow.sh` 는 TSK-ID 를 받지 않으므로 주문 ID 앞 8자리를 쓴다.
7. WBS 를 올리는 순간 주문이 '대기'로 이미 발행된다("적용 완료 — n건 반영, 주문 m건 발행"). 위임 체크가 더하는 것은 agent 태그로, 오피스에 좌석이 생기고 자동 감시가 집을 수 있게 된다.
8. 「머지 완료」는 승인 상태일 뿐이다. 실제 합치기는 `/dflow-merge` 가 한다.
9. 「이어서 시작」은 그 PC의 `/dflow-team` 팀장만 처리한다. `/dflow-poll`·수동 실행에서는 그 PC에서 `/dflow-dev <id8>` 를 다시 실행한다.
10. 반려 뒤 다시 일하게 하는 것은 PC 쪽이다. poll 은 자동, team 은 수동, 수동 실행이면 다시 실행해야 한다.
11. 셸 킷은 서버 lease 를 부르지 않는다. 그래서 lease 충돌은 생기지 않지만, 다른 PC에서 같은 계정으로 팀장을 띄워도 막지 못한다.
12. 실습 WBS 머리말의 `credits` 는 쓰이지 않는다. 실적은 프로젝트 크레딧(기본 착수 전 0·작업 중 30·반려 50·검수 대기 80·완료 100)을 따른다.

## 제품 쪽 확인이 필요한 것(매뉴얼과 별개)

- PAT 화면 문구 "work:claim — 조회 포함"과 서버 동작이 어긋난다(문구를 고치거나 서버가 claim 을 read 로 인정하게 하거나).
- 승인 단계가 둘 이상인 프로젝트에서 위임 표 줄의 「승인」이 단계 코드 없이 나가 거부될 수 있다(코드 판독, 재현 필요 — `DelegationTable.tsx:499-502`).
- 완료 보고 알림이 명단 권한 「관리자」 행에게만 간다. 상속 관리자는 알림을 받지 못한다.
- 팀원 신원 `<계정>/<PC>/w<N>` 에 `/` 가 들어가 서버가 `pat-…` 로 바꿔 적으면 「이어서 시작」 대상 PC 판정이 어긋날 수 있다(`routeShared.ts:80-81`).
- `dflow.sh` 순번·접두 해석이 실패해도 명령이 멈추지 않고 빈 id 로 진행한다(`dflow.sh:238-241`).
