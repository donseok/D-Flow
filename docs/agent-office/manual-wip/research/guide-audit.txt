## DIAGRAM IDEAS
- 한 장 흐름도(가로 스윔레인 4줄: 관리자·웹 / D-Flow 서버 / 개발 PC의 Claude Code / GitHub): 위임 체크 → 주문 '대기(미착수)' → /dflow-dev 착수(작업 중) → 설계 25·구현 60·검증 85% → agent 브랜치 push + 완료 보고(승인 대기) → 웹 승인(승인됨, 오피스는 '머지 완료') → /dflow-merge 로 main 합치기. '승인 ≠ 코드 합치기'를 빨간 번개 표시로 강조
- 주문 상태 기계(원과 화살표): 대기(미착수) →착수→ 작업 중 →완료 보고→ 승인 대기 →승인→ 승인됨; 반려(사유 필수)·재작업 요청은 작업 중으로, 승인 취소는 승인 대기로, 중단·위임 해제는 취소(다시 체크하면 새 대기). 작업 중 아래에 시계 아이콘으로 무응답(5분)·끊김(30분)
- WBS 단계·실적 사다리 막대: 미착수 → 할당됨 0% → 작업 중 30% → 검수 대기 80% → 완료 100%, 반려 화살표는 작업 중 50%로(개발 워크플로 크레딧 기본값)
- 누가·어디서 준비 지도(5칸 계단): 플랫폼 관리자(모듈·AI → 모듈 사용 범위 → 에이전트) → 워크스페이스 관리자(새 프로젝트 시작·멤버·초대 계정 추가·명단 권한) → 프로젝트 관리자(모듈·메뉴 에이전트, WBS 승인 흐름, wbs.md 업로드, 담당자, 위임) → 개발 계정(내 계정 → PAT) → 각 PC(킷 설치·.env·heartbeat 훅)
- 메뉴 경로 칩 카드: 자주 쓰는 10개 경로를 '전체 프로젝트 › 새 프로젝트 시작'처럼 버튼 모양 칩으로 나열하고 각 칩에 누가 할 수 있는지 배지
- 권한 매트릭스 표(○/×): 조회 전용·멤버·작업 담당자·상위 항목 담당자·프로젝트 관리자 × 화면 열기/위임·지시문/승인/반려·승인 취소·재작업/중단·이어서 시작/단계 변경. 관리자 칸에 '자기 담당도 승인 가능' 각주
- PAT 발급 화면 목업에 번호 풍선: ① 이름(office-mac1) ② 허용 프로젝트 '전체' 체크 해제→실습만 ③ 스코프 두 칸 모두 체크(조회+claim, 경고 아이콘) ④ 만료 30일 ⑤ 토큰 발급 ⑥ 복사(한 번만 보임)
- PC 4대 토폴로지: 가운데 D-Flow 웹(주소·프로젝트 ID 하나), 위에 GitHub office-demo(저장소 하나), 둘레에 PC 4대 — 각 PC에 다른 개발 계정·다른 PAT, 같은 DFLOW_API_BASE·DFLOW_PROJECT_ID. 'PC마다 다른 값은 DFLOW_PATS 하나' 말풍선
- .env 파일 해부도: 다섯 줄 각각 옆에 라벨(같음/PC마다 다름/비워 둠/0 유지)과 '절대 공유 금지' 자물쇠
- 브랜치 그림: main ─ agent/<주문8자>-<이름> 가지(설계·구현·검증·정리 커밋, DFlow-Order 트레일러) ─ push ─ 웹 승인 ─ --no-ff 머지 커밋 'merge: TSK… (approved)' + phase=merged 커밋 ─ agent 브랜치 삭제
- heartbeat 판단 순서도: 도구 사용 → git 리포인가 → agent/ 브랜치(또는 .dflow-agent)인가 → 진행 중 state.json 인가 → 60초 지났나 → .env 있나 → 신호 전송 → 응답이 409 cancelled 면 표식 파일 남기고 세션 정지
- 오피스 화면 해부도: 머리 숫자 칸(보기마다 다름), 도구 줄(보기 전환·완료 포함·잡담·내 작업/전체), 에이전트 보기 PC 카드(팀장/단독 감시·팀원·빈자리·자리 n/m), 평면도(층=프로젝트, 구역=상위 항목, 책상=주문), 상태 레인 4줄, 상세 카드 다섯 칸 사다리
- '계속 대기(미착수)' 문제 해결 결정 나무: 사유 칩 확인 → 위임 필요(체크) / 선행 대기(선행 끝내기·합치기) / 에이전트 꺼짐(PC에서 /dflow-dev 또는 감시 실행) / 에이전트 바쁨(기다리기) / 착수 대기(감시 PC 로그 확인)
- 수동 vs 자동 비교표 3열: /dflow-dev(한 건, 태그 무관, 질문은 그 화면에서) · /dflow-poll(agent 태그+내 담당, 한 건씩, 승인 감지 시 머지, 반려 자동 재작업, '단독 감시') · /dflow-team(팀원 최대 4, 30분마다 머지, 이어서 시작 처리, 반려는 사람이 재시작, '팀장')
- 위임 체크 한 번의 효과 그림: [☑] → agent 태그 + 개발 워크플로 + 주문(대기) → 오피스에 좌석 생김 / 감시자가 집어감. 반대로 [☐] → 대기·작업 중 주문 취소, 단계 할당됨
- dflow.sh 종료 코드 신호등 표: 0 초록, 4·10 노랑(상태·중단), 2·3·5·7 빨강(설정·인증·권한·꺼짐), 6 회색(네트워크) — 각 줄에 '먼저 볼 곳'
- wbs.md 업로드 전후 비교 그림: 왼쪽 파일(PH/WP/TSK 들여쓰기, requirements·acceptance) → 오른쪽 웹(코드 office-demo/TSK-01-01, 명세 본문 '## 요구사항', 수용 기준 체크 목록, 주문 5건 '대기', 사유 '위임 필요')

- '에이전트 토큰 만료 임박' 알림은 목록에만 있고 만드는 코드를 찾지 못했다 — 매뉴얼에 언급할지, 기능이 예정인지.
- 오피스 '머지 완료' 표기가 실제로는 '승인됨'을 뜻하는 점 — 화면 문구를 바꿀 계획이 있는지, 매뉴얼은 '승인됨(코드 합치기 전일 수 있음)'으로 설명할지.
- 승인용 관리자 계정을 실습 프로젝트 명단에 권한 '관리자'로 넣을지: 넣지 않으면 '완료 보고 — 승인 요청' 알림을 받지 못한다(프로젝트를 만들어도 명단에 자동으로 안 들어감).
- 'claim/release/완료보고 (work:claim)' 설명의 '조회 포함' 문구가 서버 동작과 다른데, 화면 문구를 고칠지(코드 변경은 이 감사 범위 밖) 아니면 매뉴얼에서 '두 칸 모두 체크'로만 안내할지.
- /dflow-dev 사용법이 'TSK-ID'도 받는다고 적혀 있지만 dflow.sh 는 받지 않는다 — 매뉴얼 예시를 주문 8자로 통일할지.
