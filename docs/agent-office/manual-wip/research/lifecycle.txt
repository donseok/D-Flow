## DIAGRAM IDEAS
- 주문 상태 기계: 상자 5개(ready·claimed·reported·approved·cancelled)를 왼쪽→오른쪽으로 놓고 화살표마다 사건 이름과 주체를 색으로 구분(PC/API=파랑: claim·완료 보고·반납, 웹 사람=주황: 승인·반려·승인 취소·재작업 요청·중단·위임 해제). cancelled 는 이중 테두리 종착점, approved→reported/claimed 는 점선 '되감기', approved/cancelled 에서 새 ready 로 가는 점선 '재발행(새 주문 ID)'. 각 상자 아래에 세 화면 이름(위임·승인 칩 / 오피스 좌석 / WBS 패널 칩)을 작게 병기.
- 스윔레인 시퀀스(4줄: 관리자 웹 | D-Flow 서버 | 개발 PC의 Claude Code+킷+훅 | GitHub): 위임 체크 → poll(scope=assigned+agent 태그) → show(명세·선행 검사) → claim(단계 작업 중·30%) → heartbeat 60초 루프 → progress 보고 → push → done(검수 대기·80%) → 웹 승인(완료·100%) 또는 반려(작업 중·50%, 사유가 PC로) → /dflow-merge 로 기본 브랜치 합치기. '승인 ≠ 머지' 말풍선을 승인 화살표 옆에.
- 단계 사다리(가로 진행 막대): 미착수(—) → 할당됨 as 0% → 작업 중 ip 30% → 검수 대기 im 80% → 완료 xx 100%. 작업 중 위에 '반려·재작업 rw 50%' 되돌이 화살표, 검수 대기 안에 다단계 승인 칸(1/2 ✓ → 2/2 ✓). 칸마다 '누가 옮기나'(사람 배정 / PC 착수 / PC 완료 보고 / 사람 승인)와 자물쇠 아이콘(위임·점유 중 사람 직접 변경 금지).
- 착수(claim) 관문 깔때기: 위에서 아래로 11칸(ID 형식 → 본문 → 토큰 인증 → work:claim → user_email 일치 → 주문·토큰 범위 → 멤버 → 에이전트 기능 → 담당자 → 선행 → ready 상태). 각 칸 오른쪽에 막히면 나오는 HTTP·code·dflow.sh exit 와 해결 한 줄. 옆에 별도 상자로 '킷만 하는 검사: 명세 본문·로컬 선행 커밋·프로젝트 바인딩·agent 태그(자동 감시)'.
- 신호 타임라인: 마지막 신호 0분 ──5분(무응답)──30분(끊김) 띠 그래프. 위에 '결정 대기'는 시간과 무관하게 덮는 반투명 막, '반려 · 재작업'은 0~5분 구간에만. 아래 별도 축 두 개: 감시자 70분(감시 중→감시 없음), 착수 24시간(WBS 패널 '응답 없음'). 신호를 만드는 것 목록(heartbeat 훅·progress·완료 보고·결재)과 만들지 않는 것(이어서 시작).
- 토큰 범위 벤 다이어그램: 원 4개(발급 워크스페이스 / 허용 프로젝트 / 내 명단 권한 관리자·멤버 또는 워크스페이스 관리자 / 에이전트 기능 켜짐)의 교집합 = /me 에 보이는 프로젝트. 바깥은 404(존재 숨김). 구석에 '플랫폼 관리자도 승격 없음' 메모.
- 스코프 × 엔드포인트 체크 표: 행=me, work, work/mine, work/{id}, wbs/structure, claim, heartbeat, report, release, watch, lead/lease, wbs/import / 열=스코프 없음·work:read·work:claim. 표 위 경고 배지 'work:claim 은 조회를 포함하지 않음 — 둘 다 체크'.
- 중단 흐름도: [중단 확정 또는 위임 체크 해제] → 주문 cancelled + 단계 할당됨(as) → (훅 있음) 다음 도구 사용 때 heartbeat 409 cancelled → 세션 정지 메시지 / (훅 없음) 다음 progress·done 409 → dflow.sh exit 10. 끝에 '다시 맡기기 = 위임 체크 → 새 주문 ID'와 'reported 는 취소 안 됨 → 승인·반려로 정리' 갈림길.
- 다단계 승인 도식: 검수 대기(im) 상자 안에 단계 칩 1→2→3, 중간 승인은 주문 reported 유지·실적 불변, 마지막 승인에서 완료(xx)·100%. 승인자 종류(상위 담당자 또는 관리자 / 프로젝트 관리자만)와 '단계마다 다른 승인자' 규칙, 반려 시 그 라운드 승인 전부 철회 표시.
- 팀장 lease 도식: (계정+프로젝트) 의자 1개, 180초 모래시계, renew 화살표(holder·generation 일치), 다른 팀장의 acquire → 409 lead_lease_held, takeover 로 의자 빼앗기 → 옛 팀장 renew 가 lost → 물러남. '동봉 셸 킷은 사용 안 함' 꼬리표.
- 같은 주문의 세 화면 이름 대응표: 행=ready / claimed(5분 안) / claimed 5~30분 / 30분+ / blocked / 반려 뒤 / reported / approved / cancelled, 열=DB 값 · 위임·승인 칩 · 오피스 좌석 · WBS 상세 칩 · dflow.sh 약어(RD/CL/RP/AP/CX).
- 오류 대응 카드 표: HTTP·code → 쉬운 뜻 → dflow.sh exit → 할 일(예: 401 토큰 확인·폐기·만료·보관 워크스페이스 / 403 insufficient_scope 스코프 재발급 / 403 not_assignee 담당자·계정 연결 / 403 dependency_not_met 선행 끝내기 / 404 기능·범위·멤버 / 409 conflict 상태 확인 / 409 cancelled 멈춤 / 429 10분 대기).
## OPEN
- 팀원 신원 라벨 '<신원>/<host>/w<슬롯>'에는 '/'가 들어가는데 서버는 agent 라벨을 영숫자·._- 64자만 받아(AGENT_NAME_RE) 맞지 않으면 claimed_by 를 'pat-<토큰 id 8자>'로 바꿔 적는다(src/lib/agent/routeShared.ts:80-81, src/lib/domain/agentWork.ts:69). '이어서 시작'의 대상 PC 는 claimed_by 에서 뽑으므로(src/lib/domain/agentWork.ts:164-171) /dflow-team 팀원 좌석의 재개 요청이 엉뚱한 host('pat-xxxxxxxx')로 기록되고 팀장의 same_host 판정(.claude/skills/dflow-team/SKILL.md:297-305)도 어긋날 수 있다. 실제 팀장 운영에서 확인이 필요하다.
- 승인 뒤에도 agent 태그가 남는데, 담당자 재지정·WBS 재가져오기·개발 워크플로 대상 재설정 같은 발행 계기가 생기면 완료(xx) 작업에도 새 대기 주문이 발행된다(src/lib/agent/ensureOrder.ts:57-79, src/app/actions/wbsAssign.ts:176-186). 이때 자동 감시가 그 주문을 다시 착수하면 단계가 작업 중으로 돌아가는지(claim 은 단계를 확인하지 않음) 운영 정책·실측 확인이 필요하다.
- 담당자 없는 위임 작업을 화면은 '착수 대기'로 보여 주지만 동봉 킷의 자동 감시는 scope=assigned 만 본다. 화면 문구를 고칠지, 매뉴얼에서 '자동 착수에는 담당자 지정 필수'로 안내할지 결정이 필요하다.
- '머지 완료' 좌석 이름은 실제로는 '승인됨'(approved)이다. 매뉴얼에서 '승인됨(합치기는 별도)'로 풀어 쓸지, 화면 라벨 자체를 바꿀지 제품 결정이 필요하다.
- 운영 서버(d-flow-eight)의 AGENT_API_ENABLED 값과 워크스페이스별 에이전트 허용 상태는 리포만으로 확인할 수 없다(네트워크 확인 금지). 매뉴얼은 '모든 호출이 404 면 관리자에게 기능 켜짐 확인'으로 안내하는 수준이 안전하다.
- 요청 제한(같은 IP 10분 30회 실패)은 서버 인스턴스별 메모리 카운터라 Vercel 다중 인스턴스에서는 실제 한도가 더 느슨할 수 있다. 매뉴얼에 숫자를 그대로 적을지 '여러 번 실패하면 잠시 막힘'으로 적을지 정해야 한다.
- lead lease 를 실제로 부르는 클라이언트(원본 wbs-web·dmes-standard 의 Node 클라이언트, 계약 2.11)는 이 리포 밖이다. 이 매뉴얼(동봉 셸 킷 기준)에서 lease 를 다룰 범위 — 개념 소개만 할지, 409 lead_lease_held 대응까지 쓸지 — 결정이 필요하다.
- 발급 화면의 work:claim 설명 '조회 포함'과 서버 동작(조회 미포함)이 어긋난다. 화면 문구·서버 중 어느 쪽을 맞출지는 제품 결정이며, 그 전까지 매뉴얼은 '두 칸 모두 체크'로 안내해야 한다.
