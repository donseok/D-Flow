# 사용자 매뉴얼 메뉴 — 설계

- 날짜: 2026-10-16
- 요청: "사용자 매뉴얼을 만들고 싶어. 이 프로젝트에 하나의 메뉴로 넣어야 돼. 언제든지 확인 가능하도록 최대한 쉽고 자세하게."
- 사용자 결정(2026-10-16, 네 가지 모두 권고안):
  1. 진입점 = 워크스페이스 사이드바 항목 + 계정 메뉴 링크(프로젝트 안에서도 두 번 누르면 열린다)
  2. 독자 = 등급별 장 구분 — 보는 사람이 쓸 수 없는 관리자 장은 목차에서 숨기고, 장마다 대상 표지를 붙인다
  3. 그림 = 글 먼저. 스크린샷은 다음 차례(자리만 비워 두지 않는다 — 글만으로 따라 할 수 있게 쓴다)
  4. 내용 관리 = 리포 안 마크다운 파일. 기능이 바뀌면 코드와 함께 고치고 배포로 반영한다. DB 변경 없음

## 1. 목표와 성공 기준

- 로그인한 누구나 어느 화면에서든 두 번 이내의 클릭으로 매뉴얼을 연다.
- 처음 쓰는 사람이 매뉴얼만 보고 자기 등급에서 할 수 있는 일을 끝까지 해낼 수 있다 — 버튼·메뉴 이름이 화면과 글자 그대로 같고, 순서가 번호로 적혀 있다.
- 매뉴얼에 적힌 기능은 모두 실제로 있는 기능이다(코드·사전에서 확인한 것만 쓴다).
- 낱말로 찾을 수 있다(검색).
- 매뉴얼이 낡으면 고치기 쉽다 — 장 하나가 파일 하나다.

비목표: 스크린샷·동영상, 관리자가 화면에서 고치는 편집기, 영어판, 화면별 '?' 버튼(다음 차례 후보).

## 2. 사용자 경험

### 2.1 진입점
- 워크스페이스 사이드바 `ws.main` 그룹 맨 끝에 **사용자 매뉴얼**(아이콘 `BookOpenText` — `navIcons` 표에 이미 있다). 모든 등급에 보인다(`needs: null`), 모듈이 아니므로 끌 수 없다.
- 계정 메뉴(오른쪽 위 이름 버튼)에 **사용자 매뉴얼** 링크 — 프로젝트 화면에서는 사이드바가 프로젝트 메뉴로 바뀌므로 이 링크가 진입점이다.
- 주소는 슬러그 없는 전역 화면 `/help`·`/help/<장>` — `(global)` 레이아웃 아래(계정·플랫폼 관리 화면과 같은 셸).

### 2.2 `/help` — 매뉴얼 첫 화면
- 제목 "사용자 매뉴얼"과 한 줄 안내.
- 내 등급 안내: "○○ 등급이라 아래 장들이 보입니다." 등급 판독이 실패하면 "권한 정보를 불러오지 못해 일반 사용자용 장만 보여 줍니다"(조회 실패를 숨기지 않는다 — 서버 로그도 남긴다).
- 검색창(GET `?q=`): 제출하면 같은 화면에 결과 목록 — "장 제목 › 절 제목"과 본문 발췌, 누르면 그 절로 간다. 결과가 없으면 "찾는 낱말이 없습니다" + 검색 팁. 검색은 서버에서 하고 보이는 장만 뒤진다(클라이언트로 전체 본문을 보내지 않는다).
- 부(part)별 장 카드: 장 제목 + 요약 한 줄 + 대상 표지(관리자 장만).

### 2.3 `/help/<장>` — 장 화면
- 넓은 화면: 왼쪽에 장 목록(부별, 현재 장 강조), 가운데 본문. 좁은 화면: 장 목록은 본문 위 접힘 목록.
- 본문 맨 위: 장 제목, 대상 표지, "이 장의 내용" 절 목록(앵커 링크).
- 본문 아래: 이전 장 / 다음 장 링크(보이는 장 기준), "매뉴얼 처음으로".
- 보는 사람 등급보다 높은 장을 주소로 직접 열면 숨기지 않고 보여 주되 "이 장은 ○○용입니다 — 지금 등급에서는 이 기능이 보이지 않을 수 있습니다" 안내를 붙인다(매뉴얼은 비밀이 아니다 — 목차 숨김은 편의다).
- 없는 장은 404.

### 2.4 등급
`member < projectAdmin < workspaceAdmin < platformAdmin`. 보는 사람의 등급 = 가진 것 중 가장 높은 것:
- 플랫폼 관리자(`isSuperuser`) → platformAdmin
- 어느 워크스페이스든 `admin` → workspaceAdmin
- 어느 프로젝트든 명단 `access_role='admin'` → projectAdmin
- 그 밖 → member
판정은 순수 함수(`src/lib/domain/authz.ts` 옆 규칙 — §4.2)로, 가드가 아니다(매뉴얼은 로그인만 요구한다). 장은 자기 대상 등급 이하인 사람에게 목차·검색에 보인다.

### 3.2 글쓰기 규칙(모든 장)
- 존댓말(~합니다/~하세요), 한 문장에 한 가지. 개발 용어 금지(RPC·RLS·모듈·DB·토큰 등 → "기능", "설정", "권한"으로 풀어 쓴다).
- 버튼·메뉴·탭·칸 이름은 **화면 글자 그대로** 굵게 쓴다 — 사전(`src/lib/i18n/dict/*`)과 화면 코드에서 확인한 것만.
- 따라 하기는 번호 목록, 한 단계에 한 동작. 결과("저장됨이 보입니다")까지 적는다.
- 장 머리: 제목 아래 "이 장에서 할 수 있는 일" 목록, 누가 쓸 수 있는지.
- 팁·주의는 인용 블록: `> **팁** …`, `> **주의** …`.
- 예시는 지어낸 일반 값(예: "조업 To-Be 프로세스"처럼 실제 고객·실명이 아닌 것). 고객명·실명 금지.
- 화면에 없는 기능, 확인하지 못한 동작은 쓰지 않는다. 등급·설정에 따라 달라지면 그 조건을 적는다.
- 다른 장으로는 `/help/<장>` 또는 `/help/<장>#<절>` 링크로 보낸다(검사가 끊긴 링크를 잡는다).

## 4. 구조

### 4.1 내용 파일과 적재
- 원본: `src/content/manual/<NN>-<slug>.md`. 머리말(frontmatter):
  ```
  ---
  title: 주간보고
  part: daily            # start | daily | projectAdmin | workspaceAdmin | platformAdmin | help
  audience: member       # member | projectAdmin | workspaceAdmin | platformAdmin
  summary: 업무영역별 주간 실적과 계획을 시트에 쓰고 보고서로 내려받습니다.
  ---
  ```
  장의 주소 조각(slug) = 파일 이름에서 번호를 뺀 것(`06-weekly` → `weekly`). 순서 = 번호.
- 런타임에 파일을 읽지 않는다 — `scripts/manual-build.mjs`(`npm run manual:build`)가 원본을 모아 `src/content/manual/chapters.generated.ts`(원문 문자열 배열)를 만들고 그 파일을 커밋한다. 배포 번들이 파일 추적에 기대지 않는다(인증 뒤 화면이라 배포 뒤 curl 로 확인할 수 없어서 런타임 fs 를 피한다).
- `tests/manual/content.test.ts`: 생성 파일이 원본과 같은지(다르면 "npm run manual:build 를 돌리세요"), 머리말 필수 칸·값, slug 유일, 장 안 `/help/…` 링크와 `#앵커` 가 실제로 있는지, 본문이 비지 않았는지, 금지어(개발 용어 목록) 검사.
- 파서·색인은 순수 모듈 `src/lib/manual/`:
  - `parse.ts` — 머리말 해석, 절(제목 `##`·`###`) 추출과 앵커(한글 보존 slug, 장 안에서 유일), 검색용 평문.
  - `chapters.ts` — 생성 파일을 해석해 장 목록(순서·부·대상)을 한 번 만든다. 해석 오류는 throw(테스트가 먼저 잡는다).
  - `search.ts` — 보이는 장들에서 낱말 찾기(공백으로 나눈 낱말 모두 포함, 대소문자 무시), 결과는 장·절·발췌.

### 4.2 등급 판정
- `src/lib/domain/authz.ts` 에 순수 함수 `manualAudienceOf(actor: Actor | null): ManualAudience`(규칙 §2.4, null → member). 액션이 아니라 판정 위치 규칙(판정은 domain/authz·authz/** 두 곳)에 맞춘다.
- 페이지는 `getActorViewState()` 의 actor 로 판정한다. `degraded` 거나 actor 가 없으면 member + 안내 + `console.error`.

### 4.3 화면
- `src/app/(app)/(global)/help/page.tsx`(첫 화면·검색), `src/app/(app)/(global)/help/[chapter]/page.tsx`(장). 둘 다 서버 컴포넌트.
- `src/components/manual/`: `ManualArticle`(react-markdown + remark-gfm — 이미 의존성, 제목에 앵커 id, 내부 링크는 next/link, 표·인용 블록 모양), `ManualChapterNav`(부별 장 목록), `ManualSearchResults`.
- 화면 글자(제목·안내·등급 이름·부 이름·검색 문구)는 사전 `src/lib/i18n/dict/` 의 `manual.*` 키. 본문은 내용 파일(사전 아님 — `src/components`·`src/app` 밖이라 한국어 리터럴 검사 대상이 아니다).
- `globals.css` 는 건드리지 않는다 — 본문 모양은 컴포넌트에서 기존 토큰 클래스로 준다.

### 4.4 메뉴
- 내비 id `ws.help` 추가(26 → 27): `src/lib/nav/ids.ts`(목록·그룹 `ws.main`), `src/lib/nav/registry.ts` SHELL_NAV `{ id: 'ws.help', labelKey: 'nav.help', icon: 'BookOpenText', segment: '/help', group: 'ws.main', order: 90, scope: 'workspace', needs: null }`, 사전 `nav.help` = "사용자 매뉴얼". 플랫폼 관리자 화면을 더할 때와 같은 파생 지점(메뉴 설정 검증·사용 현황 메뉴 표·`ui-capture.routes.json`·모듈 페이지 관문 예외·내비 테스트의 개수)을 같이 고친다.
- 계정 메뉴 `src/components/app/AccountMenu.tsx` 에 `/help` 링크 — **UI 위험 파일**이므로 브랜치 작업, 로컬 눈확인 뒤 `Preview-checked: local …` 트레일러(CLAUDE.md).

### 4.5 오류 처리
- 내용 해석 오류는 빌드 전 테스트가 잡고, 런타임에 나면 throw(오류 화면) — 빈 매뉴얼로 위장하지 않는다.
- 등급 판독 실패는 member 로 좁히고 화면 안내 + 로그(§2.2).
- 검색어는 길이 상한(100자)과 공백 정리 뒤 사용. 빈 검색어는 첫 화면.

## 5. 테스트
- 내용 검사(§4.1), 파서·앵커·검색 단위 테스트, `manualAudienceOf` 표 테스트.
- 화면: jsdom 으로 첫 화면(등급별 목차 걸러짐·판독 실패 안내·검색 결과·결과 없음), 장 화면(앵커 목록·이전/다음·상위 등급 장 안내·없는 장 404).
- 내비: `ws.help` 가 모든 등급에 보이고 `/help` 로 간다, 개수 27.
- 계정 메뉴에 `/help` 링크.
- 전체 `npm run test`·`lint`·`build`.

## 6. 작업 순서
1. 바탕: 내용 형식·생성기·파서·색인·검색·등급 판정 + 테스트(장 2개 맛보기 원본으로).
2. 화면·메뉴·사전 + 테스트.
3. 계정 메뉴 링크(UI 위험 파일).
4. 본문 작성 — 장마다 실제 화면 코드와 사전을 읽고 쓴다(서로 다른 파일이라 나눠 쓸 수 있다).
5. 정확성 검토 — 다른 눈이 장마다 버튼 이름·절차·등급 조건을 코드와 대조, 고친다.
6. 생성·전체 검증, 로컬 눈확인, 머지·배포(배포는 사용자 확인 뒤).
