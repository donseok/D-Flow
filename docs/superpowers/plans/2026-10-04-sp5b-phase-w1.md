## 결정 기록(구현 중)

- 대기 단계가 없을 때(스냅샷 없음 — D15, 또는 그 라운드가 이미 다 승인된 im — 서비스 경로로 단계만 되돌린 행) 판정 사건은 **새 라운드를 연다**.
  D15 의 일반화다 — 승인은 늘 열린 라운드의 대기 단계에 기록되고, 기존 패리티 테스트의 `arrange`(서비스 경로로 stage 만 맞춤)가 그대로 돈다.
- `set_stage 'xx'` 가 이미 xx 인 항목에 오면 승인 판정 없이 현행(실적만 맞춘다).
- `approve_step` 은 dev_workflow 를 보지 않는다(D14 의 "im 대기 라운드는 흐름을 꺼도 승인으로 끝낸다"와 같은 축). 잠금(위임·점유)은 `locked`, im 아닌 항목은 `not_in_review`.
- `updateActual` 은 행 값만으로 되는 판정(잠금·스냅샷 단계 수)을 앱에서 먼저 하고, 설정을 읽어야 하는 판정은 DB 가드(JWT 경로라 반드시 돈다)가 같은 문구로 막는다 —
  기존 액션 테스트의 조회 큐를 늘리지 않는다. 문구는 `WBS_ACTION_ERRORS.approvalRequired`(화면은 사전 `wbs.err.approvalRequired`).
- 승인 판정 재료 로더 `src/lib/agent/approvalState.ts` 는 단위 테스트 전역 셋업(`tests/setup/module-gate.ts`)이 기본 1단계로 mock 한다(호환 규칙 S1 —
  승인 액션을 import 하는 기존 테스트의 admin 큐가 밀리지 않게). 로더 자체는 `tests/agent/approval-state.test.ts` 가 진짜 모듈로 본다.
- 중간 단계 알림 `work.approval_step` 수신자는 `work.reported` 와 같은 기준(프로젝트 명단의 관리자, 승인한 본인 제외) — 서브트리 관리자까지 넓히는 것은 W2 의 승인 가능 셈과 함께.
- `getWbsAssigneeStage` 의 `approval` 은 쓰이는 때(im, 또는 유효 단계 ≥2)만 싣는다 — 기존 반환 형태 단언을 지킨다.
- 선행 기준(final)의 소비처 주입(claim 게이트·대기 사유·화면)은 W2(D21) — W1 의 E2E 는 승인 흐름까지, "후속 claim 403 → 허용" 은 W2 가 `workflow-approval` 에 더한다.
  W1 에서 `final` 은 RPC 첫 도달(`reached_first`)에만 반영된다.
- E2E 시드는 화면과 같은 액션 경로(addWbsItem → setWbsAssignee → setWbsDevWorkflow — 주문 자동 발행)다. 명단 행(나·carol)만 service_role 로 넣는다.
- main 의 CI 수정 둘을 이 브랜치 시작 전에 처리했다: `settings-writes` 의 e2e 참조 수(I 의 issue-status-flow), test 잡 제한 시간 15 → 25분(단위 1.2만 건 + build 가 15분 경계).
